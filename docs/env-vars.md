# Environment Variables

## Required

- `DISCOGS_TOKEN` -- Discogs API token

## Optional

- `DATABASE_URL_DISCOGS` -- PostgreSQL URL for Discogs cache
- `DATABASE_URL_MUSICBRAINZ` -- PostgreSQL URL for the musicbrainz-cache. Powers the MB leg of the `/api/v1/lookup` external-cache fallback (Phase 1.5 mojibake recovery). Optional; when unset the MB leg is skipped.
- `SPOTIFY_CLIENT_ID` -- Spotify client ID for streaming availability checks
- `SPOTIFY_CLIENT_SECRET` -- Spotify client secret for streaming availability checks
- `SENTRY_DSN` -- Sentry error tracking. Init lives in [`wxyc-fastapi`](https://github.com/WXYC/wxyc-fastapi); LML calls `init_sentry(service_name="library-metadata-lookup", environment=settings.environment, ...)` at startup. The default `HttpxIntegration` is on, so outbound calls (Discogs, Spotify, Deezer, Apple Music, Bandcamp) are traced.
- `POSTHOG_API_KEY` -- PostHog telemetry. Client construction lives in `wxyc-fastapi` as a process-wide singleton; LML wraps it with the LML-side `enable_telemetry` flag via per-caller dependencies built by `core/dependencies._make_posthog_client_dep` (`get_posthog_client` for `/lookup`, `get_streaming_posthog_client` for `/api/v1/streaming-check`). When this is unset the shared singleton warns once per caller `event_prefix`, so each endpoint surfaces its own missing-key warning under its own `caller=` label (LML#659).
- `LIBRARY_DB_PATH` -- Path to SQLite database (default: `library.db`)
- `ADMIN_TOKEN` -- Bearer token for admin endpoints (upload endpoint)
- `STREAMING_WEBHOOK_URLS` -- Comma-separated URLs to POST streaming status changes after library.db upload
- `ETL_NOTIFY_KEY` -- Bearer token used by LML when *pushing* the streaming-status webhook to tubafrenzy
- `LML_API_KEY` -- Bearer token required from tubafrenzy / Backend-Service callers (see "Inbound Auth" below)
- `LML_REQUIRE_AUTH` -- When `true`, enforce `LML_API_KEY` on protected endpoints. Default `false` (see rollout phasing in `core/auth.py`)
- `LML_RESOLVE_ARTIST_CANONICAL` -- When `true`, the canonical-artist resolver pre-pass in `search_compilations_for_track` swaps the inbound artist name for the top trigram match in `discogs-cache` when the similarity score >= `CANONICAL_ARTIST_SIMILARITY_FLOOR` (`lookup/orchestrator.py`). Default `false`. When the flag is `false`, the entire pre-pass is skipped — no PG trigram lookup, no `resolver_pre_pass` log line, no Sentry attribute. This is the cost-saving path (~50 ms / lookup) until calibration clears the swap to be enabled. To enable the swap, run `scripts.resolver_calibration` against the discogs-cache, confirm FP-rate ≤ 0.5% at the chosen floor, document the run in `docs/resolver-calibration/`, and flip the flag in Railway. See WXYC/library-metadata-lookup#318 and #343.
- `LML_RESOLVE_COMPILATION_RELEASE` -- When `true`, the artwork **binding step** (`fetch_artwork_for_items` in `lookup/orchestrator.py`) consumes the `discogs_titles` seam the LML#604 way: it **trust-and-binds** a `ResolvedRelease` the search strategy already carried (skipping the artist-floor re-search), and when its floor search returns `None` and a `song` is present it **lazily** runs `resolve_release_for_track` as a fallback — binding the validated release (typically a Various-Artists compilation) without the 80/80 artist floor. The lazy probe honors `LML_RESOLVE_ARTIST_CANONICAL` (canonical-swap) and fires the album-title wave, matching the live `search_compilations_for_track` probe; an unresolvable row is **negative-cached** (L1, keyed on `(song, artist, album)`) so a steady poll never re-probes. Default `false` — a floor-rejected release stays unbound and carried releases re-search exactly as before (pre-PR2). **Never enabled on `/lookup/bulk`** (the drain passes `allow_release_resolution_fallback=False`, so the 35k-album backfill can't trigger the per-row Discogs fan-out). Roll staging → prod, watch the Discogs call-rate (`release_resolution_bind` log line / Sentry attribute). See WXYC/library-metadata-lookup#604.
- `LML_RESOLVE_NONLIBRARY_RELEASE` -- When `true`, **five** row-less producers **surface a resolvable Discogs release that is NOT in `library.db` as a row-less result** instead of dropping it. Three are track-validating strategies (`TRACK_ON_COMPILATION` / `search_compilations_for_track`, `SONG_AS_TRACK` + `SWAPPED_INTERPRETATION` / the shared `_match_track_releases_to_library` kernel, all in `lookup/orchestrator.py`): they otherwise drop a non-library release on the library-row gate (LML#628 "A1 carry-through"). The fourth, `SONG_AS_ARTIST` (`search_song_as_artist`, LML#631), surfaces a row-less pick over the releases the artist probe already fetched; the fifth, the A4 cached-track safety net (`find_library_albums_with_cached_track`, LML#629), surfaces one over the Discogs-cache track confirmations — both without an extra resolve or cache write. Because per-release track-validation is deferred until *after* the library gate (LML#536), a non-library release is otherwise discarded before the validation that would confirm it. With the flag on, when the library walk surfaces no row, the release is resolved + validated via the **uncached, bounded** `resolve_release_for_track(max_validations=5)` (LML#633 — the L1 `resolve_release_for_track_cached` wrapper is *not* used; its key omits `max_validations`) and surfaced as `LibraryItem(id=0)` + a real `DiscogsSearchResult` (the same row-less shape `_library_miss_discogs_search` produces — real `release_id`/`release_url`, **not** the BS#1185 `release_id=0` sentinel). The resolution is amortized by the **LML#632 PG positive cache** (`lml_cache.release_resolution_cache`, keyed on the **typed** artist + track, 90-day positive / 7-day miss TTL) threaded in as `discogs_cache_pg`, so a repeat add does not re-pay search+validate. The row-less bind in `fetch_artwork_for_items` is gated on this flag for `id==0` items (independent of `LML_RESOLVE_COMPILATION_RELEASE`). **Never enabled on `/lookup/bulk`** (the drain passes `allow_release_resolution_fallback=False`): the per-request kill switch is threaded into **all five** row-less producers and the `id==0` artwork bind, so on the backfill path none of those five pays the carry-through resolve, writes the #632 cache, or surfaces a row-less result — parity with the `LML_RESOLVE_COMPILATION_RELEASE` bulk exclusion (LML#652). (Scope note: the separate `_library_miss_discogs_search` path (LML#583) — which fires on a typed artist+album library miss and is **not** gated on this flag — surfaces a confident Discogs album match row-less via a single `search` call, not the resolution fan-out. It **also honors the bulk kill switch** (LML#671): on `/lookup/bulk` (`allow_release_resolution_fallback=False`) Step 3a is skipped, so it pays no per-row `search` and surfaces no row-less item. This gate is load-bearing for the bulk no-row-less invariant: the album-only backfill shape (artist+album, no song) hits *this* producer, not the five song-bearing ones above, so #583 was the only un-gated row-less producer that shape reached on bulk (it fires solely on a library-miss, so on a library-resident drain like the documented album backfill it's a tail, not every row) until LML#671 closed it. On `/lookup` it still fires exactly as before, independent of this flag.) Default `false` — a non-library release stays dropped (today's empty/sentinel behavior). Roll staging → prod, watch the Discogs call-rate. **Telemetry (LML#681):** the flip is sliceable through the per-request `cache_stats` dict (projected to PostHog as `cache.<key>` and onto the Sentry transaction as `lml.cache.<key>` via the router's existing `_project_cache_stats_to_transaction` — which, as of LML#683, attaches each numeric key **two ways**: as span `data` for per-trace drill-down in the trace explorer **and** as a transaction *measurement* so the value is aggregatable and can back a metric alert. `set_data` alone reads back as "Unknown attribute" in the spans/metrics datasets, so a metric alert on it is impossible; the measurement is the alertable series, e.g. `avg(measurements[lml.cache.api_calls])` for the Discogs call-rate guard and `lml.cache.release_resolution_cache_miss` / `_unavailable` for the silent-outage proxy. `traces_sample_rate=1.0` (LML's `init_sentry` default), so the measurement series covers every request, not a sampled fraction): `lml_resolve_nonlibrary_release` (and the companion `lml_resolve_compilation_release`) carry the flag state as `0`/`1`, recorded once per `cache_stats` context at the router (`_record_lml_flag_tags`, right after `init_cache_stats`) so the shared-context `/lookup/bulk` batch reports `0`/`1`, never summed to the batch size; `nonlibrary_release_surfaced` counts each **flag-gated** row-less `id=0` emission at the single `_make_rowless_item` chokepoint (`0` when the flag is off — the un-gated #583 `_library_miss_discogs_search` `id=0` path builds its item directly and is **excluded by construction**); and `release_resolution_cache_hit` / `release_resolution_cache_miss` / `release_resolution_cache_unavailable` report the #632 positive cache from `get_cached_release_id` — **hit** on `was_present` (a fresh positive id **or** a fresh known-miss short-circuit; both skip the live probe, which is the amortization this proves), **miss** only on the absent/stale `row is None` branch, **unavailable** on the PG-exception branch (a degradation kept apart so an outage can't inflate the miss rate). All keys are seeded into `_LML_CACHE_STATS_EXTRA_KEYS` so the payload shape is stable (LML#544). See WXYC/library-metadata-lookup#628 (and #604/#616 for the in-library bind, #626/#632/#633 for the prerequisites, #652 for the bulk kill switch, #671 for the #583 bulk gate, #681 for this telemetry).
- `LML_PERSIST_STREAMING_URLS` -- **Master kill switch** for the persistent streaming-URL cache post-process in `/api/v1/lookup` (LML#573, generalizing the LML#571 Apple-only flag). When `true` (default), `/api/v1/lookup` post-processes every item whose per-service URL came out null and runs a cache-backed probe per *enabled* service using the **request's** `(artist, album)` independent of the item's library row. When `false`, the entire post-process short-circuits regardless of the per-service flags — one-flip disable of Apple + Spotify persistence without a re-deploy. Successful resolutions persist to `lml_cache.album_streaming_url_cache` (keyed by `(service, artist_normalized, album_normalized)`) so subsequent lookups hit the cache rather than re-querying upstream; known misses are recorded with a 7-day TTL. Live resolutions also mint the parsed ID into `entity.release_identity`. The schema is bootstrapped at startup via `set_up_streaming_url_cache_schema` in `main.py` lifespan (`CREATE SCHEMA IF NOT EXISTS lml_cache` + `CREATE TABLE`); if the discogs-cache PG is unreachable, the cache layer degrades to a no-op (every request pays one extra probe).
- `LML_PERSIST_STREAMING_URL_APPLE_MUSIC` / `LML_PERSIST_STREAMING_URL_SPOTIFY` -- **Per-service flags** for the streaming-URL cache post-process. **AND-gate: a service is persisted only when BOTH `LML_PERSIST_STREAMING_URLS` (master) AND its per-service flag are `true`.** The master defaults `true` and the per-service flags default `false`, so the feature is **off until Railway sets a per-service flag** — flipping the master alone enables nothing. Set both to `true` in Railway (staging + prod) to enable Apple + Spotify persistence. Rollback per service: flip its flag `false` (no re-deploy). There is **no deprecated alias** for the old `LML_PERSIST_APPLE_MUSIC_URL` — ops renames the Railway env var (`LML_PERSIST_APPLE_MUSIC_URL` → `LML_PERSIST_STREAMING_URL_APPLE_MUSIC`) before this deploys; if the rename is forgotten, Apple persistence silently stays off until corrected. See WXYC/library-metadata-lookup#573 (and #570/#571 for the originating Apple-only shape).
- `LML_SEARCH_BUDGET_MS` -- Soft budget (ms) for `execute_search_pipeline`; default 4000. Short-circuits the cascade once `state.results` is non-empty (LML#340). When the caller sends `X-Caller-Budget-Ms`, the effective budget is `min(caller − 200ms, env)` (LML#345), AND the cascade also short-circuits when `state.results` is empty (Epic A no-results tail follow-up; sets `state.timed_out=True`). The empty-state cutoff is only active when the caller explicitly opts in via the header — without a header, the cascade keeps grinding past the budget for the no-results case (preserves warm-cache / write-path semantics). Tune via Railway env; values must be a positive integer (unparseable/zero/negative fall back to the default with a WARN).
- `LML_APPLE_MUSIC_LOOKUP_TIMEOUT_MS` -- Per-call wall-clock ceiling (ms) for `AppleMusicClient.find_track_url` from the lookup hot path (`lookup/orchestrator.enrich_one`); default 4000. Wraps the call in `asyncio.wait_for` so a single Apple-side retry storm (worst case 2×5s with the LML#450 trim) can't pull the rest of the enrichment past its deadline. On timeout the item degrades to no-Apple-URL — same path as the LML#444 exception guard. Values must be a positive integer (unparseable/zero/negative fall back to the default with a WARN). See LML#449 + LML#450.
- `LML_ARTIST_IDENTITY_SPLIT_GATE` -- When `true` (default), the `extended=true` lookup path gates `artist_bio` / `wikipedia_url` / `profile_tokens` / `discogs_artist_id` AND the LML#487 Apple Music probe's `artwork_url` on the LML#504 `artist_identity_verified` composite predicate: request artist ↔ (`item.artist` OR `item.alternate_artist_name`) ↔ `top1_release.artist` each at `score_match >= 80` (Discogs disambiguation suffix stripped symmetrically before scoring -- numeric `(2)`, country `(UK)`, and word `(band)` forms all caught), neither side a `is_compilation_artist` alias. The artwork gate fires on the library-row hop alone (so a fuzzy-collision row doesn't surface a stranger's cover via the synth-path probe) and runs per-item, not just on top-1. Set the env var to any common false spelling -- `false`, `0`, `no`, `off`, `disabled` (case-insensitive, whitespace-trimmed) -- to revert ALL of those fields (bio + wiki + profile_tokens + discogs_artist_id + artwork_url) to the broader `is_album_derived_eligible` / LML#487 behavior that PR #500 introduced. Read at request time via `os.getenv` so the knob flips without a redeploy. The split predicate only takes effect when `LookupRequest.extended=true` AND a non-empty `artist` was supplied AND the library row carries a non-empty artist anchor (album-only lookups and corrupted library rows fall back to the legacy gate so they don't lose bio); BS forces `extended=true` on every wire call, so the split exercises on all BS write-path traffic immediately. Divergence between the new and legacy gates emits shadow-mode telemetry under category `artist_identity_split_gate` regardless of the rollback flag, so the divergence signal stays visible during rollback; the breadcrumb is silenced on album-only and empty-anchor paths since those trivially diverge without affecting bio surfacing. See LML#504.
- `LML_MB_RESCUE_REQUIRE_SONG_MATCH` -- When `true` (default), the MusicBrainz tracklist rescue (`lookup/orchestrator.enrich_one` → `resolve_tracklist_via_musicbrainz`) runs a post-resolver song-presence sanity check (`clients.streaming.matching.score_match_track` against each track title at the shared 80 acceptance floor). When the DJ's requested `song` doesn't appear in the rescued tracklist, the candidate is dropped — likely a sibling-release leak (LML#506 Deluxe-vs-Original shape: long album-title substring clears the resolver's lenient 0.70 trigram floor, but `LIMIT 1` returns the wrong edition). Set the env var to any common false spelling -- `false`, `0`, `no`, `off`, `disabled` -- to bypass the sanity check and surface the resolver's `LIMIT 1` tracklist unconditionally (pre-LML#506 behavior). Read at request time via `os.getenv` so the knob flips without a redeploy. The check is skipped on artist+album picker lookups (`song is None`); the resolver-side `_SIMILARITY_FLOOR` (0.70) and this check's per-track floor (80) are co-tuned and should be bumped together on calibration. Known limitation: only the bonus-only-track Deluxe variant is caught; shared-track-Deluxe leaks (DJ requests a track present on both editions) pass undetected — telemetry surfaces both populations under `lookup.mb_resolver.requested_album` / `returned_album` and `lookup.mb_rescue.song_sanity_rejected`. See LML#506.
- `LML_SEARCH_MAX_API_CALLS` -- Per-invocation cap on Discogs API calls dispatched from one `_chunked_gather` invocation (one strategy leg's validation tail); default 15. Sized above the warm-cache `extended=true` happy-path window (8-14 calls measured) so legitimately-busy lookups don't trip, while still bounding the zero-canonical failing tail flagged in LML#543 (15-24 calls / 16-17s wall time per failing leg). The gate is **baseline-relative**: each `_chunked_gather` captures the request's `stats["api_calls"]` at entry and checks `(current − baseline) >= cap` between chunks. Per-invocation (not request-wide) on purpose: a request-wide cap would (1) starve later items in `/api/v1/lookup/bulk` batches that share one cache_stats dict, and (2) silently disable the LML#319/#237 album-title fallback whose own `_chunked_gather` follows the main loop in `search_compilations_for_track`. In-flight calls inside the current chunk run to completion — the gate is between chunks, not mid-chunk, so the actual ceiling per invocation is `cap + chunk_size − 1` where `chunk_size = MAX_SEARCH_RESULTS = 5`. Read at request time via `os.getenv` (shared `resolve_positive_int_env` helper from `core/search`) so the value flips without a redeploy. Misconfigured values (negative, zero, unparseable) fall back to the default with a WARN. Telemetry: each cap-fire increments `search_api_call_cap_fired` on the per-request cache-stats dict (a counter — for batch-aggregate PostHog), AND bumps a separate per-task `ContextVar` counter (`core.search._cap_fire_count_var`) for runner-side control flow. `execute_search_pipeline` reads the per-task counter (NOT the shared cache_stats dict) so concurrent `/api/v1/lookup/bulk` items can't race-poison each other; after each strategy, when the strategy fired the cap AND the natural-completion gate (`state.results and not state.song_not_found`) didn't fire, the runner sets `state.timed_out=True` and short-circuits the cascade. The complementary gate means: a strategy that surfaced a confirmed song match keeps `timeout=False` (natural completion wins), and a strategy that surfaced an artist-fallback `Outcome.artist_fallback` keeps the timeout signal (so the cap actually bounds wall time in the `song_not_found` cascade). The cache_stats counter projects onto the Sentry transaction as `lml.cache.search_api_call_cap_fired` via the router's existing `_project_cache_stats_to_transaction`; filter on `lml.cache.search_api_call_cap_fired:>0` for the cap-fire slice.
- `LML_SEARCH_HARD_TIMEOUT_MS` -- Hard ceiling (ms) on `execute_search_pipeline` wall time; default 25000. Fires regardless of `state.results` to bound cascade-exhaustion tail latency (LML#370). Wrapped around every strategy via `asyncio.wait_for`, so a single slow Discogs cascade gets cancelled with its in-flight `gather()` probes — frees the Discogs semaphore on cap-fire. Unlike the soft budget, callers cannot raise this via header (safety floor, not a budget). To effectively disable, set well above the request timeout (e.g. `600000`). Telemetry: `hard_cap_fired:true` projects onto the Sentry transaction; response carries `LookupResponse.timeout: true`.

## Cross-cache-identity feature flags

Per-cache toggles for which `wxyc_library` hook table the matcher reads (legacy schema vs. new normalized schema), plus an emergency rollback flag for the §3.2.2.1 manual-override skip endpoint. All default `false`.

The **canonical inventory** (with naming-convention rationale, phase state machine, rollout-checklist locations, and approval gates) lives in `WXYC/Backend-Service/CLAUDE.md` "Cross-cache-identity feature flags (canonical inventory)". When a flag is renamed or its default changes, both the canonical Backend section AND this list must update in the same PR; CI on this repo grep-asserts the names listed here match the §4.2 inventory.

| Flag | Scope | Default | Set true when |
|---|---|---|---|
| `LML_USE_NEW_HOOK_DISCOGS` | per-cache (Docker discogs, port 5433) | `false` | Docker discogs cache parity-check passes 7 consecutive days |
| `LML_USE_NEW_HOOK_DISCOGS_FULL` | per-cache (Homebrew full discogs) | `false` | Homebrew (full) discogs cache parity-check passes 7 consecutive days |
| `LML_USE_NEW_HOOK_MUSICBRAINZ` | per-cache | `false` | musicbrainz cache parity-check passes 7 consecutive days |
| `LML_USE_NEW_HOOK_WIKIDATA` | per-cache | `false` | wikidata cache parity-check passes 7 consecutive days |
| `LML_MANUAL_OVERRIDE_CHECK_DISABLED` | global | `false` | Emergency rollback only — disables the §3.2.2.1 manual-override skip endpoint call. Backend's write rules still reject low-confidence reruns of manual rows correctly, just less efficiently. |

Production location: Railway environment variables for the LML service. Updater is Jake via the Railway dashboard. The per-cache flags require 7 consecutive days of clean parity-check audit (E5 daily report); `LML_MANUAL_OVERRIDE_CHECK_DISABLED` is for unscheduled emergency rollback only.

Plan reference: `WXYC/wiki/plans/library-hook-canonicalization-plan.md` §4.2.

## Inbound Auth (`LML_API_KEY`)

`core/auth.py:require_lml_key` is a FastAPI dependency that validates `Authorization: Bearer <LML_API_KEY>` on every tubafrenzy / Backend-Service-facing endpoint. Wired in `main.py` via `app.include_router(..., dependencies=[Depends(require_lml_key)])` for the `lookup`, `library`, `discogs`, and `streaming` routers.

Three auth surfaces in this service, intentionally separate:

| Surface | Direction | Env var | Implementation |
|---|---|---|---|
| Inbound from tubafrenzy / Backend-Service | tubafrenzy → LML | `LML_API_KEY` | `core/auth.py:require_lml_key` (router-level dep) |
| `/admin/*` (library.db upload) | ETL → LML | `ADMIN_TOKEN` | `routers/admin.py:_validate_auth` (per-route call) |
| Outbound streaming-status webhook | LML → tubafrenzy | `ETL_NOTIFY_KEY` | `routers/admin.py:_send_streaming_webhook` (sends `Authorization: Bearer ...`) |

Untouched: `/health`, `/identity/resolve`, `/identity/bulk`. Identity routes are consumed by semantic-index too, so locking them down is a separate decision.

**Rollout:** `LML_REQUIRE_AUTH` defaults to `false` so the dep can ship before consumers send the header. Once tubafrenzy and Backend-Service are updated, flip the flag in Railway to enforce.
