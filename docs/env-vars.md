# Environment Variables

## Required

- `DISCOGS_TOKEN` -- Discogs API token

## Optional

- `DATABASE_URL_DISCOGS` -- PostgreSQL URL for Discogs cache
- `DATABASE_URL_MUSICBRAINZ` -- PostgreSQL URL for the musicbrainz-cache. Powers the MB leg of the `/api/v1/lookup` external-cache fallback (Phase 1.5 mojibake recovery). Optional; when unset the MB leg is skipped.
- `SPOTIFY_CLIENT_ID` -- Spotify client ID for streaming availability checks
- `SPOTIFY_CLIENT_SECRET` -- Spotify client secret for streaming availability checks
- `SENTRY_DSN` -- Sentry error tracking. Init lives in [`wxyc-fastapi`](https://github.com/WXYC/wxyc-fastapi); LML calls `init_sentry(service_name="library-metadata-lookup", environment=settings.environment, ...)` at startup. The default `HttpxIntegration` is on, so outbound calls (Discogs, Spotify, Deezer, Apple Music, Bandcamp) are traced.
- `POSTHOG_API_KEY` -- PostHog telemetry. Client construction lives in `wxyc-fastapi` as a process-wide singleton; LML wraps it with the LML-side `enable_telemetry` flag via per-caller dependencies built by `core/dependencies._make_posthog_client_dep` (`get_posthog_client` for `/lookup`, `get_streaming_posthog_client` for `/api/v1/streaming-check`). When this is unset the shared singleton warns once per caller `event_prefix`, so each endpoint surfaces its own missing-key warning under its own `caller=` label (LML#659).
- `LIBRARY_DB_PATH` -- Path to SQLite database (default: `library.db`). In local-directory storage mode (see below) this path's **parent directory** is also the object-store root, so `streaming_availability.db` resolves as its sibling — the local-dev layout. In bucket mode (the staging/production posture since the volume eviction, LML#834) the bucket is the object store and this path is only the boot-fetch destination for `library.db`, on the Dockerfile-created ephemeral `/data` dir (no longer a mounted volume).
- `LML_BUCKET_NAME` / `LML_BUCKET_ENDPOINT` -- Railway Bucket name and S3 endpoint URL for object storage (the bucket's `BUCKET` and `ENDPOINT` variable references). When **both** are set, LML serves `library.db` and `streaming_availability.db` from an S3-compatible Railway Bucket instead of a local `/data` volume — the zero-downtime, replica-ready posture from the volume-eviction epic (WXYC/library-metadata-lookup#834). When either is unset (the default), storage falls back to local-directory mode rooted at `LIBRARY_DB_PATH`'s parent. Selection happens once in `core/dependencies.get_object_store`; exactly one store is active per deployment (no dual-write, no fallback chain). This is the active staging/production posture since the 2026-07 cutover (PRs #835–#837 landed the store, endpoints, and `library.db` boot-fetch; #838/#839 executed the per-environment cutovers and removed the volume — see the [cutover runbook](deployment.md#cutover-runbook-data-volume--railway-bucket)).
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` -- S3 credentials for the Railway Bucket, read by `boto3` **natively** (LML never references them in code). Railway's bucket variable-reference presets provision these standard names, so bucket mode needs no LML-specific credential vars. Only consulted when bucket mode is active (`LML_BUCKET_NAME` + `LML_BUCKET_ENDPOINT` both set).
- `LML_BUCKET_ADDRESSING_STYLE` -- S3 addressing style for the bucket client: `virtual` (default; virtual-hosted `<bucket>.<endpoint>` — the format Railway serves for newly created buckets, so no override is needed), `path` (`<endpoint>/<bucket>` — required only by **legacy** pre-change buckets, as the bucket's Credentials tab states), or `auto`. Passed verbatim to botocore's `Config(s3={"addressing_style": ...})` and validated at Settings load (an out-of-range value fails loudly at boot). Only consulted in bucket mode. See WXYC/library-metadata-lookup#834.
- `ADMIN_TOKEN` -- Bearer token for admin endpoints (upload endpoint)
- `STREAMING_WEBHOOK_URLS` -- Comma-separated URLs to POST streaming status changes after library.db upload
- `ETL_NOTIFY_KEY` -- Bearer token used by LML when *pushing* the streaming-status webhook to tubafrenzy
- `LML_API_KEY` -- Bearer token required from tubafrenzy / Backend-Service callers (see "Inbound Auth" below)
- `LML_REQUIRE_AUTH` -- When `true`, enforce `LML_API_KEY` on protected endpoints. Default `false` (see rollout phasing in `core/auth.py`)
- `LML_API_KEY_CACHE_REFRESH_SECONDS` -- How often (seconds) the in-process per-consumer API-key cache (`core/api_key_cache.py`'s `ApiKeyCache`, backed by `lml_cache.api_keys`) reloads its active-key snapshot from the discogs-cache PG; default 300 (`ge=1`). Introduced by the LML per-consumer API keys plan (`docs/plans/lml-per-consumer-api-keys.md`), which replaces the single shared `LML_API_KEY` with one row per consumer (tubafrenzy, Backend-Service, wxyc-canary, the operator drain script) so a leaked or rotated credential no longer has to move in lockstep across every consumer. This knob bounds **revocation staleness**: a revoked key stays valid in an already-booted process for up to this long after the revoke lands in PG -- fine for a planned rotation (issue-new -> confirm -> revoke-old), not a substitute for `LML_REQUIRE_AUTH=false` if a key needs to die immediately. A refresh failure (a transient PG blip) never clears the existing snapshot -- only a successful fetch swaps it -- so a slow discogs-cache does not intermittently 403 every consumer. An out-of-range value raises a startup validation error (no silent fallback), mirroring `DISCOGS_SEARCH_STATEMENT_TIMEOUT_MS`'s `ge=1`. `require_lml_key` accepts a resolving table-backed key OR the legacy `LML_API_KEY` throughout the migration (dual-accept); see `docs/plans/lml-per-consumer-api-keys.md` for the full rollout and the PR that eventually retires the legacy branch.
- `LML_RESOLVE_ARTIST_CANONICAL` -- When `true`, the canonical-artist resolver pre-pass in `search_compilations_for_track` (`lookup/strategies/track_on_compilation.py`) swaps the inbound artist name for the top trigram match in `discogs-cache` when the similarity score >= `CANONICAL_ARTIST_SIMILARITY_FLOOR` (`core/thresholds.py`). Default `false`. When the flag is `false`, the entire pre-pass is skipped — no PG trigram lookup, no `resolver_pre_pass` log line, no Sentry attribute. This is the cost-saving path (~50 ms / lookup) until calibration clears the swap to be enabled. To enable the swap, run `scripts.resolver_calibration` against the discogs-cache, confirm FP-rate ≤ 0.5% at the chosen floor, document the run in `docs/resolver-calibration/`, and flip the flag in Railway. See WXYC/library-metadata-lookup#318 and #343.
- `LML_RESOLVE_COMPILATION_RELEASE` -- When `true`, the artwork **binding step** (`fetch_artwork_for_items` in `lookup/artwork.py`) consumes the `discogs_titles` seam the LML#604 way: it **trust-and-binds** a `ResolvedRelease` the search strategy already carried (skipping the artist-floor re-search), and when its floor search returns `None` and a `song` is present it **lazily** runs `resolve_release_for_track` as a fallback — binding the validated release (typically a Various-Artists compilation) without the 80/80 artist floor. The lazy probe honors `LML_RESOLVE_ARTIST_CANONICAL` (canonical-swap) and fires the album-title wave, matching the live `search_compilations_for_track` probe; an unresolvable row is **negative-cached** (L1, keyed on `(song, artist, album)`) so a steady poll never re-probes. Default `false` — a floor-rejected release stays unbound and carried releases re-search exactly as before (pre-PR2). **Never enabled on `/lookup/bulk`** (the drain passes `allow_release_resolution_fallback=False`, so the 35k-album backfill can't trigger the per-row Discogs fan-out). Roll staging → prod, watch the Discogs call-rate (`release_resolution_bind` log line / Sentry attribute). See WXYC/library-metadata-lookup#604.
- `LML_RESOLVE_NONLIBRARY_RELEASE` -- When `true`, **five** row-less producers **surface a resolvable Discogs release that is NOT in `library.db` as a row-less result** instead of dropping it. Three are track-validating strategies (`TRACK_ON_COMPILATION` / `search_compilations_for_track`, in `lookup/strategies/track_on_compilation.py`; `SONG_AS_TRACK` + `SWAPPED_INTERPRETATION` / the shared `_match_track_releases_to_library` kernel, in `lookup/strategies/track_release_matching.py`): they otherwise drop a non-library release on the library-row gate (LML#628 "A1 carry-through"). The fourth, `SONG_AS_ARTIST` (`search_song_as_artist`, LML#631), surfaces a row-less pick over the releases the artist probe already fetched; the fifth, the A4 cached-track safety net (`find_library_albums_with_cached_track`, LML#629), surfaces one over the Discogs-cache track confirmations — both without an extra resolve or cache write. Because per-release track-validation is deferred until *after* the library gate (LML#536), a non-library release is otherwise discarded before the validation that would confirm it. With the flag on, when the library walk surfaces no row, the release is resolved + validated via the **uncached, bounded** `resolve_release_for_track(max_validations=5)` (LML#633 — the L1 `resolve_release_for_track_cached` wrapper is *not* used; its key omits `max_validations`) and surfaced as `LibraryItem(id=0)` + a real `DiscogsSearchResult` (the same row-less shape `_library_miss_discogs_search` produces — real `release_id`/`release_url`, **not** the BS#1185 `release_id=0` sentinel). The resolution is amortized by the **LML#632 PG positive cache** (`lml_cache.release_resolution_cache`, keyed on the **typed** artist + track, 90-day positive / 7-day miss TTL) threaded in as `discogs_cache_pg`, so a repeat add does not re-pay search+validate. The row-less bind in `fetch_artwork_for_items` is gated on this flag for `id==0` items (independent of `LML_RESOLVE_COMPILATION_RELEASE`). **Never enabled on `/lookup/bulk`** (the drain passes `allow_release_resolution_fallback=False`): the per-request kill switch is threaded into **all five** row-less producers and the `id==0` artwork bind, so on the backfill path none of those five pays the carry-through resolve, writes the #632 cache, or surfaces a row-less result — parity with the `LML_RESOLVE_COMPILATION_RELEASE` bulk exclusion (LML#652). (Scope note: the separate `_library_miss_discogs_search` path (LML#583) — which fires on a typed artist+album library miss and is **not** gated on this flag — surfaces a confident Discogs album match row-less via a single `search` call, not the resolution fan-out. It **also honors the bulk kill switch** (LML#671): on `/lookup/bulk` (`allow_release_resolution_fallback=False`) Step 3a is skipped, so it pays no per-row `search` and surfaces no row-less item. This gate is load-bearing for the bulk no-row-less invariant: the album-only backfill shape (artist+album, no song) hits *this* producer, not the five song-bearing ones above, so #583 was the only un-gated row-less producer that shape reached on bulk (it fires solely on a library-miss, so on a library-resident drain like the documented album backfill it's a tail, not every row) until LML#671 closed it. On `/lookup` it still fires exactly as before, independent of this flag.) Default `false` — a non-library release stays dropped (today's empty/sentinel behavior). Roll staging → prod, watch the Discogs call-rate. **Telemetry (LML#681):** the flip is sliceable through the per-request `cache_stats` dict (projected to PostHog as `cache.<key>` and onto the Sentry transaction as `lml.cache.<key>` via the router's existing `_project_cache_stats_to_transaction` — which, as of LML#683, attaches each numeric key **two ways**: as span `data` for per-trace drill-down in the trace explorer **and** as a transaction *measurement* so the value is aggregatable and can back a metric alert. `set_data` alone reads back as "Unknown attribute" in the spans/metrics datasets, so a metric alert on it is impossible; the measurement is the alertable series — the live LML#683 alerts query it on the Sentry **EAP spans** dataset as `avg(tags[lml.cache.api_calls,number])` (Sentry disabled transaction-based metric alerts org-wide, so the `avg(measurements[lml.cache.api_calls])` transactions form is unavailable) for the Discogs call-rate guard, with `release_resolution_cache_miss` / `_unavailable` the silent-outage proxy. `traces_sample_rate=1.0` (LML's `init_sentry` default), so the measurement series covers every request, not a sampled fraction): `lml_resolve_nonlibrary_release` (and the companion `lml_resolve_compilation_release`) carry the flag state as `0`/`1`, recorded once per `cache_stats` context at the router (`_record_lml_flag_tags`, right after `init_cache_stats`) so the shared-context `/lookup/bulk` batch reports `0`/`1`, never summed to the batch size; `nonlibrary_release_surfaced` counts each **flag-gated** row-less `id=0` emission at the single `_make_rowless_item` chokepoint (`0` when the flag is off — the un-gated #583 `_library_miss_discogs_search` `id=0` path builds its item directly and is **excluded by construction**); and `release_resolution_cache_hit` / `release_resolution_cache_miss` / `release_resolution_cache_unavailable` report the #632 positive cache from `get_cached_release_id` — **hit** on `was_present` (a fresh positive id **or** a fresh known-miss short-circuit; both skip the live probe, which is the amortization this proves), **miss** only on the absent/stale `row is None` branch, **unavailable** on the PG-exception branch (a degradation kept apart so an outage can't inflate the miss rate). All keys are seeded into `_LML_CACHE_STATS_EXTRA_KEYS` so the payload shape is stable (LML#544). See WXYC/library-metadata-lookup#628 (and #604/#616 for the in-library bind, #626/#632/#633 for the prerequisites, #652 for the bulk kill switch, #671 for the #583 bulk gate, #681 for this telemetry). **Alert wiring, thresholds, baseline rationale, and the kill-switch runbook live in [`observability-rowless-flag.md`](observability-rowless-flag.md) (LML#683).**
- `LML_RESOLVE_ARTIST_VARIATIONS` -- When `true`, `TRACK_ON_COMPILATION` (`search_compilations_for_track` in `lookup/strategies/track_on_compilation.py`) admits a title-matched library row whose `artist`/`alternate_artist_name` is an **exact** normalized name-variation of the resolved **non-compilation** Discogs release's artist entity — bridging a row filed under a band name or abbreviated alias (e.g. "Burning Star Core" / "C.S. Yeh") to a typed personal name ("C. Spencer Yeh") that prefix-matching misses. Keyed on the release id via `DiscogsCacheService.get_release_artist_variations` (`release_artist` → `artist` / `artist_name_variation`, `extra = 0`). **Exact membership** (not prefix, so a bare variation like "Yeh" can't admit an unrelated longer row) and **non-compilation releases only** (a V/A release's `extra = 0` artist is the "Various" entity, whose variations carry no identity signal and would bypass the compilation title-score floor). The variation lookup is **lazy** (only a row that clears neither the strict artist filter nor the compilation carve-out consults it) and **best-effort / fail-closed** (a cache miss/outage yields no bridge, never a strategy failure); every admitted row still passes `validate_release_for_track` on the typed artist. Default `false`; roll staging → prod like the sibling resolve flags. See WXYC/library-metadata-lookup#971.
- `LML_TIGHTEN_COMPILATION_TITLE_CARVEOUT` -- When `true` (default), `TRACK_ON_COMPILATION`'s compilation-artist title carve-out (both the strict branch and the album-title fallback's `_fallback_row_acceptable` in `lookup/strategies/track_on_compilation.py`) additionally requires a library row's title to be length-comparable to the Discogs release title (`min(len)/max(len) >= 0.9`) on top of the existing `fuzz.ratio >= 80` floor. LML#973: the ratio floor alone can't tell "same comp, reformatted title" from "different comp, similarly-worded title" -- e.g. "Greatest Hits Of The 50's" vs "Greatest hits of the 50s & 60s" clears `ratio >= 80` (87.3) despite naming a different, track-less pressing. Default `true` -- the #973 fix is active on merge, no rollout needed. Set `false` to revert to the pre-#973 ratio-floor-only admission without a redeploy, if the guard turns out to cost more recall than it fixes in prod. See WXYC/library-metadata-lookup#973.
- `LML_LIBRARY_RELEASE_OVERRIDE` -- When `true`, `/api/v1/lookup` consults a durable, hand-verified `library_id -> discogs_release_id` pin before the fuzzy release pick. The orchestrator (`_step_fetch_artwork` in `lookup/orchestrator.py`) prefetches all pins for the request's library rows in **one** query against `lml_cache.library_release_override` (keyed by `library_id = ANY($1)`, via `get_library_release_overrides` in `entity/library_release_override.py`), and `fetch_one` (`lookup/artwork.py`) binds the pinned release **before** the LML#604 trust-bind block and the LML#478 artist-floor fuzzy `search`. A hand-verified human override is the most-trusted signal, so it wins even over a carried release; an override hit also short-circuits the fuzzy `search` + its Discogs call. The pinned release then flows through enrichment on the **normal** LML#477/#487 title gate (`row_title_matches_requested_album` in `lookup/enrichment/item.py`) — there is deliberately **no** override carve-out: a genuine library-album lookup (request album == the catalog row title, which the dj-site picker and BS flowsheet-linkage both send) passes the gate and the pin's tracklist surfaces, while a request whose album diverges from the surfaced row's title collapses to the `release_id=0` sentinel exactly as before (so a pin can never leak a mismatched row's release **or** its curated `streaming_links`). The prefetch is **skipped on the `/lookup/bulk` drain** (`allow_release_resolution_fallback=False`), parity with the sibling bulk exclusions. When `false`, no prefetch runs and resolution is the pre-override fuzzy pick, byte-for-byte (zero added PG/Discogs work). The table is bootstrapped at startup via `set_up_library_release_override_schema` in `main.py` lifespan (`CREATE SCHEMA IF NOT EXISTS lml_cache` + `CREATE TABLE`); if the discogs-cache PG is unreachable the prefetch degrades to an empty map and `/lookup` falls through to the fuzzy pick. Seed the table with the verified data (`scripts/seed_library_release_overrides.py`, dry-run default) **before** flipping this `true`; ship dark, verify on staging, then flip in Railway. Fully reversible: `DELETE FROM lml_cache.library_release_override WHERE source = 'alex-l-2026'` + flip `false`. See WXYC/library-metadata-lookup#850.
- `LML_LOCATION_UNION_ENABLED` -- **Server-side kill switch** for the comprehensive multi-location union (LML#1022), folded transparently into `results` per the location-union-transparent-results plan (supersedes the original per-request `include_locations` design). `POST /api/v1/lookup` folds every other WXYC shelf location that carries the same track directly into `results` as ordinary `LookupResultItem`s -- no separate response field, no request opt-in -- when this flag is `true` (the default), a song is present, and the caller is not low-priority (`not is_discogs_low_priority()`, checked at the task-creation site -- BS enrichment, the CDC firehose, and backfills are excluded there via `X-Caller-Class`, not this flag). When on, the orchestrator (`lookup/orchestrator.py`) launches `lookup.location_union.resolve_track_shelf_locations` as a concurrent `asyncio` task alongside the whole spine (not just step 3) as soon as `parsed` is built -- a single indexed btree probe against `lml_cache.compilation_track_location` (the LML#1019 recall index) on the normalized `(track_artist, track_title)` key, no live Discogs call. After `_step_external_cache_fallback` (step 7) builds the response, the ranked candidates (credit-tier `primary > featured > extra` -> title-ratio -> `library_id`) are narrowed to "every OTHER location" (`build_location_result_items`), excluding whichever library ids are already present in `results` -- so the union fires even when the artist's own release already matched (Case A), not only when the pipeline came up empty (Case B) -- and converted into `LookupResultItem`s tagged `matched_via` (`source: discogs_release`). Every degraded/shed early return carries the same task through a bounded (~250ms) await, so a stalled probe never blocks an already-degraded response. Default `true`: the union is active on merge for every interactive song-bearing lookup. LML#1026 widened this flag's blast radius: on the union-active path the recall index is also **authoritative for comp-track resolution** -- the same task is threaded into `TRACK_ON_COMPILATION`, whose live-Discogs comp-discovery pass (Wave A/B + per-release validates) does not fire when the index answers (an index hit -- at least one renderable location -- means the fold supplies the locations, leading the response as the Case-B primary; an authoritative miss is final for comps, per the #271-locked "removed, not augmented" decision, while the keyword last-resort, #319 album-title fallback, and #628 rowless carve still run). A **degraded probe** (discogs-cache PG failure or the 500ms probe timeout) restores the full legacy live pass instead -- "union unavailable" never reads as "index says no" -- and increments the `location_union_index_degraded` cache-stats counter, the alertable signal for that state. Set `false` in Railway to disable the union globally in an incident without a client deploy -- no location rows are appended to `results` for any caller AND the legacy live comp-discovery pass is fully restored, making the flag a complete rollback lever for both LML#1022 and LML#1026. See WXYC/library-metadata-lookup#1022 and #1026 (and #1019 for the recall index, #271 for the parent epic).
- `LML_PERSIST_STREAMING_URLS` -- **Master kill switch** for the persistent streaming-URL cache post-process in `/api/v1/lookup` (LML#573, generalizing the LML#571 Apple-only flag). When `true` (default), `/api/v1/lookup` post-processes every item whose per-service URL came out null. **Since LML#706 the response path is cache-read-only**: it reads `lml_cache.album_streaming_url_cache` per *enabled* service using the **request's** `(artist, album)` (independent of the item's library row), fills the URL synchronously on a hit, does nothing on a known-recent miss (the cache already holds a fresh "not found"), and on a genuine miss (absent/stale row) schedules a bounded background warm that runs the live probe → cache UPSERT → mint **off the response path** (so streaming URLs are eventually consistent — the *next* lookup of a cold album is warm; artwork is unaffected). The high-volume `/api/v1/lookup/bulk` path does cache read-fill **only** — it suppresses the background warm (like its `bandcamp=None` / `allow_release_resolution_fallback=false` opt-outs) so a 35k-album drain can't spawn a decoupled warm tail that starves the live `/lookup` path; the offline warmer (#548) is the tier for bulk cache fill. When `false`, the entire post-process short-circuits regardless of the per-service flags — one-flip disable of Apple + Spotify persistence without a re-deploy (and the only way to fully disable the background warm). Known misses are recorded with a 7-day TTL; live resolutions mint the parsed ID into `entity.release_identity`. The schema is bootstrapped at startup via `set_up_streaming_url_cache_schema` in `main.py` lifespan (`CREATE SCHEMA IF NOT EXISTS lml_cache` + `CREATE TABLE`); if the discogs-cache PG is unreachable, the cache layer degrades to a no-op (the cache read returns null and the deferred warm is the only probe).
- `LML_PERSIST_STREAMING_URL_APPLE_MUSIC` / `LML_PERSIST_STREAMING_URL_SPOTIFY` -- **Per-service flags** for the streaming-URL cache post-process. **AND-gate: a service is persisted only when BOTH `LML_PERSIST_STREAMING_URLS` (master) AND its per-service flag are `true`.** The master defaults `true` and the per-service flags default `false`, so the feature is **off until Railway sets a per-service flag** — flipping the master alone enables nothing. Set both to `true` in Railway (staging + prod) to enable Apple + Spotify persistence. Rollback per service: flip its flag `false` (no re-deploy). There is **no deprecated alias** for the old `LML_PERSIST_APPLE_MUSIC_URL` — ops renames the Railway env var (`LML_PERSIST_APPLE_MUSIC_URL` → `LML_PERSIST_STREAMING_URL_APPLE_MUSIC`) before this deploys; if the rename is forgotten, Apple persistence silently stays off until corrected. See WXYC/library-metadata-lookup#573 (and #570/#571 for the originating Apple-only shape).
- `LML_STREAMING_ERROR_TTL_MINUTES` -- Minutes a `lml_cache.album_streaming_url_cache` **error row** (`is_error=true`) stays authoritative before the next `/lookup` re-probes; default **5**. LML#1121: a transport failure (Bandcamp 5xx/Cloudflare block/connect timeout, or any other client exception) during `entity.streaming_url_cache.resolve_streaming_url_with_cache`'s default (non-`fail_fast`) mode is a "couldn't ask", not a confirmed absence, so LML#1115 stopped it from freezing as the 7-day genuine-miss sentinel (`miss_ttl`). But writing NOTHING on that path (the #1115-#1121 interim posture) also removed the only backpressure on the default warm path: with no cache row, every subsequent `/lookup` for the same `(service, artist, album)` re-enqueues a fresh background warm for as long as the outage lasts, since the warm task's dedup key (`lookup/streaming_url_postprocess.py`'s `_streaming_warm_in_flight`) is discarded once the task completes -- it dedups *concurrent* warms only, not repeat ones across the outage. Unbounded background-task growth on one service starves the Apple/Spotify legs on the shared process-global warm semaphore (compounding LML#1094's warm-slot contention), while upstream RPS stays capped by the client's own rate limiter regardless. The fix: still write a row on a default-mode exception, but marked `is_error=true` so it ages on this much-shorter TTL instead of `miss_ttl` -- self-healing fast once the outage clears while still absorbing repeat `/lookup` traffic for its duration. The read gate (`entity/streaming_url_cache.py`'s `_SELECT_SQL`) is gated on `is_error` so the two miss flavors age on fully independent clocks (a genuine miss past `LML_STREAMING_ERROR_TTL_MINUTES` but still inside the 7-day `miss_ttl` stays a fresh known miss, and vice versa); a later genuine resolve or genuine miss on the same key always clears a stale `is_error=true` via the UPSERT. LML#1115 closed the matching read-SIDE gap this TTL knob's write-side fix left open: writing `is_error=true` is only half the story if nothing downstream of the SELECT can tell it apart from a genuine miss, so `peek_cached_streaming_url` now surfaces the row's `is_error` bit as a third return value and `resolve_streaming_url_with_cache` reports a fresh error row as the distinct `cache_error_recent` source (not `cache_miss_recent`); the `/api/v1/lookup` post-process (`lookup/streaming_url_postprocess.py`) maps a fresh error row to `StreamingResolutionStatus.unresolved` (a couldn't-check) rather than the confirmed-negative `absent` a genuine known miss reports, and — unlike a genuine known miss, which deliberately does NOT warm — schedules the same bounded, deduplicated background warm a genuine absent/stale miss would, since re-asking after a transient outage (rather than waiting out the short TTL) is the whole point of distinguishing the two; the depth bound (`LML_STREAMING_WARM_QUEUE_DEPTH_MULTIPLIER`, below) still governs it via the same enqueue path. Resolved **at call time** (not cached) via the shared `core.search.resolve_positive_int_env` helper, so **unparseable/zero/negative values fall back to the default with a WARN** and a live override takes effect on the very next resolution -- no redeploy (the Bandcamp hot-path-regression lesson: this class of knob needs an incident-time lever). Service-agnostic by construction (the cache serves Apple/Spotify/Bandcamp alike); Apple and Spotify currently collapse a couldn't-ask outcome to a plain `None` upstream of this resolver, so in practice only Bandcamp sets `is_error` today -- extending the other clients to raise instead of swallowing is a separate, not-yet-filed follow-up. - `LML_STREAMING_WARM_CONCURRENCY` -- Process-wide cap on **concurrent background streaming-URL warm probes** scheduled by the `/api/v1/lookup` post-process on a cache miss (LML#706); default 4. Deliberately separate from the bio warm's hardcoded `_WARM_CACHE_CONCURRENCY` (different upstreams + rate limits) and, unlike it, env-tunable — this path was introduced to fix the cold-tail incident, so a no-redeploy throttle/kill from Railway is a deliberate lever (the Bandcamp hot-path-regression lesson). Read once at first-warm via the shared `resolve_positive_int_env` helper, so **unparseable/zero/negative values fall back to the default with a WARN**: the effective floor is `1` (serializes warms to one probe at a time), not `0`. To disable the warm path entirely, flip the `LML_PERSIST_STREAMING_URLS` master flag (or the relevant per-service flag) — `LML_STREAMING_WARM_CONCURRENCY` only throttles, it cannot reach zero. Set low (e.g. `1`) to relieve pool/upstream pressure during an incident without losing eventual cache fill.
- `LML_STREAMING_WARM_QUEUE_DEPTH_MULTIPLIER` -- (LML#1108) Multiplier on `LML_STREAMING_WARM_CONCURRENCY` giving the **pending-plus-running warm depth bound** (`lookup/streaming_warm_admission.py`): `_enqueue_streaming_warm` SHEDS (does not queue) a genuine cache-miss warm once `len(_streaming_warm_in_flight) >= concurrency * this multiplier`. Default **16**. The semaphore alone bounds *concurrency*, not how many warms may be *pending* behind it — LIBRARY-METADATA-LOOKUP-1B saw a 232-deep backlog accumulate under a sustained Spotify 429 storm. The first cut of this bound (multiplier 4, not env-tunable) proved too tight against prod's real shape: at the prod `LML_STREAMING_WARM_CONCURRENCY=1` pin, a bound of 4 sheds under two ordinary concurrent cold `/lookup` calls (each can enqueue up to 3 keys — Apple + Spotify + Bandcamp), not just a storm. 16 gives headroom for roughly 5 concurrent 3-key cold lookups while remaining a >14x reduction from the incident peak. WXYC/library-metadata-lookup#1094 forbids raising `LML_STREAMING_WARM_CONCURRENCY` itself as a fix (it protects the single-worker event loop, #706), which makes this multiplier the only no-redeploy lever left for the depth bound. Read fresh on **every** enqueue call (not cached at semaphore-build time like the concurrency itself) via `resolve_positive_int_env`, so **unparseable/zero/negative values fall back to the default with a WARN** and a live override takes effect immediately. A shed reports the same `unresolved` `StreamingResolutionStatus` a healthy enqueue would (no `/lookup` response-shape change) but projects the `cache_miss_shed` Sentry outcome and increments the `streaming_warm_depth_shed` cache-stats counter (seeded to 0 in `lookup/router.py`'s `_LML_CACHE_STATS_EXTRA_KEYS`, so the shed rate is an alertable baseline series on the #683 surface). LML#1121 FIX 7: a shed triggered by a fresh error row projects `cache_miss_shed` *alongside* `cache_error_recent`, not instead of it -- an earlier posture projected only `cache_error_recent` for every error-row sub-case (enqueue/suppress/shed alike), which meant this depth-shed signal went silent for the dominant service during exactly the outage when shedding peaks.
- `LML_LOOKUP_MAX_CONCURRENT` -- Process-wide cap on **concurrent single `/api/v1/lookup` requests** (LML#706 PR3); default `min(8, LML_DISCOGS_POOL_MAX_SIZE)` = **5** at stock pool sizing. The ceiling is 8, but the effective default is **clamped to the discogs-cache pool** because every `/lookup` borrows that pool for its cache reads, trigram match, and identity mint (WXYC#395): a cap wider than the pool doesn't add throughput, it just relocates the queue from the (measured, bounded) semaphore onto `pool.acquire()`, where the wait attaches to whatever PG span is open — the LML#706 reopen mechanism, a 1.4 ms `entity.identity` SELECT measured at 5 s. Raising `LML_DISCOGS_POOL_MAX_SIZE` lifts the default back up to the ceiling; an explicit override *above* the pool is still honoured (the no-redeploy lever) but logs a **WARN guard** so the mismatch can't ship silently. Profiling for the reopen ruled out `library/db.py` as the loop-blocker (its fallback paths are 5–9 ms, off-loop, <2 ms loop lag even at ×8), which is what redirected the fix here rather than to on-loop fuzzy scoring. The #706 congestion collapse compounded because single `/lookup` had no in-flight bound: cold requests piled up (Little's law), each holding the one event loop through seconds of external I/O and contending for the 5-connection asyncpg pool, inflating even trivial PG spans to tens of seconds. Excess requests **queue** on a process-global semaphore around `perform_lookup` — no 429/503 shedding; callers see latency, never a new error mode. A caller that disconnects **while still queued** is reaped (LML#715): the permit acquire races the `watch_disconnect` sentinel (the same one `/lookup/bulk` and identity bulk-resolve use), so a departed client's slot frees promptly and **no lookup runs on its behalf** — the request short-circuits 499 with a filterable `lml.client_aborted: true` tag. This matters under the #706 cold-storm shape, where callers time out at their ~5–10 s budget and retry: without reaping, each abandoned attempt keeps its FIFO slot, later burns a full permit on a cold lookup nobody reads, and retries stack zombie work into the cap. The race guards the **queued phase only** — a request that already holds a permit runs to completion (a mid-lookup disconnect is not reaped; that phase already holds its pool + cap resources). A request that arrives to a saturated cap (the `locked()` pre-check is exact on Python ≥3.12 — it includes waiters) gets: a filterable Sentry **tag** `lml.lookup.inflight_capped: true` (a tag, not `set_data` — the LML#683 lesson: `set_data` alone is unqueryable in the spans dataset) plus a `lml.lookup.inflight_wait_ms` **measurement** (the quantitative series for tuning the cap), and its measured queue wait is **deducted from `X-Caller-Budget-Ms`** (floored at 1 ms — a non-positive value would fall back to the env default and hand the most-delayed caller the largest budget) so the A8/LML#345 "return slightly before the caller times out" contract holds under saturation. Deliberately separate from `LML_BULK_MAX_CONCURRENT` (which bounds items *inside* one `/lookup/bulk` batch via a per-request semaphore; this knob bounds single-`/lookup` requests *across* the process). **Scope note:** the bulk-family consumers (`/lookup/bulk`, identity bulk-resolve, cache refresh) are bounded by their own cross-request budget, `LML_BULK_GLOBAL_MAX_CONCURRENT` (LML#716, below) — **peak discogs-pool contention when both gates saturate is the SUM of the two caps**, so size `LML_DISCOGS_POOL_MAX_SIZE` against that sum, not either cap alone. `/streaming-check` sits under neither cap (it borrows no pool connection); its loop-time residual is tracked in LML#753. Read once at first request via the shared `resolve_positive_int_env` helper, so **unparseable/zero/negative values fall back to the default with a WARN** (a `0` cap would deadlock every request); the effective floor is `1` (fully serialized lookups). Set low from Railway to relieve pool/upstream pressure during an incident; raise only with evidence the loop + pool absorb the extra in-flight cold work.
- `LML_STREAMING_CHECK_MAX_CONCURRENT` -- Process-wide cap on **concurrent `/api/v1/streaming-check` requests** (LML#753); default **8**, a literal (not pool-derived — see below). Each request fans out four external streaming-service calls in one gather (`check_streaming_availability`), so N concurrent requests hold 4xN in-flight external HTTP calls on the shared event loop with no cross-request bound — the only existing throttles are *inside* the clients (per-client rate limits, the LML#449 Apple Music semaphore), which bound upstream call *rate*, not how many requests are simultaneously in flight. Mirrors the `/lookup` cap's shape (LML#706 PR3, `lookup/router.py`): a process-global `asyncio.Semaphore`, built lazily on first request so the env is read at request time (the no-redeploy Railway lever) and reset between test event loops (the suite-wide autouse fixture in `tests/conftest.py`). Excess requests **queue** — no 429/503 shedding; callers (tubafrenzy / Backend-Service) see latency, never a new error mode. **Deliberately NOT derived from `LML_DISCOGS_POOL_MAX_SIZE`** (unlike `LML_LOOKUP_MAX_CONCURRENT` / `LML_BULK_GLOBAL_MAX_CONCURRENT`, above): this endpoint borrows no asyncpg pool connection — no `pool.acquire`, no `lml_cache` writes, no identity mints anywhere under `streaming/` (persistence is explicitly the caller's job, the LML#376 "treat `None` as do-not-persist" verdict contract) — so it is deliberately excluded from the LML#716 bulk-family pool-derived budget; folding it in would queue flowsheet adds behind pool-bound bulk-drain work they don't share. One budget per contended resource: this cap protects loop time + sockets, not the discogs-cache pool. The default 8 is picked from observed organic peaks — flowsheet adds are single-digit concurrent — with headroom above that so a caller storm (the 2026-07-06 flowsheet-backfill-flood shape) can't occupy the loop unbounded. A request that arrives to a saturated cap gets a filterable Sentry **tag** `lml.streaming_check.inflight_capped: true` plus a `lml.streaming_check.inflight_wait_ms` **measurement** (same two-channel shape as the #706 cap — the LML#683 unqueryable-`set_data` lesson). Read once at first request via the shared `resolve_positive_int_env` helper, so **unparseable/zero/negative values fall back to the default with a WARN** (a `0` cap would deadlock every request). **Per-worker caveat:** if `UVICORN_WORKERS > 1` ever ships (LML#747), this becomes a per-worker bound — same caveat `LML_LOOKUP_MAX_CONCURRENT` and `LML_BULK_GLOBAL_MAX_CONCURRENT` carry. There is no observed streaming-check incident motivating this today; it exists so the residual is tracked structurally rather than living only in a code comment.
- `LML_STREAMING_CHECK_TIMEOUT_MS` / `LML_STREAMING_CHECK_BANDCAMP_TIMEOUT_MS` -- Per-service wall-clock ceiling (ms) on a **single `/api/v1/streaming-check` leg** (LML#1081); defaults **10000** (non-Bandcamp) and **15000** (Bandcamp). `check_streaming_availability` fans out each service's `find_album_match` concurrently and, before this, awaited each with no timeout — so one slow leg (Bandcamp especially, which post-#1080 chains up to three 1-req/s phases through a 429 exponential backoff with no internal `budget_deadline`, an untimed worst case of ~105s) could stall the whole request while holding an `LML_STREAMING_CHECK_MAX_CONCURRENT` semaphore slot the entire time. Each leg is now wrapped in `asyncio.wait_for` at task creation (`streaming/orchestrator.py`), which cancels the underlying coroutine on timeout — releasing its rate-limiter/semaphore promptly — and degrades that service into `errored_sources` (the LML#376 "None = do not persist / retry later" verdict, never a whole-request failure). Bandcamp gets the looser ceiling because its normal fallback path legitimately makes a handful of 1-req/s fetches; the others are single httpx calls. Both are resolved **at request time** via the shared `lookup.timeouts.probe_timeout_s_from_env` helper (the same integer-ms→seconds knob the Apple probe's `LML_APPLE_MUSIC_LOOKUP_TIMEOUT_MS` uses), so **unparseable/zero/negative values fall back to the default with a WARN** and the ceilings are tunable from Railway with no redeploy — `LML_STREAMING_CHECK_BANDCAMP_TIMEOUT_MS` is the knob to widen first under a real 429 storm. A caller may also pass a per-service `timeouts=` override to `check_streaming_availability` (used by tests and any future settings-threaded tuning), which wins over both the env knob and the static default. This is a reliability bound on `/streaming-check` only; it is not the iOS Bandcamp-search-fallback symptom fix (that path is `/lookup/bulk`, tracked separately).
- `LML_DISCOGS_POOL_MAX_SIZE` -- `max_size` of the **discogs-cache asyncpg pool** (`_build_discogs_pool`); default 5. This is the hot-path pool: the trigram release match, the `lml_cache.album_streaming_url_cache` read, and every identity mint borrow it (the LML#395 shared seam — the Discogs cache service *and* the entity store run through one pool). In the LML#706 cold-tail incident, `LML_LOOKUP_MAX_CONCURRENT` (default 8) in-flight `/lookup` requests contended for these 5 connections on one event loop, so even the trivial `pg_advisory_unlock_all()` connection-reset span inflated to ~5 s. **Raising this to at least the in-flight cap (8) is the most direct relief** — it stops admitted requests from queueing on connections. Read at pool-build via the shared `resolve_positive_int_env` helper (unparseable/zero/negative fall back to the default with a WARN). The pool is built once at startup, so a change takes effect on the next restart, not live. Connection budget: the process opens up to `LML_DISCOGS_POOL_MAX_SIZE` connections against discogs-cache PG — keep it under that server's `max_connections` (the LML#241/#357 FD-exhaustion lesson). **Kept in sync:** the `/api/v1/identity/bulk-resolve-libraries` semaphore *default* (`identity/router._bulk_resolve_default_concurrency`) reads this same knob so it stays sized to the pool's `max_size` — a semaphore wider than the pool would queue coroutines on `pool.acquire()`. Note that setting `LML_BULK_MAX_CONCURRENT` overrides that default outright, so raising it above `LML_DISCOGS_POOL_MAX_SIZE` re-introduces exactly that queueing; keep the two in step if you tune either. The `LML_BULK_GLOBAL_MAX_CONCURRENT` budget (LML#716, below) *also* defaults to this knob, so both pool-tracking defaults move together; remember the **sum invariant** — worst-case pool demand is `LML_LOOKUP_MAX_CONCURRENT` + `LML_BULK_GLOBAL_MAX_CONCURRENT`, so a pool sized to only one of them still queues on `pool.acquire()` when both saturate (acceptable queueing, not starvation, but visible in PG span times).
- `LML_BULK_GLOBAL_MAX_CONCURRENT` -- Process-wide budget on **concurrent in-flight items across ALL bulk-family requests** (LML#716); default = `discogs_pool_max_size()` (i.e. it tracks `LML_DISCOGS_POOL_MAX_SIZE` rather than adding a third hand-synced literal). The per-request knob (`LML_BULK_MAX_CONCURRENT`) bounds items *inside one* request, so N concurrent batches admit N× that many items against the one event loop + discogs-cache pool — the residual the #714 cap's review flagged. This budget is one process-global semaphore consulted inside every bulk-family per-item runner (`/api/v1/lookup/bulk`, `/api/v1/identity/bulk-resolve-libraries`, `/api/v1/cache/refresh-for-identities`; always per-request gate OUTER, global permit INNER), so concurrent requests share one budget instead of multiplying. Excess items **queue** FIFO — no 429/503, no new error mode, and a small interactive batch interleaves with (rather than parks behind) a long operator drain. An item that arrives to a saturated budget gets a filterable Sentry **tag** `lml.bulk.global_capped: true` plus a `lml.bulk.global_wait_ms` **measurement** (running max across the request's items — the worst wait the request saw), same two-channel shape as the #714 cap (the LML#683 unqueryable-`set_data` lesson). Deliberately does NOT cover single `/lookup` (its own cap above) or `/streaming-check` (borrows no pool connection — pool-free loop residual tracked in LML#753; principle: one budget per contended resource). Read once at first bulk item via `resolve_positive_int_env` (unparseable/zero/negative → WARN + default; a `0` would deadlock every bulk item forever). **Per-worker caveat:** if `UVICORN_WORKERS > 1` ever ships (LML#747), this silently becomes a per-worker bound — same caveat as `LML_LOOKUP_MAX_CONCURRENT`; re-derive the sizing math first. Lower from Railway to squeeze bulk drains during an incident without touching interactive traffic; raise only with pool headroom for the **sum** of this + `LML_LOOKUP_MAX_CONCURRENT`. **Reserved-headroom rationale — do NOT tune this back up to the `LML_DISCOGS_POOL_MAX_SIZE` default (LML#924).** The two entry-level admission gates admit up to `LML_LOOKUP_MAX_CONCURRENT` + `LML_BULK_GLOBAL_MAX_CONCURRENT` requests, but they all funnel into the shared **5-permit Discogs concurrency semaphore** (`discogs/ratelimit.py`) — the measured bottleneck (prod trailing-14d `lml.discogs.semaphore` p95 ≈ **117 s**, versus ≈ **32 ms** on the 50/min Discogs *quota*, so concurrency, not quota, is the constraint). Its default tracks `LML_DISCOGS_POOL_MAX_SIZE` (which prod sets to **8**; 5 at stock sizing) — a different resource from the 5-permit semaphore — and at that default the bulk lane admits enough in-flight items to occupy all **5** Discogs permits and head-of-line-block interactive `/lookup` (measured p99 **22.7 s**, past the ~8 s Backend/canary budget — the #924 incident shape that trips the `proxy-library-search` canary). Prod therefore pins this to **2**, so bulk holds at most 2 permits, reserving ≥3 of the 5 for interactive; keep it **below** the interactive lane. Raising it back toward the pool-tracking default lets bulk reclaim those permits and reintroduces the starvation — the fix is to *reserve* concurrency, not add more (do **not** raise `DISCOGS_MAX_CONCURRENT` to compensate; that just relocates the collision onto Discogs' 60/min quota and the discogs-cache PG pool). This was the interim, env-only mitigation for the interactive `/lookup` lane; the durable, code-level class-aware reservation *at* the Discogs semaphore itself has since shipped as `LML_DISCOGS_BULK_MAX_CONCURRENT` (LML#927, below) and supersedes it -- this cap is kept in place as cheap insurance (see that entry's supersession note) rather than reverted outright. `/api/v1/library/search` starvation (event-loop contention, not this gate) remains the structural work in BS#1819. **`X-Caller-Class` routing (LML#928):** an optional caller-declared `X-Caller-Class` header (integer 1-5, forwarded by Backend-Service per BS#1843) generalizes this budget's reach beyond its implicit bulk-only default: class 5 (batch/cron/backfill) additionally routes a single `POST /api/v1/lookup` request onto this SAME budget (`maybe_acquire_bulk_global_permit` in `core/bulk_concurrency.py`, wrapping `perform_lookup`), so a batch/cron job that calls the single-item endpoint instead of `/lookup/bulk` still shares the low-priority lane rather than competing for `LML_LOOKUP_MAX_CONCURRENT` headroom. Classes 1-4, an absent header, and any unparseable/out-of-range value (`resolve_caller_class`) are all a no-op — today's per-endpoint lane placement is unchanged, and `/lookup/bulk` items remain unconditionally on this budget regardless of what class is sent (down-rank only: no class value can escalate a bulk caller OUT of the low-priority lane either). The header is honored only on the authenticated Backend-Service-to-LML channel (the `lookup` router's `require_lml_key` dependency gates every request first) and is never trusted to grant a protected/interactive lane beyond a caller's existing entitlement. This is the durable, self-documenting generalization of the [LML#924](https://github.com/WXYC/library-metadata-lookup/issues/924) interim (`LML_BULK_GLOBAL_MAX_CONCURRENT=2` in prod today, unchanged by this ticket) and operates strictly at this entry-level admission gate — it does not reach into the shared 5-permit Discogs concurrency semaphore itself (`discogs/ratelimit.py`); reserving class-aware headroom AT that deeper gate is the separate [LML#927](https://github.com/WXYC/library-metadata-lookup/issues/927) slice, below, which has since shipped. A `pytest` in `tests/unit/test_lookup_router.py::TestCallerClassLowPriorityLane` and `tests/unit/test_bulk_lookup_endpoint.py::TestCallerClassAntiUpRankInvariant` pin the class -> lane routing invariant across both endpoints as a CI regression guard.
- `LML_DISCOGS_BULK_MAX_CONCURRENT` -- The durable, code-level replacement for the `LML_BULK_GLOBAL_MAX_CONCURRENT` interim above (LML#927, superseding LML#924). Size of a NEW per-event-loop sub-semaphore in `discogs/ratelimit.py` (`get_bulk_discogs_semaphore`), default **2**, that low-priority Discogs calls must hold BEFORE (outer) the shared `DISCOGS_MAX_CONCURRENT`-permit semaphore (inner) -- reserving `DISCOGS_MAX_CONCURRENT - LML_DISCOGS_BULK_MAX_CONCURRENT` permits (>= 3 at stock sizing) for interactive `/lookup`, permit-for-permit, rather than relying on the entry-level admission caps above to happen to leave headroom. Read via the shared `resolve_positive_int_env` helper (unparseable/zero/negative -> WARN + fall back to 2; a `0` would deadlock every low-priority Discogs call forever). **Per-process (per-event-loop), same as every sibling primitive:** correct at `UVICORN_WORKERS=1` (today) and >1 (LML#747) alike -- each worker reserves independently against its own shared semaphore, so no re-derivation is needed the way the rate dimension (LML#841's shared bucket + `floor(50/N)` split) requires. - `DISCOGS_BREAKER_FAILURE_THRESHOLD` -- Consecutive **failed requests** (not attempts) that trip the LML#755 **saturation circuit-breaker** OPEN; default 4 (`ge=1`). The existing outbound limiter (`DISCOGS_RATE_LIMIT` 50/min + a 5-permit semaphore) bounds egress *rate* but, under a sustained flood (the 2026-07-10 `flowsheet-metadata-backfill` incident), converts excess demand into unbounded per-request *latency*: every lookup fans out ~5 live Discogs calls, they queue on the 50/min `rate_limiter.acquire()`, and 429 backoff stacks to ~62s/call — so a lookup's wall time runs past Backend-Service's 35s client timeout → timeouts → worker saturation → 502s. The breaker closes that loop: when OPEN, `discogs/service.py:_request_with_retry` **sheds before** `rate_limiter.acquire()` (no queuing, no network, no backoff) by raising `DiscogsBreakerOpenError` — a shed is "couldn't ask", which callers treat as *unknown* (never a confirmed-empty verdict that would poison a durable negative cache; see the architecture doc's breaker section). The lookup **fast-fails to cache-only** — library + already-cached-Discogs results, live probe shed. Cache hits are unaffected (they short-circuit in `discogs/fallthrough.py` before the live probe). **Counting unit:** the breaker counts failed *requests*, not attempts — each `_request_with_retry` records at most one terminal outcome (429-exhaustion → failure carrying the last-seen remaining; 2xx → success; 5xx → neutral, neither resets the run nor closes a half-open trial). A single healthy response resets the run, so only a *sustained* window — 4 lookups in a row all exhausting into 429s — opens it. The proactive floor (`DISCOGS_BREAKER_REMAINING_FLOOR`) rides both the 429 and success paths, so an at/below-floor bucket opens even before the reactive threshold. Breaker state lives in a **per-event-loop** dict alongside the limiter/semaphore (`discogs/ratelimit.py:get_discogs_breaker`), so it is process-global on the single-worker deployment today (`entrypoint.sh` runs bare `uvicorn main:app`). **Per-worker caveat:** if `UVICORN_WORKERS > 1` ever ships (LML#747) the breaker becomes per-worker — re-size `DISCOGS_BREAKER_REMAINING_FLOOR` / this threshold so aggregate outbound stays under the shared 60/min Discogs ceiling first (same caveat as `LML_LOOKUP_MAX_CONCURRENT` / `LML_BULK_GLOBAL_MAX_CONCURRENT`). **Telemetry:** every shed increments `discogs_breaker_open_shed` on the per-request `cache_stats` dict — the same #683 `cache.*` counter surface (projected to PostHog as `cache.discogs_breaker_open_shed` and onto the Sentry transaction as `lml.cache.discogs_breaker_open_shed`, seeded to 0 in `_LML_CACHE_STATS_EXTRA_KEYS`) that the row-less flag degradation alerts use, so breaker-open time is alertable. The human-readable OPEN/CLOSED transitions are logged once each (per-shed logging is `debug`, so a multi-hour flood doesn't flood the log). **Validation:** these are pydantic-settings `Field`s with `ge=` bounds — an out-of-range value raises a validation error at startup (it does **not** silently fall back to the default). Read once at breaker-build; a change takes effect on the next restart. See WXYC/library-metadata-lookup#755.

- `DISCOGS_BREAKER_COOLDOWN_SECONDS` -- How long the LML#755 breaker stays OPEN (shedding live probes to cache-only) before admitting a single **half-open** trial request; default 20.0 (`ge=0.0`). Roughly a third of the Discogs 60s rate-limit window, so the bucket has partially refilled before the re-probe. A genuine 2xx trial (`X-Discogs-Ratelimit-Remaining` above the floor) CLOSES the breaker; a 429 (or a still-exhausted remaining) re-OPENS it for another cool-down; a trial that dies without any terminal outcome — request-layer error, cancellation — also re-OPENS it (LML#787: a lost trial is *inconclusive*, never latches HALF_OPEN); a 5xx trial is neutral (neither closes nor re-opens — the slot stays occupied until the watchdog below fires; prompt re-arm is LML#791). The trial is guarded by a monotonic epoch so a stale response from the CLOSED era can't decide it, and concurrent callers during the cool-down are shed — only the one trial is admitted. **This knob also scales the LML#787 stuck-trial watchdog**: HALF_OPEN persisting past `max(cooldown × DISCOGS_BREAKER_TRIAL_WATCHDOG_MULTIPLIER, 60s)` is presumed stranded and re-OPENs, so lowering the cool-down also tightens the watchdog window. An out-of-range value raises a startup validation error (no silent fallback). See WXYC/library-metadata-lookup#755, WXYC/library-metadata-lookup#787.
- `DISCOGS_BREAKER_TRIAL_WATCHDOG_MULTIPLIER` -- LML#787 HALF_OPEN watchdog scale: a half-open trial still unresolved after `max(DISCOGS_BREAKER_COOLDOWN_SECONDS × this, 60s)` is presumed lost (or its slot stranded) and the breaker re-OPENs — fresh cool-down, fresh trial — instead of latching HALF_OPEN forever (the 2026-07-13 incident: ~8h shedding 100% of live Discogs calls until a restart). The watchdog runs inside `allow_request`, so the bound holds under traffic (an idle service can sit HALF_OPEN longer, harmlessly). An out-of-range value raises a startup validation error (no silent fallback). See WXYC/library-metadata-lookup#787.

Telemetry: a skip fire increments the `skipped_prefetch` cache-stats counter (projects to PostHog `cache.skipped_prefetch` / Sentry `lml.cache.skipped_prefetch`) and sets Sentry `lml.enrich.synthesis_path_skipped_prefetch`; the recovery cohort (artist verifies, title doesn't) sets `lml.enrich.synthesis_path_recovered_artist` regardless of this flag, so the cohort split stays visible during rollback. See WXYC/library-metadata-lookup#507.
- `LML_SEARCH_MAX_API_CALLS` -- Per-invocation cap on Discogs API calls dispatched from one `_chunked_gather` invocation (one strategy leg's validation tail); default 15. Sized above the warm-cache `extended=true` happy-path window (8-14 calls measured) so legitimately-busy lookups don't trip, while still bounding the zero-canonical failing tail flagged in LML#543 (15-24 calls / 16-17s wall time per failing leg). The gate is **baseline-relative**: each `_chunked_gather` captures the request's `stats["api_calls"]` at entry and checks `(current − baseline) >= cap` between chunks. Per-invocation (not request-wide) on purpose: a request-wide cap would (1) starve later items in `/api/v1/lookup/bulk` batches that share one cache_stats dict, and (2) silently disable the LML#319/#237 album-title fallback whose own `_chunked_gather` follows the main loop in `search_compilations_for_track`. In-flight calls inside the current chunk run to completion — the gate is between chunks, not mid-chunk, so the actual ceiling per invocation is `cap + chunk_size − 1` where `chunk_size = MAX_SEARCH_RESULTS = 5`. Read at request time via `os.getenv` (shared `resolve_positive_int_env` helper from `core/search`) so the value flips without a redeploy. Misconfigured values (negative, zero, unparseable) fall back to the default with a WARN. Telemetry: each cap-fire increments `search_api_call_cap_fired` on the per-request cache-stats dict (a counter — for batch-aggregate PostHog), AND bumps a separate per-task `ContextVar` counter (`core.search._cap_fire_count_var`) for runner-side control flow. `execute_search_pipeline` reads the per-task counter (NOT the shared cache_stats dict) so concurrent `/api/v1/lookup/bulk` items can't race-poison each other; after each strategy, when the strategy fired the cap AND the natural-completion gate (`state.results and not state.song_not_found`) didn't fire, the runner sets `state.timed_out=True` and short-circuits the cascade. The complementary gate means: a strategy that surfaced a confirmed song match keeps `timeout=False` (natural completion wins), and a strategy that surfaced an artist-fallback `Outcome.artist_fallback` keeps the timeout signal (so the cap actually bounds wall time in the `song_not_found` cascade). The cache_stats counter projects onto the Sentry transaction as `lml.cache.search_api_call_cap_fired` via the router's existing `_project_cache_stats_to_transaction`; filter on `lml.cache.search_api_call_cap_fired:>0` for the cap-fire slice.
- `LML_SEARCH_HARD_TIMEOUT_MS` -- Hard ceiling (ms) on `execute_search_pipeline` wall time; default 25000. Fires regardless of `state.results` to bound cascade-exhaustion tail latency (LML#370). Wrapped around every strategy via `asyncio.wait_for`, so a single slow Discogs cascade gets cancelled with its in-flight `gather()` probes — frees the Discogs semaphore on cap-fire. Unlike the soft budget, callers cannot raise this via header (safety floor, not a budget). To effectively disable, set well above the request timeout (e.g. `600000`). **Coverage (LML#865):** the cap is now **spine-level** — it bounds step 2 (`resolve_albums_for_track`'s Discogs pass) as well as step 3. Step 2 runs under the `lookup/spine_deadline.py` deadline (`run_within_spine_deadline`, which cancels the in-flight probe and frees the Discogs semaphore exactly like the step-3 per-strategy `wait_for`), and step 3's clock is re-based to the spine start (`pipeline_start_offset_ms`), so a step-2-heavy request can no longer run 60s+ without ever tripping the cap. Telemetry: `hard_cap_fired:true` projects onto the Sentry transaction; a step-2-originated trip additionally sets `hard_cap_step` (e.g. `album_lookup`) so it is distinguishable from a step-3 trip; response carries `LookupResponse.timeout: true`.
- `DISCOGS_SEARCH_STATEMENT_TIMEOUT_MS` -- Per-transaction `statement_timeout` (ms) applied via `SET LOCAL` on the two discogs-cache **trigram search arms** (`DiscogsCacheService.search_releases`, `search_releases_by_track` in `discogs/cache_service.py`); default 10000, pydantic `ge=1` (an out-of-range value raises a startup validation error — no silent fallback). This is a **server-side** query bound, distinct from the pipeline wall-clock budgets above: `uvicorn` does not propagate client disconnects into handler coroutines and an asyncpg query runs to completion once dispatched, so without it a long trigram scan holds a scarce discogs-cache pool slot (and, since LML#706 clamped the `/lookup` in-flight cap to the pool size, a `/lookup` cap slot) long past the point any caller is listening — the 2026-07-15/16 LIBRARY-METADATA-LOOKUP-29 tail (p95 5.1s / max 15.4s for 10+ hours after the ~15:00 UTC discogs-cache blip). Chosen 10s to sit **above** the largest legitimate caller budget (Backend-Service ~5s, visible as `lml.caller_budget_ms` on spans) so it catches only true runaways, not steady-state queries. A timed-out query surfaces as `asyncpg.QueryCanceledError`, which the search arms map into `CacheUnavailableError` — the fallthrough seam's cache-only degrade boundary (`_ARMING_EXCEPTIONS`), never a 500 (LML#755's "couldn't ask" principle) — freeing both slots at once. `SET LOCAL` reverts at transaction end, so it never touches the write-serving pool session (the discogs-cache pool also serves api_fetch cache writes, `entity.identity` write-backs, and bulk-drain write-backs). Read once at `DiscogsCacheService` construction; a change takes effect on the next restart. See WXYC/library-metadata-lookup#804 (post-deploy prod EXPLAIN/p95 tuning is the follow-up #806).
- `DISCOGS_SEARCH_WORK_MEM` -- Per-transaction `work_mem` applied via `SET LOCAL` on the same two trigram search arms, as a Postgres memory value (e.g. `128MB`); default 128MB. Default `work_mem` (4MB) makes the trigram bitmap heap scans go **lossy** and recheck-storm under degraded latency — the 2026-05-25 pg_trgm investigation measured this path at ~92s under default `work_mem` vs ~12.7s with a large `work_mem` (the same query is p95 151ms warm, so this is a degraded-mode amplifier, not steady-state cost). **Bounded on purpose:** per-connection `work_mem` allocations multiply by pool size on the shared 8GB Railway discogs-cache instance, so **NOT** 1GB — 128MB is a safe default to ship; empirical prod tuning + EXPLAIN/p95 verification is the separate follow-up #806. The value is interpolated into the `SET LOCAL` string (Postgres `SET` takes no bind params), so it is validated against Postgres' `<digits><unit>` grammar (anchored `^\d+(kB|MB|GB|TB)?\Z`) at **two** points: a pydantic field validator at Settings load, so a bad value (lowercase unit, embedded space, trailing newline, injected fragment) raises a startup validation error loudly at boot rather than a first-request 500 — symmetric with `DISCOGS_SEARCH_STATEMENT_TIMEOUT_MS`' `ge=1` — and again in `_build_search_bounds_sql` at interpolation time (defense in depth). `SET LOCAL` reverts at transaction end (same write-path safety as the timeout above). Read once at `DiscogsCacheService` construction. See WXYC/library-metadata-lookup#804.
- `LML_EMIT_SERVER_TIMING` -- When `true` (default), `/api/v1/lookup` and `/api/v1/lookup/bulk` attach a [`Server-Timing`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Server-Timing) response header serializing the per-stage timings `RequestTelemetry.track_step` **already** captures (the LML half of the cross-repo Server-Timing trace; enrichment-observability hardening epic WXYC/Backend-Service#881, Epic G). The grammar is `name;dur=<ms>` entries, comma-joined: on `/lookup`, one per tracked stage (`library_search`, `metadata_enrichment`, `track_validation`, … in insertion order), then a **derived `discogs` leg** = `cache_stats["pg_time_ms"] + cache_stats["api_time_ms"]` (so the header never disagrees with the `cache_stats` JSON), then exactly one **live `total`** from `get_total_duration_ms()`. `/lookup/bulk` emits a batch-level **`total` only** (per-item stages aren't meaningful in a single per-HTTP-request header). Motivation: a `lookup` CLI round-trip measured 8.99s while the caller could only see the Discogs `cache_stats` block (`pg 404ms / api 0ms`) — the ~8.5s actually spent in `metadata_enrichment` (Apple-probe timeouts under the BS#1631 backfill flood) was captured by telemetry but never reached the client, so the slowdown couldn't be attributed to a named stage. **Purely out-of-band instrumentation:** the header is set on an injected FastAPI `Response`, so there is **no `api.yaml` / `CacheStats` / `LookupResponse` change and no wxyc-shared regen** — the JSON body is byte-identical whether the header is present or not (this is the shared-package half of a chained cross-repo trace: LML emits → request-o-matic forwards + merges the header on `/request` and prints it in the `lookup` CLI). **Caveats:** (1) `metadata_enrichment` is elapsed **wall-clock** for a stage that runs concurrent probes, so `Σ steps + discogs ≠ total` (overlap + untimed glue between stages); the header measures where wall-time went, not a partition of it. (2) The header `total` is sampled at header-build time, a few ms **before** `send_to_posthog` runs, so it and the PostHog `total_duration_ms` are two independent measurements — close but not identical. (3) Exposing internal stage latencies on the (Slack-facing) request path is low-sensitivity (durations only, no data) and standard practice, but flip this `false` in Railway to withhold it without a redeploy. Observability must never break the request path: a settings-read or serialize failure logs at WARNING and the response ships **without** the header (never a 500). Requires `wxyc-fastapi>=1.1.0` (the release that added `RequestTelemetry.as_server_timing`). See the enrichment-observability epic WXYC/Backend-Service#881 (Epic G).
- `LML_EVENT_LOOP_LAG_GAUGE` -- When `true` (default), a background sampler task (started in `main.py` lifespan, cancelled on shutdown) measures **event-loop scheduling lag** — how much longer than a fixed `asyncio.sleep(0.5s)` the single uvicorn worker's loop actually takes to resume, i.e. how long a ready coroutine waits to be scheduled. It keeps an EWMA in a process global (`core/event_loop_lag.py`); the lookup router stamps the current value onto each request's `cache_stats` as `event_loop_lag_ms`, so it rides the existing `cache.*` / `lml.cache.*` projection to PostHog (`cache.event_loop_lag_ms` on `lookup_completed`) and Sentry (`lml.cache.event_loop_lag_ms` measurement) with **no new alerting plumbing**. This surfaces the `/lookup` **single-worker starvation tax** (`plans/lookup-latency-event-loop-starvation.md` §3) — the multi-second post-await response tail that `RequestTelemetry.track_step` and the `Server-Timing` header structurally **cannot** capture (both measure *inside* pipeline steps; the tax lands before the first, between, and after the last) — and is the before/after metric for Lever A′ (`LML_APPLE_MUSIC_RATE_PER_MIN`, #904) and Lever B (multi-worker, #747). The stamp is a per-request **sample** of the process-global gauge, not the request's own tail; aggregated avg/p95 across requests it tracks loop health over time. Near-zero cost (a plain sleep loop with a subtraction twice a second — it never blocks or does I/O, so it can't corrupt its own signal). The stamp is a no-op when the gauge is unsampled (sampler off, or the first ~0.5s of process life), leaving the `event_loop_lag_ms` key at its seeded `0`. Observability must never break the request path: a gauge-read failure logs at WARNING and the request proceeds without the stamp (never a 500). Default `true`. To disable, set `false` **and confirm a redeploy landed** — the flag is read at process start (the sampler is a `lifespan` task; the stamp reads `@lru_cache`d `Settings`), so a var flip takes effect only on the next boot, and a Railway var-set that comes back **SKIPPED** (see #904) leaves the running sampler untouched. See WXYC/library-metadata-lookup#907 and [`observability-rowless-flag.md`](observability-rowless-flag.md).
- `UVICORN_WORKERS` -- Number of uvicorn worker processes launched by `entrypoint.sh`; default 1. This is the multi-worker headroom lever for the LML#706 event-loop starvation tax, but set it above 1 only after the [horizontal-scaling runbook](deployment.md#horizontal-scaling-runbook-enabling-n2-replicas) prerequisites are satisfied: shared Discogs-rate budgeting (`DISCOGS_RATE_BUCKET_ENABLED=true` or divided local `DISCOGS_RATE_LIMIT`), per-process Discogs concurrency/breaker sizing, discogs-cache PG connection budget, and container memory. The shell entrypoint validates this before uvicorn starts: unset/blank means 1; non-integer, zero, or negative values emit a `WARN` to stderr and fall back to 1 instead of crash-looping before the service binds.

## Inbound Auth (`LML_API_KEY`)

`core/auth.py:require_lml_key` is a FastAPI dependency that validates `Authorization: Bearer <LML_API_KEY>` on every tubafrenzy / Backend-Service-facing endpoint. Wired in `main.py` via `app.include_router(..., dependencies=[Depends(require_lml_key)])` for the `lookup`, `library`, `discogs`, and `streaming` routers.

Three auth surfaces in this service, intentionally separate:

| Surface | Direction | Env var | Implementation |
|---|---|---|---|
| Inbound from tubafrenzy / Backend-Service | tubafrenzy → LML | `LML_API_KEY` | `core/auth.py:require_lml_key` (router-level dep) |
| `/admin/*` (library.db upload) | ETL → LML | `ADMIN_TOKEN` | `core/auth.py:require_admin_token` (per-route dep in `routers/admin.py`) |
| Outbound streaming-status webhook | LML → tubafrenzy | `ETL_NOTIFY_KEY` | `routers/admin.py:_send_streaming_webhook` (sends `Authorization: Bearer ...`) |

Untouched: `/health`, `/identity/resolve`, `/identity/bulk`. Identity routes are consumed by semantic-index too, so locking them down is a separate decision.

**Rollout:** `LML_REQUIRE_AUTH` defaults to `false` so the dep can ship before consumers send the header. Once tubafrenzy and Backend-Service are updated, flip the flag in Railway to enforce.
