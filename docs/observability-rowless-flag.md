# Row-less flag observability & alerts (`LML_RESOLVE_NONLIBRARY_RELEASE`)

Runbook for the automated degradation alerts on the `LML_RESOLVE_NONLIBRARY_RELEASE` row-less carry-through feature (LML#628), wired in [LML#683](https://github.com/WXYC/library-metadata-lookup/issues/683). The counters and flag tag these alerts consume are emitted by [LML#681](https://github.com/WXYC/library-metadata-lookup/issues/681) through the existing `cache_stats` seam — see the `LML_RESOLVE_NONLIBRARY_RELEASE` entry in [`env-vars.md`](env-vars.md) for the emit side. This doc is the **consume** side: what is watched, the thresholds and why, and what to do when one fires.

## Why this exists

The feature's worst failure mode is **silent by design**. The row-less resolve path swallows its Discogs probe errors (returns `[]`/`None`), so a Discogs outage shows up as *fewer* row-less surfaces, **not** an error spike in Sentry — LML#681 explicitly scoped silent-degradation alerting *out*. The only machine-readable signals are the LML#681 counters, and before LML#683 nothing watched them. The cold-path Discogs cost is also the exact sensitivity behind the 2026-05-13 regression ([LML#337](https://github.com/WXYC/library-metadata-lookup/issues/337)): a call-rate spike here can degrade `/lookup` latency for the whole live stack. These alerts make a Discogs call-rate spike, a positive-cache hit collapse, or a Postgres cache outage **page automatically** instead of being noticed late or never.

## Signals

All ride the per-request `cache_stats` dict (seeded in `_LML_CACHE_STATS_EXTRA_KEYS`, `lookup/router.py`). PostHog receives them as the `cache` property of the `lookup_completed` event (`cache.<key>`); Sentry receives them as transaction measurements (`lml.cache.<key>`, projected by `_project_cache_stats_to_transaction`, `traces_sample_rate=1.0`).

| Key | Meaning | Degradation it proves |
|-----|---------|-----------------------|
| `api_calls` | Discogs API calls made on the request | Call-rate spike → `/lookup` latency risk (the LML#337 cost guard; primary rollback trigger) |
| `release_resolution_cache_hit` / `_miss` | LML#632 positive-cache outcome (`get_cached_release_id`) | Miss climbing while hits stop = swallowed-error **Discogs outage** proxy |
| `release_resolution_cache_unavailable` | PG-exception branch of the positive cache | Sustained > 0 = **Postgres positive-cache outage** (direct signal) |
| `lml_resolve_nonlibrary_release` | Flag state, `0`/`1`, recorded once per context | Used to **scope every alert to flag-on traffic** |
| `nonlibrary_release_surfaced` | Flag-gated row-less `id=0` emissions | Context (feature actually surfacing results); not alerted |

## Baseline (the numbers the thresholds are set from)

Telemetry went live in prod 2026-06-27. Baseline pulled 2026-06-30 over the **3-day flag-on window** (`lml_resolve_nonlibrary_release=1`), `lookup_completed` only (bulk excluded — on `/lookup/bulk` the counters are batch totals across up to 100 items). The flag is fully enabled, so 100% of `lookup_completed` traffic is flag-on (7,560 requests).

**PostHog population (`lookup_completed`, flag-on, 3d):**

- `api_calls` per request: avg **0.75**, p50 0, p90 2, p95 3, p99 9, max 36. **73%** of requests make **zero** Discogs calls (library/cache hit). Trailing-6h average ranges **0.41–1.71** (1.71 was a cold-start morning).
- Positive cache: hits **163**, misses **228**, **unavailable 0 in every one of the 72 hours**. Hit fraction `hits/(hits+misses)` ≈ **0.42** overall; **0.31–0.61** across trailing-12h windows (warming upward).
- `nonlibrary_release_surfaced`: 291 (feature working).

**Sentry population** (all transaction types, EAP spans, 18,795 spans/3d — more diluted than PostHog because it includes non-lookup transactions): avg `api_calls` **0.483** (hourly avg maxes at **1.27**), `release_resolution_cache_miss` **0.010**, `release_resolution_cache_unavailable` **0.0**.

The migration is **forward-only**: PostHog cannot move events between projects, so all LML history from before 2026-08-10, and the three insights as they existed pre-cutover, remain queryable only in the [Request-O-Matic project](https://us.posthog.com/project/293013) (id `293013`) — see the "pre-cutover history" column. ## Sentry alerts — project [`wxyc/library-metadata-lookup`](https://wxyc.sentry.io/alerts/rules/?project=4511363514302464)

Metric alerts on the EAP spans dataset (`dataset: events_analytics_platform`, filter `is_transaction:true transaction:"/api/v1/lookup"`). **Sentry has disabled transaction-based metric alerts org-wide** ("Creation of transaction-based alerts is disabled, as we migrate to the span dataset"), so the alertable series is the EAP attribute form `avg(tags[lml.cache.<key>,number])`, **not** the `avg(measurements[lml.cache.<key>])` transactions-dataset form. Note also that in the legacy `transactions` dataset only `api_calls` was extracted (miss/unavailable read as no-data there) — another reason these run on EAP, where all three are present. 60-minute window, email to jake@wxyc.org.

**Transaction scope ([LML#985](https://github.com/WXYC/library-metadata-lookup/issues/985)).** All three rules filter `transaction:"/api/v1/lookup"` so they evaluate only single-lookup transactions, mirroring the PostHog alerts' `lookup_completed`-only exclusion of `/lookup/bulk` (see [Bulk is excluded](#notes--gotchas)). On `/lookup/bulk` the `cache.*` counters are **batch totals** across up to 100 items — bulk averaged ~13 `api_calls`/txn vs ~0.27 for single `/api/v1/lookup` — so including it inflated the per-transaction average and produced benign warning-threshold breaches (e.g. the 2026-07-29 miss-rate warning at 0.0517 while the single-lookup miss rate that hour was 0.0045). Thresholds are unchanged: scoping to single-lookup only *lowers* the baseline, so they stay conservative. This does **not** remove small-denominator noise in very-low-traffic hours — a per-request-rate threshold on a sparse signal still crosses occasionally — so the PostHog **Hit-rate collapse** alert remains the authoritative slow-degradation detector, with these Sentry rules the acute per-transaction pager. `transaction:"/api/v1/lookup"` is a positive scope (not `!transaction:"…/bulk"`) so any future bulk-shaped endpoint that starts emitting the `cache.*` seam is also excluded.

| Alert | Aggregate | Critical / Warning | Rule |
|-------|-----------|--------------------|------|
| **Discogs call-rate** | `avg(tags[lml.cache.api_calls,number])` | **3.0** / 2.0 | [441584](https://wxyc.sentry.io/alerts/rules/details/441584/) |
| **PG cache unavailable** | `avg(tags[lml.cache.release_resolution_cache_unavailable,number])` (per-request rate) | **0.10** / 0.02 | [441716](https://wxyc.sentry.io/alerts/rules/details/441716/) |
| **Cache miss-rate** | `avg(tags[lml.cache.release_resolution_cache_miss,number])` (per-request rate) | **0.10** / 0.05 | [441717](https://wxyc.sentry.io/alerts/rules/details/441717/) |

Sentry thresholds are set against the Sentry (diluted, all-transaction) population where the baselines are avg `api_calls` 0.48 (hourly max 1.27), `miss` 0.010, `unavailable` 0.0. The call-rate 3.0 has ~2.4× headroom over the worst observed hour. The Sentry `miss` alert is a **coarse per-request-rate proxy** — Sentry metric alerts can't express the `hits/(hits+misses)` ratio, so the authoritative "miss climbing without offsetting hit" detector is the PostHog **Hit-rate collapse** alert; the Sentry `miss` and `unavailable` alerts are the fast per-transaction guards that fire on a *dense* (severe) signal. (EAP timeseries can under-report a very sparse signal, so treat PostHog as authoritative for mild/slow degradations and Sentry as the acute pager.)

## Response — what to do when one fires

1. **Confirm it's real, not a traffic artifact.** Open the firing insight/rule. For call-rate, check whether Discogs is actually being hit harder (cold cache after a deploy, a burst of novel artists) vs a measurement glitch. For hit-rate/unavailable, cross-check the other surface (PostHog ↔ Sentry) and the [Discogs cache](https://github.com/WXYC/discogs-etl) health.
2. **Decide on the kill switch.** The feature is opt-in per-request and fully reversible. If the call-rate spike is sustained and `/lookup` latency is affected (or the hit-rate/unavailable alert confirms an upstream Discogs/PG outage the row-less path is amplifying), disable the flag:

   ```bash
   railway variables --set "LML_RESOLVE_NONLIBRARY_RELEASE=false" \
     --service library-metadata-lookup --environment production
   ```

   Railway redeploys on the variable change. **Verify** the flip landed: `/health` returns healthy and flag-on traffic drops to zero — the `cache.lml_resolve_nonlibrary_release` tag flips to `0` in PostHog and `lml.cache.lml_resolve_nonlibrary_release` to `0` in Sentry. (A Railway variable-set redeploy can occasionally fail silently — confirm via `/health` and the tag, don't assume.) With the flag off, non-library releases stay dropped (pre-LML#628 behavior); no data is lost, and re-enabling later just resumes the carry-through.
3. **Root-cause before re-enabling.** Kill switch buys time; it is not the fix. A call-rate spike usually points at cache coldness (see [LML#337](https://github.com/WXYC/library-metadata-lookup/issues/337) and the post-launch hardening epics); a hit-rate collapse or `unavailable` streak points at the Discogs cache or the `lml_cache.release_resolution_cache` Postgres, respectively.

## Rate-gate fail-open counter (`discogs_rate_gate_fail_open`, LML#879)

Not part of the row-less flag, but documented here because it follows the same unsampled-counter pattern and lands in the same PostHog project. The shared Discogs rate token bucket (LML#841, `DISCOGS_RATE_BUCKET_ENABLED`, default **off**) fails **open** to the local `AsyncLimiter` on any discogs-cache PG error, missing bucket row, or round-trip timeout. The gate's Sentry signal (`lml.discogs.rate_gate=fallback`) rides **sampled** transactions, and the dominant fail-open traffic — the BS flowsheet/album backfill floods — runs `tracesSampleRate=0` and client-discards its LML transactions, so the tag under-counts fail-open during exactly the floods it is meant to catch. The PostHog event is the sampling-independent signal.

- **Emitter:** `_capture_fail_open` in `discogs/ratelimit.py`, fired from `DiscogsRateGate.acquire`'s fail-open branch on **every** fail-open. Wired through the shared `wxyc_fastapi.observability.get_posthog_client` accessor (the gate runs deep in `discogs/service._request_with_retry`, outside any request handler, so FastAPI DI is unavailable). Best-effort: a telemetry failure never breaks the fail-open itself.
- **Shape:** event `discogs_rate_gate_fail_open`, `distinct_id="library-metadata-lookup-service"`, properties `error_type` (exception class — distinguishes a PG outage from a code defect) and `environment` (`staging` vs `production` — both draw from the **same** shared bucket, so knowing which process failed open matters). `environment` reads the bare `ENVIRONMENT` env var (`Settings.environment`, default `development`; Railway's auto-injected `RAILWAY_ENVIRONMENT` is **not** read). Verified set to `production`/`staging` on both Railway services 2026-07-20 — re-verify with `railway variables --service library-metadata-lookup --environment <env> --kv | grep '^ENVIRONMENT='` if a service is ever recreated, or every process reports `development` and the discriminator is useless.
- **Interpretation:** with the flag **off** the gate never touches PG and can never fail open, so the counter is correctly zero — not a bug. With the flag **on**, a **sustained non-zero rate means the shared bucket is silently not enforcing** (every process is falling back to its uncoordinated local limiter, i.e. pre-LML#841 behavior); check discogs-cache PG health. Occasional single events are transient PG hiccups doing exactly what fail-open is for. **A zero is only trustworthy if the emitter can deliver**: emission is best-effort and silently skipped when `POSTHOG_API_KEY` is unset, `ENABLE_TELEMETRY=false`, or the client fails — a blind emitter and a healthy bucket look identical at zero. Before reading zero as healthy during the rollout, confirm the service's other PostHog events (e.g. `lookup_completed`) are arriving in the same window; if those are absent too, you're blind, not healthy.
- **Alerting:** none yet — an alert on this counter should be wired **during the flag-enablement rollout** (mirror the hourly single-row HogQL insight pattern above; thresholds need an observed flag-on baseline, which cannot exist while the flag is default-off). Tracked in LML#879.

## Rate-gate queue wait + Discogs semaphore depth (LML#879)

Not part of the row-less flag, but documented here because it is the companion measurement for the shared Discogs rate bucket's N>=2 rollout. An empty-but-healthy shared bucket deliberately **queues** rather than failing open; that preserves the no-overshoot invariant, but at N>=2 the total token wait can grow while each waiter holds one per-process Discogs semaphore permit. These signals measure that behavior before changing it.

- **Rate-token queue wait emitter:** `_capture_queue_wait` in `discogs/ratelimit.py`, fired once a gate call has waited through at least one `allowed=false` token-bucket response. Queueing is healthy saturation, not fail-open, so this **does not** increment `discogs_rate_gate_fail_open`. If a call queues and then later fails open on a PG error/timeout, both the queue-wait event and the fail-open event are emitted.
- **Rate-token queue wait shape:** PostHog event `discogs_rate_gate_queue_wait`, `distinct_id="library-metadata-lookup-service"`, properties `wait_ms`, `queue_sleeps`, and `environment`. Sentry also tags the transaction `lml.discogs.rate_gate_queued=true` and records the transaction's worst (max-`wait_ms`) queue as measurements/data `lml.discogs.rate_gate_queue_wait_ms` plus its companion `lml.discogs.rate_gate_queue_sleeps` — the sleep count of that same worst queue, not an independently-maxed series, so the pair always describes one queue.
- **Semaphore-depth emitter:** `DiscogsService._request_with_retry` samples `_approx_semaphore_queue_depth` before awaiting the Discogs semaphore. The per-call span still carries `lml.semaphore.queue_depth`; the transaction also records the request's max queue depth as measurement/data `lml.discogs.semaphore_queue_depth`, with tag `lml.discogs.semaphore_queued=true` when depth is above zero.
- **Interpretation:** non-zero `discogs_rate_gate_queue_wait` with zero `discogs_rate_gate_fail_open` means the shared bucket is enforcing and callers are waiting for legitimate capacity. Watch p95/max `wait_ms` next to p95/max `lml.discogs.semaphore_queue_depth` during the N>=2 double-flood. If queue wait is high while semaphore depth also climbs, the likely mitigation is to release the semaphore during the rate-token sleep; do **not** fail open on a healthy-but-empty bucket.
- **Decision as of this change:** measure first and leave behavior unbounded. No semaphore-release refactor has shipped because the live N>=2 double-flood baseline is still the gate for deciding whether the tail is a real problem.

## Artist-path breaker-shed counter (`discogs_artist_breaker_shed`, LML#1049)

Not part of the row-less flag, but documented here because it follows the exact same unsampled-counter pattern as the rate-gate fail-open counter above. LML#1049 fixed `DiscogsService.get_artist_details` swallowing a saturation-breaker shed (`DiscogsBreakerOpenError`) into a plain `None` — identical to a genuine "no such artist" 404 to every downstream caller. The shed now propagates (mirroring `get_release`'s pre-existing LML#755 FIX 1), and callers handle it per their own semantics: the `/discogs/artist/{id}` and `/discogs/entity/artist/{id}` routes return 503, the cache-refresh dispatcher's artist leg records a retriable `error` outcome, and bio/markup enrichment (`lookup/enrichment/top1.py`, `discogs/markup_parser.py`) degrades silently with no negative cached. This counter is the artist path's own signal that the shared `BREAKER_OPEN_STAT_KEY` (`discogs_breaker_open_shed`, `cache.*` seam) can't provide on its own — that surface aggregates every method's sheds with no per-path breakdown.

- **Emitter:** `_capture_artist_breaker_shed` in `discogs/service.py`, fired from `get_artist_details`'s `_api_fetch` on every artist-path shed, immediately before the shed re-raises. Wired through the shared `wxyc_fastapi.observability.get_posthog_client` accessor. Best-effort: a telemetry failure never turns the shed's re-raise into something worse.
- **Shape:** event `discogs_artist_breaker_shed`, `distinct_id="library-metadata-lookup-service"`, properties `artist_id` and `environment` (same `Settings.environment` caveat as the fail-open counter above — confirm it reads `staging`/`production`, not the `development` default, before trusting the environment split).
- **Interpretation:** a healthy breaker means this counter stays at zero. A sustained non-zero rate means the shared saturation breaker is OPEN for artist-detail fetches specifically — check `discogs_breaker_open_shed` for the aggregate picture and the Discogs API health / call-rate dashboards for root cause. Same blind-emitter caveat as the fail-open counter: zero is only trustworthy if the emitter can deliver (`POSTHOG_API_KEY` set, `ENABLE_TELEMETRY=true`).
- **Alerting:** none yet — wire an hourly single-row HogQL insight once a flag-on baseline exists, mirroring the row-less flag alerts above.

## Bandcamp live-probe shed counter (`bandcamp_live_probe_shed`, LML#1098/#1106)

Not part of the row-less flag, but documented here because it follows the exact same unsampled-counter pattern as the two counters above. The LML#1098 inline Bandcamp live probe (`lookup/enrichment/bandcamp_probe.py`'s `run_bandcamp_live_probe`, gated on `LML_BANDCAMP_LIVE_PROBE`) resolves a DIRECT Bandcamp album URL synchronously on the `/lookup/bulk` enrichment path, through LML#1106's fail-fast `BandcampClient.find_album_match(fail_fast=True)` and its saturation breaker (`clients/bandcamp_breaker.py`). A shed there is a "couldn't ask" — a breaker-OPEN shed, a 429 on the single fail-fast attempt, or a non-429 transport failure (5xx, Cloudflare 403/1015, connect timeout, an unparseable 200 body — `clients/bandcamp.py`'s `BandcampTransportError`) — and maps the item's `streaming_status.bandcamp` to `unresolved` with NO cache write. Left unmeasured, a sustained Bandcamp saturation episode (rate-limit OR transport) would only be visible as a quiet drop in fill rate, the same silent-degradation blind spot the row-less flag counters above exist to close.

- **Emitter:** `_capture_shed` in `lookup/enrichment/bandcamp_probe.py`, fired from `run_bandcamp_live_probe`'s combined `except (BandcampBreakerOpenError, BandcampRateLimitedError, BandcampTransportError)` handler on every shed. Wired through the shared `wxyc_fastapi.observability.get_posthog_client` accessor. Best-effort: every branch is wrapped so a telemetry failure can never turn a shed into a lookup failure. A `TimeoutError` (the probe's own `asyncio.wait_for` ceiling tripping — genuine Bandcamp slowness or a near-zero LML#930 deadline clamp) is deliberately **excluded**: it is transient like a shed, but not itself a breaker/rate-limit signal, so it does not increment this counter (mirrors the LML#879 rate-gate queue-wait vs. fail-open distinction — queueing/timing out and failing open are different signals).
- **Shape:** event `bandcamp_live_probe_shed`, `distinct_id="library-metadata-lookup-service"`, properties `reason` (the exception class name — `BandcampBreakerOpenError`, `BandcampRateLimitedError`, or `BandcampTransportError` — distinguishes a breaker-open shed from a fresh 429 from a transport failure) and `environment` (same `Settings.environment` caveat as the counters above — confirm it reads `staging`/`production`, not the `development` default).
- **Interpretation:** a healthy Bandcamp path means this counter stays at zero. A sustained non-zero rate means the fail-fast breaker is OPEN or Bandcamp itself is degraded (rate-limited or transport-failing) for the live-probe path specifically — cross-check the breaker's own state transition logs (`clients/bandcamp_breaker.py`'s `_open()` WARNING) and the `reason` property to tell a rate-limit flood from a Cloudflare-block/tarpit shape apart. Same blind-emitter caveat as the counters above: zero is only trustworthy if the emitter can deliver (`POSTHOG_API_KEY` set, `ENABLE_TELEMETRY=true`) — confirm other PostHog events (e.g. `lookup_completed`) are arriving in the same window before reading zero as healthy.
- **Alerting:** none yet — wire an hourly single-row HogQL insight once a flag-on baseline exists, mirroring the row-less flag alerts above. `LML_BANDCAMP_LIVE_PROBE` is default-off pending the BS#642 backfill drain (see `docs/env-vars.md`), so there is no production traffic to baseline against yet.

## Compilation-track batched-read fail-open counter (`compilation_track_read_fail_open`, LML#1021)

Not part of the row-less flag, but documented here because it follows the exact same unsampled-counter pattern as the three counters above. LML#1021's `POST /api/v1/identity/bulk-resolve-libraries` handler does one batched pre-fan-out read of `lml_cache.compilation_track_identity` per request (when `include_tracks: true`), keyed on the request inputs' `legacy_release_id`s. A `TRANSIENT_PG_ERRORS` failure on that read degrades every affected `kind: compilation` row to the unvisited `(tracks_attempted: false, tracks: [])` state rather than failing the whole batch closed (a deliberate posture choice — see the PR body's "503-vs-degrade" design note) — but that wire shape is **identical** to the routine case where a release simply hasn't been backfilled by `scripts/backfill_compilation_track_identity.py` yet. A `logger.warning` alone can't tell those two apart from the outside; this counter is the distinguishing signal.

- **Emitter:** `_capture_compilation_track_read_fail_open` in `identity/router.py`, fired from `bulk_resolve_libraries`'s `except TRANSIENT_PG_ERRORS` handler around the batched read, on every degrade. Wired through the shared `wxyc_fastapi.observability.get_posthog_client` accessor. Best-effort: every branch is wrapped so a telemetry failure can never turn the graceful degrade into something worse.
- **Shape:** event `compilation_track_read_fail_open`, `distinct_id="library-metadata-lookup-service"`, properties `error_type` (exception class name), `legacy_release_id_count` (how many releases in the batch the failed read would have covered), and `environment` (same `Settings.environment` caveat as the counters above — confirm it reads `staging`/`production`, not the `development` default).
- **Interpretation:** a healthy discogs-cache PG means this counter stays at zero — including during normal operation of a partially-backfilled catalog, since an un-backfilled release never reaches this code path at all (it has no `lml_cache.compilation_track_identity` rows to read, which is a successful read returning nothing, not a failure). A sustained non-zero rate means the discogs-cache PG pool (the same one `entity.identity` reads share) is degraded specifically for this query — cross-check `/health` and the entity-store probe. Same blind-emitter caveat as the counters above: zero is only trustworthy if the emitter can deliver (`POSTHOG_API_KEY` set, `ENABLE_TELEMETRY=true`).
- **Alerting:** none yet — wire an hourly single-row HogQL insight once a baseline exists, mirroring the row-less flag alerts above.

## Single-artist track-derivation batched-read fail-open counter (`single_artist_track_read_fail_open`, LML#1138)

The `kind: single_artist` sibling of the LML#1021 counter directly above — same pattern, same rationale. LML#1138's arm of `POST /api/v1/identity/bulk-resolve-libraries` runs two batched pre-fan-out reads per request (when `include_tracks: true`): the `lml_cache.library_release_override` pins mapping (`legacy_release_id` → `discogs_release_id`) and the pinned releases' tracklists from the discogs-cache `release_track` tables. A `TRANSIENT_PG_ERRORS` failure on **either** read degrades every affected `kind: single_artist` row to the unvisited `(tracks_attempted: false, tracks: [])` state — byte-identical to the routine un-pinned case (~71% of non-V/A rows at v1's pin coverage), so only this counter distinguishes "PG is unhappy" from "the catalog isn't pinned yet".

- **Emitter:** `_capture_single_artist_track_read_fail_open` in `identity/router.py`, fired from `bulk_resolve_libraries`'s `except TRANSIENT_PG_ERRORS` handler around the paired reads, on every degrade. One counter for the pair, deliberately — either read failing degrades the same rows the same way. Same best-effort wrapping as the sibling.
- **Shape:** event `single_artist_track_read_fail_open`, `distinct_id="library-metadata-lookup-service"`, properties `error_type`, `legacy_release_id_count` (how many candidate releases the failed read pass would have covered), `environment` (same caveat as above).
- **Interpretation:** identical to the sibling — an un-pinned release is a successful read returning nothing and never fires this; sustained non-zero means the discogs-cache PG pool is degraded for these queries. Note the pins read uses the *strict* override reader (`get_library_release_overrides_strict`) precisely so failures reach this counter; the swallowing `/lookup` reader would silently map an outage to "no pins" and blind it.
- **Coverage vs. failure:** this counter is NOT the coverage signal. The v1 coverage gap (un-pinned rows + the MB tail per the LML#1138 decision record) is observable per request via the `lml.bulk_resolve.single_artist_tracks_asked` / `lml.bulk_resolve.single_artist_tracks_pinned` span data and the matching `bulk resolve complete:` exit-log fields — the asked/pinned spread is the gap LML#842's `streaming_album` leg is expected to close toward ~77%.
- **Alerting:** none yet — wire an hourly single-row HogQL insight once a baseline exists, mirroring the sibling.

## Artist-name pool unusable counter (`artist_name_pool_unusable`, LML#1245/#1248)

Not part of the row-less flag, but documented here because it follows the same unsampled-counter pattern as the counters above. `LibraryDB._build_artist_name_pool` reads the four artist-name source columns once per `adopt_connection` into the pool that serves both `_artist_exists_exactly` (LML#1248) and the full-pool fuzzy correction scan (LML#1245). If any source fails to load, the pool is marked unusable and the two consumers degrade **asymmetrically**: exact-existence falls back to per-call SQL (slower but exact), and fuzzy artist correction is suppressed entirely until the next reconnect. Both degradations are invisible from the response — a lookup that would have been corrected simply misses — so this counter is the only queryable signal that the service is running in that state.

- **Emitter:** `_capture_artist_name_pool_unusable` in `library/db.py`, fired from `_build_artist_name_pool` at build time — at most **once per `adopt_connection`**, not per affected request. The degraded state persists for the life of the connection, so a per-lookup counter would emit thousands of events describing one fact. Delegates to `core.observability.capture_unsampled_counter` (LML#1204): best-effort, gated by `Settings.enable_telemetry`, unable to raise. The build's own `logger.warning` names which source column failed; this counter carries the queryable series.
- **Shape:** event `artist_name_pool_unusable`, prefix `library_artist_pool`, property `partial_name_count` (how many names loaded before the failure — 0 means the first source failed, a near-complete count fingerprints which later source broke), plus the shared counter properties (`environment`, same `Settings.environment` caveat as the counters above).
- **Interpretation:** a healthy `library.db` means this counter stays at zero — the pool build reads the same columns `adopt_connection` just schema-probed, so firing means schema drift between the probe and the read, a mid-read file swap, or a corrupt/BLOB row in a source column (any non-`str` value disqualifies the pool rather than silently shrinking it). Expect it to correlate with a `library.db` upload or the daily sync. Same blind-emitter caveat as the counters above: zero is only trustworthy if the emitter can deliver.
- **Alerting:** none yet. Deliberately **not** on `POSTHOG_RATELIMIT_EXEMPT_EVENTS` (see `docs/env-vars.md`): it satisfies the degradation-counter membership rule, but that list is for counters that feed alerts, and its once-per-reconnect structural ceiling means there is no incident burst for the limiter to swallow. Add it to the exempt list when an alert is built on it, not before.

## Location-union index-authority verdicts (`location_union_index_*`, LML#1026)

LML#1026 makes the `lml_cache.compilation_track_location` recall index authoritative for comp-track resolution on the union-active `/lookup` path — TRACK_ON_COMPILATION's live-Discogs comp-discovery pass is suppressed whenever the index answers. That authority flip records one of three per-request `cache.*` counters at the strategy's consult site (`_consult_recall_index` in `lookup/strategies/track_on_compilation.py`), all pre-declared in `_LML_CACHE_STATS_EXTRA_KEYS` so they seed to 0 and are alertable baseline series on the same PostHog/Sentry surface as the LML#681 counters above:

- `location_union_index_hit` — ≥1 renderable shelf location; the fold supplies the results and no live comp discovery is spent.
- `location_union_index_miss` — the probe ran and found nothing renderable; live comp discovery stays suppressed (the #271-locked "removed, not augmented" decision).
- `location_union_index_degraded` — the index could not be consulted (discogs-cache PG failure, the 500ms probe timeout, or a rank/join error); the full legacy live pass is restored for that request.

**Alerting guidance:** the degraded series is the one that matters — a sustained nonzero `sum(location_union_index_degraded)` means comp lookups are running without the index (discogs-cache PG outage class; the kill switch is *not* the right lever there since degraded already falls back to the legacy pass). Hit-vs-miss rate is the dashboard for validating the #271 "index replaces live discovery" bet after the index is populated (LML#1027 step 6). No thresholds are wired yet; mirror the LML#681 alert shapes above once a populated-index baseline exists.

## Wikipedia-preferred-bio counters (`wikipedia_bio_*`, LML#513/#1192)

Phase B of the Wikipedia-preferred-artist-bio program (`docs/plans/lml-1192-wikipedia-artist-bio.md`) — behind `LML_BIO_PREFER_WIKIPEDIA` (default off, inert without `LML_WIKIPEDIA_SLUG_MATCH` also on; see `docs/env-vars.md`) — swaps `artist_bio` from the Discogs profile to a cached Wikipedia lead-paragraph extract when one is confidently picked and fresh in `lml_cache.artist_wikipedia_bio`. Eight counters split across two DIFFERENT telemetry mechanisms, deliberately:

**Per-request `cache.*` counters** (six keys, all pre-declared in `_LML_CACHE_STATS_EXTRA_KEYS` so they seed to 0 and form alertable baseline series on the same PostHog/Sentry surface as the LML#681 counters above) — all six run inside the request that triggered them, so the standard per-request recorder is the right tool, but they are NOT all recorded at the same call site: two fire during `lookup.enrichment.wikipedia_bio.resolve_served_bio` itself (before the LML#504 split gate has run), three fire from `finalize_bio`'s private helpers in the same `lookup/enrichment/wikipedia_bio.py` module (after the gate, so they can see whether the resolved bio actually survived it), and one fires from `lookup.enrichment.wikipedia_warm.schedule_wikipedia_bio_warm` in the sibling module:

- `wikipedia_bio_cache_hit` — **[`resolve_served_bio`]** a fresh positive cache row (`extract IS NOT NULL`); the Wikipedia extract is served. Since LML#1192 review round 5 the read is keyed on `discogs_artist_id` alone, not a URL match against the caller's live pick — see `entity/artist_wikipedia_bio.py`'s module docstring.
- `wikipedia_bio_cache_negative` — **[`resolve_served_bio`]** a fresh negative cache row (a prior fetch found nothing usable); falls back to the Discogs profile. Same round-5 caveat: no URL match, `discogs_artist_id` alone.
- `wikipedia_bio_cache_miss_warm_scheduled` — **[`_maybe_schedule_wikipedia_bio_warm`, called from `finalize_bio`]** the row was absent or aged past its TTL (a genuine miss — round 5 collapsed "no row" and "row exists but stale" into one outcome at the read; there is no longer a separate "keyed to a since-recalibrated URL" case, since the row no longer compares its URL against the caller's pick at all), AND `warm_cache=True`, AND the LML#504 split gate let the WIKI URL through (checked via `enriched_top1_wiki is not None`, deliberately NOT the bio-text `bio_surfaced` check the two counters above use — LML#1192 review round 4, P0-6: an artist with no Discogs profile at all has `bio_surfaced` unconditionally False even on a genuine cache miss, which would make this warm unreachable for exactly the cohort it exists for), AND a background fetch was actually scheduled (not shed or deduped).
- `wikipedia_bio_warm_shed` — **[`schedule_wikipedia_bio_warm`, `lookup/enrichment/wikipedia_warm.py`]** a miss-warm scheduling attempt was shed because the pending-plus-running depth bound (concurrency 2) was already at capacity.
- `wikipedia_bio_served` — **[`_record_bio_adoption`, called from `finalize_bio`]** the response's `artist_bio` is the Wikipedia extract. This is a GATED SUBSET of `wikipedia_bio_cache_hit`, not a mirror of it (LML#1192 review, B2-1 deliberately split them apart): a cache hit can still be nulled by the LML#504 split gate between `resolve_served_bio` and `finalize_bio`, in which case `cache_hit` fired but `served` does not. Kept as its own key so "served" reads directly as the adoption-rate numerator without a join against the gate's outcome.
- `wikipedia_bio_fallback_discogs` — **[`_record_bio_adoption`, called from `finalize_bio`]** the response's `artist_bio` is the Discogs profile, for ANY reason the bio surfaced but wasn't sourced from Wikipedia (flag off, no above-floor pick, negative cache hit, a genuine miss, or a couldn't-ask PG read failure degrading to the Discogs pair per round 6, C2-3) — the adoption-rate denominator's complement.

**Unsampled PostHog counters** (two keys, deliberately NOT in `_LML_CACHE_STATS_EXTRA_KEYS`), recorded inside `lookup.enrichment.wikipedia_warm._run_warm` — the background warm TASK itself, which by the time its `await client.get_summary(...)` resolves has typically outlived the request that scheduled it. Writing into that request's `cache_stats` dict at that point would be a silent no-op — not because `asyncio.create_task` snapshots or copies the dict (it doesn't: the task's context is a shallow copy of the parent's ContextVar *bindings*, but the dict object a `cache_stats` binding points to is the same shared mutable object in both contexts), but because of ordering: the request has almost always already read/reported its `cache_stats` snapshot and returned before the task's first await point resolves, so a write at that point lands in a dict nobody will read again — the same class of problem `background._warm_bio_cache`'s "no Sentry tag" note describes for Sentry scope, but for `cache_stats`. These go through the `discogs.service._capture_artist_breaker_shed` / `discogs.ratelimit._capture_fail_open` direct-`get_posthog_client` pattern instead, same as the counters two sections below:

- `wikipedia_bio_fetch_ok` — the warm task's live Wikipedia fetch resolved a usable extract, written to the cache as a positive.
- `wikipedia_bio_fetch_reject` — the fetch completed but the client rejected it (disambiguation page, empty extract, or a description-pattern reject — see `clients/wikipedia.py`), written to the cache as a negative. Neither key increments on a `WikipediaFetchError` (transient — timeout, network error, exhausted 429 retries): that path writes nothing to the cache and is logged only, per the "couldn't ask ≠ confirmed absent" principle every sibling breaker in this repo follows.

Both fetch counters are non-exempt from the PostHog capture rate limiter (`POSTHOG_RATELIMIT_EXEMPT_EVENTS`, `docs/env-vars.md`) -- deliberately, per the degradation-counter membership rule recorded there. Set any threshold on the reject *ratio*, never on a raw count, which a sustained traffic burst can drop while leaving the ratio intact. A `lml_cache.artist_wikipedia_bio` query is not a substitute: it measures coverage across all writers, and the offline drain dominates that table, so it cannot recover this warm path's own volume (WXYC/library-metadata-lookup#1217).

**Interpretation:** `wikipedia_bio_served / (wikipedia_bio_served + wikipedia_bio_fallback_discogs)` is the adoption rate — expect it near zero immediately after the flag flips (the offline drain, Phase C, is the primary population mechanism; the lazy miss-warm only extends coverage to artists newly entering the flowsheet) and rising as the drain progresses. A sustained nonzero `wikipedia_bio_warm_shed` under normal (non-flood) traffic means the fixed depth bound is undersized for the actual miss rate — unlike the streaming-warm sibling's multiplier, this one is NOT env-tunable (`lookup/enrichment/wikipedia_warm.py`'s `_QUEUE_DEPTH_MULTIPLIER`), so raising it needs a code change. `wikipedia_bio_fetch_reject` trending upward over time (rather than settling) can indicate the Phase-A slug-scored picks are drifting toward non-artist pages faster than the denylist + description-pattern guard catch them — worth a fresh `scripts/wikipedia_url_validation.py` sample if so.

**Alerting:** none yet — wire hourly single-row HogQL insights for the adoption rate and the shed/reject counters once a flag-on baseline exists, mirroring the row-less flag alerts above. Both unsampled counters carry the same blind-emitter caveat as the counters below: zero is only trustworthy if `POSTHOG_API_KEY`/`ENABLE_TELEMETRY` are actually delivering — confirm `lookup_completed` events are arriving in the same window before reading zero as healthy.

## Event-loop-lag gauge (`event_loop_lag_ms`, LML#907)

Not part of the row-less flag, but documented here because it rides the same `cache_stats` seam and lands on the same `cache.*` / `lml.cache.*` surface. LML runs a **single uvicorn worker**, so every request's synchronous work shares one event loop; under the enrichment flood that loop saturates and a ready coroutine's continuations — especially the post-await response tail — wait seconds to be scheduled. That wait is the `/lookup` **starvation tax** (`plans/lookup-latency-event-loop-starvation.md` §3): on a fully cache-warm, zero-I/O trace all awaited work finished at T+5.1s and then **5.08s of no spans** passed before the response returned. It is invisible to `RequestTelemetry.track_step` and the `Server-Timing` header (both measure *inside* pipeline steps; the tax lands before the first, between, and after the last), so this gauge is the only machine-readable signal for it.

- **Emitter:** a background sampler task (`core/event_loop_lag.py`, started in `main.py` lifespan, cancelled on shutdown) sleeps a fixed `0.5s` and measures `loop.time()` drift = `elapsed − 0.5s` (clamped ≥ 0) as the loop lag, keeping an EWMA (`alpha=0.3`) in a process global. The lookup router stamps the current value onto each request's `cache_stats` as `event_loop_lag_ms`, once per context right after `_record_lml_flag_tags` (so the shared-context `/lookup/bulk` batch records one sample, not a per-item sum). Seeded in `_LML_CACHE_STATS_EXTRA_KEYS` for shape stability.
- **Shape:** PostHog `cache.event_loop_lag_ms` on `lookup_completed`; Sentry transaction measurement `lml.cache.event_loop_lag_ms` (EAP attribute `tags[lml.cache.event_loop_lag_ms,number]`), `traces_sample_rate=1.0`, so it covers every request. The stamped value is a per-request **sample** of the process-global gauge, not that request's own tail — read it as loop health over time (avg/p95 across requests), not per-request attribution.
- **Interpretation:** a healthy single-worker loop sits near ~0. A sustained climb into the hundreds of ms / seconds means the loop is saturated (the starvation regime) — expected under the BS enrichment flood, and the number Lever B (#747, multi-worker) is meant to drive back down. **A flat `0` is ambiguous** — it can mean a genuinely idle loop OR that the gauge is blind (sampler disabled, the first ~0.5s of process life, or a sampler task that died): before reading `0` as "loop healthy," confirm the service is serving traffic and `lookup_completed` events are arriving in the same window (the same blind-emitter caveat as the #879 counter above). The gauge **narrows** the §4 on-CPU-attribution unknown — it confirms the loop is saturated but does not by itself split the cost between pydantic serialize / PyO3 normalization / Sentry span assembly — enough to prioritize: watch the gauge before/after Lever A′ (#904) and Lever B (#747).
- **Kill switch:** `LML_EVENT_LOOP_LAG_GAUGE` (default **on**). Off ⇒ no sampler and no stamp; the seeded key stays `0`. A gauge-read failure logs at WARNING and the request proceeds without the stamp (never a 500).
- **Alerting:** none yet — a threshold alert (mirror the Sentry EAP `avg(tags[lml.cache.event_loop_lag_ms,number])` pattern above) should be wired once an on-load baseline exists. Tracked in LML#907.

## Notes / gotchas

- **Flag-on scoping** is via the `lml_resolve_nonlibrary_release=1` tag. Historically (pre-LML#1170, single-tenant Request-O-Matic project) that alone was a sufficient scope, since the flag is fully enabled staging + prod. **Post-cutover it is no longer sufficient by itself**: prod and staging share one PostHog project and key (LML#1170's "one key for both envs" decision), so every insight in the "PostHog alerts" section above also filters `properties.environment = 'production'` — flag-on scoping still matters, and still stays correct if the flag is ever rolled back, it is just no longer the only filter keeping a staging soak's `lookup_completed` traffic out of the prod-scoped alerts.
- **Bulk is excluded** by querying `lookup_completed` only (never `lookup.bulk_completed`). On `/lookup/bulk` the counters are batch totals across the whole shared `cache_stats` context, which would mix single- and batch-shaped values.
- **Don't touch the LML#681 emit code** to change these alerts — the keys are shape-stable (`_LML_CACHE_STATS_EXTRA_KEYS`, LML#544) and correct; alerting only consumes them.
- **These alerts are UI/API config, not alert-as-code.** LML has no versioned alert config today; this doc is the source of truth for the thresholds and rationale. If the team later wants them versioned, that's a separate decision.
