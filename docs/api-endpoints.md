# API Endpoints

Non-lookup endpoints exposed by the service. The `POST /lookup` endpoint is covered in [`architecture.md`](architecture.md).

## Identity Resolution Endpoints

The service exposes REST endpoints for querying the `entity.identity` table in the discogs-cache PostgreSQL database. These endpoints are consumed by semantic-index (via `--entity-source=lml`) and other pipeline tools.

- `GET /identity/resolve?name=Stereolab` -- Look up a single artist name. Returns 200 with external IDs or 404.
- `POST /identity/bulk` with `{"names": ["Stereolab", "Autechre", ...]}` -- Resolve a batch of names. Returns `identities` (found) and `unresolved` (not found).
- `POST /api/v1/identity/bulk-resolve-libraries` -- Cross-cache-identity contract endpoint per the 2026-05-09 pivot (BS#800). Backend POSTs library rows; LML composes per-source provenance via §3.4.1.1 Rules 2-6 and returns one verdict per row (`kind: single_artist | compilation | unresolved`). Implementation lives in `identity/bulk_resolve.py`; sits under `/api/v1/` so it inherits `LML_API_KEY` bearer auth. Since LML#1151, the request's optional `include_tracks` flag (1.30.0 contract; marker 1.31.0) gates the per-result `(tracks_attempted, tracks)` pair on both resolved kinds (`None` ≡ `false`; `kind: unresolved` never carries the pair). Since LML#1021, the `kind: compilation` arm reads real per-track identity out of `lml_cache.compilation_track_identity` (the LML#1020 store) keyed on the request input's `legacy_release_id` (wxyc-shared#315 -- library.db's legacy MySQL id space, NOT Backend's serial `library_id`, a different space per LML#1021's F2 finding): a batched pre-fan-out read (one query per request, never per row) groups rows in memory before composing `tracks[]`, MIN-of-confidences only (no fabricated cross-source-agreement boost -- the per-track Discogs/MusicBrainz legs run independently with no wikidata cross-reference step, unlike the album-grain composer's `entity.identity` rows). A release with any store rows answers `(true, tracks)`, misses included (`resolved_artist_name`/`confidence`/`method` all `null`, "we looked, the answer is no"); a release with zero store rows -- unvisited, or the input carries no `legacy_release_id` bridge -- answers `(false, [])`. Per-track `sources[]` omits miss legs (a flagged wxyc-shared gap: `BulkResolveProvenanceEntry.method` is required and non-nullable, so a miss row's `null` method cannot be echoed without either fabricating a value or a schema change to make it nullable like its `confidence`/`external_id` siblings). Since LML#1138, the `kind: single_artist` arm DERIVES its `tracks[]` at read time (BS#801 decision D13, option (c) -- no store, no matcher, no backfill): the input's `legacy_release_id` is mapped to a Discogs release via the hand-verified `lml_cache.library_release_override` pins (`load_single_artist_release_pins` -- the v1 mapping source per the 2026-08-08 decision record on LML#1138; the LML#842 `lml_cache.streaming_album` leg extends the same seam once seeded, lifting coverage from the pins' ~29% of non-V/A rows toward the Discogs re-match's ~77.3%; the MusicBrainz-only tail stays out of scope for v1 -- the MB cache PG is not reachable from prod LML), and the pinned release's tracklist is read from the discogs-cache `release_track`/`release_track_artist` tables (`entity/release_tracklist.py`) -- two batched pre-fan-out reads per request, never per row. Per-track `confidence`/`method` inherit the PIN's provenance (`manual`/1.0 -- a hand-verified release mapping; D13's "inherit the release-level identity" resolved to the mapping's own provenance), `resolved_artist_name` is the release's resolved artist (`entity.identity.library_name`), and the `artist_name` echo is the per-track extra=0 Discogs credit where one exists (features, splits) else the release artist. A pinned release the cache holds answers `(true, tracks)` -- or `(true, [])` when it genuinely has no cached track rows ("we looked, the answer is nothing"; a batched presence probe on `release` makes that distinction); an un-pinned row, a bridge-less row, or a pin pointing at a release the FILTERED discogs-cache doesn't hold (reachable -- the cache build filters by exact artist-name equality, and pins exist precisely where automatic matching failed) all answer the unvisited `(false, [])` so the consumer keeps re-asking and coverage self-heals as pins, the #842 leg, and discogs-etl ingests grow. Coverage is observable per request via the `lml.bulk_resolve.single_artist_tracks_asked` / `..._pinned` span data and the matching exit-log fields. `tracks_contract_version` echoes `1` whenever `include_tracks` was understood-true (api.yaml 1.32.0's both-arms rule -- real `tracks_attempted` on BOTH kinds -- is satisfied as of LML#1138; the rule gates on emitting the pair, not on coverage), and stays `null` when the flag is off/omitted -- consumers must read `tracks_attempted`, not `tracks.length`, as the resolved signal, and value-probe the marker (`=== 1`, never key presence). The one wire change a flag-off (un-upgraded) caller observes: the compilation arm's previously always-empty `tracks: []` is now `null` — deliberate and contract-sanctioned, not a regression.
- `POST /api/v1/identity/resolve` -- Release-identity resolve endpoint added by LML#526. Accepts `{kind, source, external_id}` and returns `{identity_id, kind, minted}`. Idempotent: the same triple always returns the same `identity_id`; only the first call mints. Validation runs *before* any DB write — Discogs `external_id <= 0`, malformed Bandcamp URLs, and unknown sources are rejected with 422, so no poisoned identity rows can be created. Concurrency-safe: two concurrent mints converge on one row via the per-source `UNIQUE` constraints on `entity.release_identity` (see `entity/release_identity.sql` for the canonical DDL). Validation + coercion live in `identity/release_validation.py`; storage helpers (`mint_or_get_release_identity`, `get_release_identity_by_source`, `log_release_reconciliation`) live in `entity/store.py`. v1 accepts only `kind: release`; `kind: artist` is the documented follow-up. Use `GET /identity/resolve?name=<artist>` for the artist-name-keyed case — separate endpoint on the open router.

These endpoints return 503 when `DATABASE_URL_DISCOGS` is not set or the entity schema is not applied.

## Artist Resolve Endpoint (bulk bare-name)

`POST /api/v1/artists/resolve/bulk` resolves clean bare artist names — typically touring artists WXYC has never cataloged — to Discogs artist identities, minting `entity.identity` rows for unambiguous resolutions (LML#759). Backend-Service's concerts pipeline (BS#1614) is the consumer. Bearer `LML_API_KEY` auth (401 missing header, 403 wrong/malformed token); the per-request name cap comes from api.yaml's `maxItems` (currently 25; over-cap returns 413 — the route reads the cap from the generated model, so only this sentence can drift). A fully-escalating batch ≈ one Discogs API call per name ≈ 30s at the shared 50/min budget, so callers page.

Request: `{"names": ["Wishy", "REZN"], "dry_run": false}`. `dry_run: true` runs every tier identically — including live Discogs API verification — but skips the write-back. Inputs are sanitized (Unicode format characters dropped, whitespace trimmed; responses echo the raw string per position) and validated up front: blank, NUL-bearing, unencodable, empty-identity-form, and bare-parenthesized-number names ("(2)", "[2]", "(2)(3)" — a Discogs disambiguator whose artist name was lost upstream) return **422** for the whole batch, never an in-band verdict a consumer could negative-cache. A fully-bracketed non-numeric name like "(Smog)" is a real artist name and stays resolvable.

Inputs are deduplicated on (fixed-point identity-match form, trailing qualifier). Qualifier detection mirrors the normalizer: every balanced trailing `()`/`[]` group peels off the NFKC-folded lowercase name (nested tails included), digit qualifiers canonicalize across bracket/width/spacing spellings ("[2]", "( 2 )", "（２）" all key as "(2)"; zero-padded "(02)" stays distinct), and multi-group tails concatenate ("(2)(uk)"). A qualified name ("Popsicle (2)") is its own work unit — it never inherits (or supplies) the bare form's verdict, resolves only when the API candidate's own title carries the same qualifier, **never mints**, and skips the cache-evidence tier (stripped-form evidence can't distinguish family members).

**Verify-before-mint** (the LML#759 design): the discogs-cache is a pair-wise-filtered ~50K *biased sample* of Discogs, so for bare names it can corroborate but never decide. Per group:

1. `entity.identity` three-leg read over **every** distinct spelling in the group — true short-circuit (`method: identity_store`) when a row whose own stored key carries the group's qualifier holds a `discogs_artist_id`. Two conflicting ids across a group's spellings is the store contradicting itself → `ambiguous` (`candidate_count` null, nothing measured).
2. Cache candidate-set queries (exact / member / alias / name_variation equality legs + trigram) — evidence only, reported in `cache_corroboration` on **both** resolved and unresolved verdicts (the per-leg yield telemetry sizing a possible v2 alias arm). Always `[]` — cache never consulted, not a measured zero — on identity-store short-circuits, qualified inputs, and store-conflict verdicts.
3. Discogs API exact-form uniqueness check (`method: api_search`) — one `type=artist` search page, probed with the group's lexicographically-least spelling (deterministic in batch content), results filtered to titles whose **fixed-point** identity-match form equals the group's. The form strips trailing qualifiers, so "Popsicle (2)" collides with "Popsicle" — that strip *is* the overload detection.

Verdicts per name (index-aligned with the request; `candidate_count` is null — "not measured", never zero — when the API tier didn't run):

- **resolved** — exactly 1 exact-form API candidate whose own title qualifier matches the input's, with no disagreeing equality-leg cache candidate; or an identity-store hit. Unqualified `api_search` resolutions upsert `entity.identity` keyed on the group's least spelling (or the found Discogs-id-less row's stored key, filled in place), populating `discogs_artist_id` only. The upsert never overwrites a populated column with NULL; hardening the no-overwrite guarantee against concurrent writers is LML#766. `canonical_name` carries the raw Discogs title, "(N)" suffix included — `identity_store` resolutions omit it (the store keeps no Discogs title).
- **`unresolved_reason: ambiguous`** — ≥2 exact-form candidates (an overload family); 1 candidate that an equality-leg cache candidate disagrees with; 1 candidate whose title qualifier mismatches the input's (a "(N)"-titled singleton answering a bare input is family evidence — and vice versa); or conflicting identity-store rows. Conflict means doubt, doubt means NULL; never a guess, nothing mints.
- **`unresolved_reason: not_found`** — the API tier ran and measured 0 exact-form candidates, even when cache alias/member legs had matches (alias-shaped evidence can't be globally uniqueness-checked in v1; it's counted in `cache_corroboration` instead).
- **`unresolved_reason: escalation_unavailable`** — the **couldn't-ask** verdict: the PG tiers missed and the API tier couldn't answer (LML#755 breaker open, outage cool-down, 429/5xx after retries, network errors, a distrusted page, or no `DISCOGS_TOKEN` configured). Only a breaker trip short-circuits the rest of the batch; a per-name failure lets the batch continue. There is no batch-level 503 for Discogs outages — the PG tiers keep answering. Consumers must not apply a no-match TTL here, and should retry with bounded attempts: a persistent `escalation_unavailable` indicates a configuration or upstream condition retrying won't move.

The API-verification leg runs serially (the shared limiter paces globally at 50/min; intra-request concurrency would only starve interleaved live-lookup traffic — the LML#370/#372 lesson). Tier orchestration lives in `artists/resolver.py`, the route in `artists/router.py`, the candidate-set queries in `discogs/cache_service.py`, and the `type=artist` search in `discogs/service.py:search_artists`. Observability: an explicit `http.server` Sentry span with `lml.artist_resolve.*` counters (status pinned on every resolver-phase exit — 200/422/499/503/500; requests rejected before the resolver runs produce no span) and one aggregate `artist_resolve_completed` PostHog event per successfully completed request (no per-name events, nothing on error exits — the span carries error-class observability). The probe counter is named `discogs_api_calls` at its source (`ResolveStats`), so the span key, event property, and log field agree; the framework's per-service `api_calls` map carries the same count as `api_calls.discogs` (the cross-event slicing convention every sibling `*_completed` event follows), and the `cache` map seeds `discogs_breaker_open_shed` to 0 on every request so breaker-open time is a stable, alertable series rather than a key that appears only on shed requests.

## Bulk Artist-Genres Endpoint

`POST /api/v1/artists/genres/bulk` aggregates per-artist Discogs **genres** (coarse) and **styles** (fine) from the discogs-cache (LML#781). Backend-Service's nightly concerts enrichment (WXYC/Backend-Service#1624) is the only caller — server-to-server, never a listener hot path — powering the iOS On Tour genre filter (WXYC/wxyc-ios-64#474 R2). Bearer `LML_API_KEY` auth like `streaming-check`; the per-request artist cap is 25 (over-cap returns 413), empty batch returns 422.

Request: `{"artists": [{"artist_name": "Juana Molina", "discogs_artist_id": 12345}, {"artist_name": "Wishy"}]}`. `discogs_artist_id` is optional but strongly preferred — it keys the cache aggregation on the stable Discogs artist entity (homonym-safe); the name-only fallback is a case-insensitive exact match. Backend-Service resolves the ID via `POST /api/v1/artists/resolve/bulk` (LML#759) first, so it is usually present.

Response: `{"results": [{"artist_name": ..., "discogs_artist_id": ..., "genres": [...], "styles": [...], "source": ..., "bio": ...}]}` — index-aligned with the request. `genres` is the coarse ~15-value Discogs genre taxonomy (the iOS filter chips), majority-take truncated to the top 1-2. `styles` is the finer taxonomy, aggregated the same way but returned in full "for completeness" (the iOS filter ignores it — it is a detail-view treatment). WXYC's internal library genre taxonomy (`genre_artist_crossreference`) is deliberately never surfaced here — these values come only from the discogs-cache `release_genre` / `release_style` rows.

`bio` is the artist's Discogs `profile` (raw markup, parsed downstream), keyed on `discogs_artist_id` via a single cache-only bulk artist-details read for the whole batch (`get_artist_details_bulk` — no per-artist live-API fan-out, so it stays inside the bulk budget). It is `null` when the artist has no id (name-only input), is not in the cache, has a blank profile, or is a not-found tombstone. Additive + nullable, and **independent of `source`**: `source` continues to describe *genre* provenance only, since bio and genres can diverge (a cached profile with no genre rows, or vice-versa). Consumed by Backend-Service to project `Concert.artist_bio` on `GET /concerts` (the On Tour artist-bio card).

**Aggregation.** An artist's genres/styles are a frequency count over the artist's *primary-credit* (`release_artist.extra = 0`) releases in the discogs-cache — each release contributes each of its genres/styles once (`COUNT(DISTINCT release_id)`), ranked by count descending then name ascending (a total, insertion-order-independent tie-break — `artists/genre_aggregation.py`). The SQL aggregation lives in `discogs/cache_service.py:aggregate_artist_genre_style`; the ranking + truncation is a separate pure function so it is unit-testable without a database and shared with the fallback path.

**Cache-miss fallback.** When the discogs-cache has no genre *and* no style rows for an artist, the Discogs API fallback discovers the artist's releases via `discogs/service.py:search_release_ids_by_artist` (one `type=release` search) and fetches each (bounded by `FALLBACK_MAX_RELEASES`) through the cached `get_release` — reusing the canonical fallthrough write-back so the fetched releases (and their `release_genre` / `release_style` rows) persist to the discogs-cache. The next call for that artist therefore hits the cache path: **the fallback is self-healing.** It inherits the Discogs rate-limit + LML#755 saturation-breaker gates for free.

`source` is one of `cache` (served from the discogs-cache), `discogs_api` (cache miss; the API fallback produced genres), `not_found` (cache miss; the API answered but the artist has no genre/style data — safe to negative-cache), or `unavailable` (cache miss and the API could not be consulted — no `DISCOGS_TOKEN`, breaker open, or a transient fetch failure — retry, do NOT negative-cache). A missing Discogs service or breaker shed degrades a per-artist cache miss to `unavailable`; only a cache-pool failure returns a batch-level 503.

Implementation lives in `artists/`:
- `artists/genre_models.py` — Pydantic request/response shapes (local, like the `cache/` refresh models; the api.yaml wire-contract addition so Backend-Service generates a structurally identical type is a separate, coordinated wxyc-shared commit).
- `artists/genre_aggregation.py` — the deterministic ranking (`rank_counts`, `build_aggregation`) plus the cache-first / API-fallback orchestration (`resolve_artist_genres`).
- `artists/router.py` — the FastAPI handler (shared bulk envelope via `parse_bulk_body`; sequential per-artist processing to inherit the shared Discogs limiter's pacing without the intra-request fan-out that starves live-lookup traffic — the LML#370/#372 lesson).

## Cache Refresh Endpoint

`POST /api/v1/cache/refresh-for-identities` warms LML's Discogs cache for a batch of `entity.release_identity.id` values. Source-agnostic by design (LML#525) — Backend hands LML the canonical identity IDs and lets LML do the source-to-external-id mapping. Used by Backend-Service's rotation-artist-backfill cron (WXYC/Backend-Service#1381) so BS no longer needs to hold Discogs IDs directly (those are unstable across Discogs reshuffles).

Request: `{"identity_ids": [42, 99, 12345]}`. Max 50 ids per request — over the cap returns 400. Empty list returns 422. Duplicates are allowed; each runs independently.

Behavior per id:
1. Read `entity.release_identity` once for the whole batch (one PG round trip, not N).
2. For each `(source, external_id)` pair on the row, dispatch to the per-source release-cache refresh. Today only `discogs_release` is wired; `discogs_master`, `musicbrainz_release`, `spotify_album`, `apple_music_album`, and `bandcamp` return `release_outcome = "not_implemented"`.
3. For each refreshed Discogs release, walk `release.artists[*].artist_id` (skipping `artist_id <= 0` — the LML#525 sentinel guard extending the LML#518 / LML#546 caller-validates audit posture) and refresh the per-artist cache.
4. Roll up per-source outcomes into the per-id `status`: `warmed | not_found | not_implemented | error`. `not_found` covers "no row in `entity.release_identity`" (no 500); `warmed` requires at least one source `release_outcome == "success"`; `error` is reserved for "no useful release-cache work happened" so it is the only retry signal. Tombstones (LML#510) count as `success` — the cache state is current.

Response carries per-id results only — no top-level counters. Callers derive them via `Counter(r.status for r in results)`, matching the `BulkLookupResultItem` precedent.

The dispatcher loop mirrors `/api/v1/lookup/bulk` (`lookup/router.py`): `asyncio.gather` under a bounded semaphore (`LML_BULK_MAX_CONCURRENT`, default 10, shared with the lookup endpoint), each item additionally holding one LML#716 process-global bulk permit (`LML_BULK_GLOBAL_MAX_CONCURRENT` — the cross-request budget shared with `/lookup/bulk` and identity bulk-resolve; see `docs/env-vars.md`), per-item `try/except` so one identity's failure cannot poison siblings, and a `watch_disconnect` sentinel race so a client abort cancels the gather and frees downstream Discogs rate-limit / semaphore permits. Per-replica Discogs concurrency / rate-limit gates from `discogs/ratelimit.py` apply for free through `DiscogsService.get_release` / `get_artist_details`.

Implementation lives in `cache/`:
- `cache/models.py` — Pydantic shapes (the api.yaml entry generates structurally identical types on the Backend-Service side).
- `cache/dispatch.py` — per-identity orchestration: the per-source dispatch table, the walk-to-artists step with the `> 0` sentinel guard, and the per-id `status` rollup (all pure-logic, unit-tested in `tests/unit/test_cache_dispatch.py`).
- `cache/router.py` — the FastAPI handler, batch concurrency primitives shared with `lookup/router.py` via `core/bulk_concurrency.py`.
- `entity/store.py:get_release_identity_provenance_bulk` — the bulk PG read returning `{identity_id: [(source, external_id), ...]}`.

Sentry spans: `cache.refresh.batch` around the gather, `cache.refresh.identity` per identity, `cache.refresh.release` per source leg, `cache.refresh.artist` per walk target. Numeric attributes (`identity_id`, `external_id`) are set on the span at open, never via late binding.

## Streaming Check Endpoint

`POST /api/v1/streaming-check` checks whether an album is available on streaming platforms. Used by tubafrenzy and Backend-Service to set the `on_streaming` flag when a new release is added to the library.

Request: `{"artist": "Stereolab", "title": "Aluminum Tunes"}`

Response includes `on_streaming` (true/false/null) and per-service match details with URLs and confidence scores. Checks run concurrently across Spotify, Deezer, Apple Music, and Bandcamp. The endpoint is stateless -- it does not cache results.

Requires `SPOTIFY_CLIENT_ID` and `SPOTIFY_CLIENT_SECRET` for Spotify checks. Other services (Deezer, Apple Music, Bandcamp) need no auth. If Spotify credentials are not set, Spotify checks are skipped.

Telemetry (LML#639): every request emits a `streaming_check_completed` PostHog summary event (when both `ENABLE_TELEMETRY` is on and `POSTHOG_API_KEY` is set; otherwise the emit is a no-op) carrying per-request total/step timing, an `outcome` (`success`/`error`) + `error_type`, and a per-service verdict (`verdict_<service>`, plus `on_streaming`, `match_count`, `errored_count`, `errored_sources`). The shared telemetry helper also emits one per-step event (`streaming_check_availability`) per request alongside the summary. Both outcomes share one schema. On success each `verdict_<service>` is `matched`/`errored`/`absent` derived from the response — note partial (per-service) failures come back as a 200 with `on_streaming=null` and the failing services in `errored_sources`/`verdict_<service>=errored` (LML#376). On a total failure (the 500 path, when `check_streaming_availability` itself raises) the event is still emitted with `outcome=error`, `error_type` set, and every verdict `unknown`. The `cache` and `api_calls` fields are emitted with a stable, all-zero shape — the path is application-cache-free and the clients record no API calls yet; real values land in [LML#641](https://github.com/WXYC/library-metadata-lookup/issues/641). The emit is best-effort and wrapped in its own swallow (a telemetry failure logs at WARNING and never fails the check nor masks the 500, since this endpoint is on the synchronous flowsheet-add path).
