# Architecture

## Lookup Flow

Step labels match the `_step_*` spine in `lookup/orchestrator.py` (`perform_lookup`); each step function's docstring declares the `LookupState` fields it reads and writes.

- **Steps 1+2 — Artist Correction + Album Resolution** (`_step_prepare_request`): Fuzzy-match the artist against the library catalog to fix typos; if a song is provided without a usable album (missing, equal to the artist name, or a self-titled placeholder such as "S/T" or "Epon." — `needs_album_resolution` in `lookup/matching.py`, LML#1392), query Discogs for album names. The eponymous forms are request-side only (`REQUEST_SELF_TITLED_PLACEHOLDERS`): the catalog-side `SELF_TITLED_PATTERNS` excludes them so a catalog row whose real title is "Eponymous" (R.E.M.) keeps validating and binding artwork against its own title. Before a placeholder takes step 2, a literal-title guard (`runs_album_resolution` in `lookup/strategies/artist_plus_album.py`) reads the titles of the (corrected) artist's own rows, with no Discogs I/O (`artist_spellings`, then `LibraryDB.titles_by_artist`, no window, LML#1421; an artist with no shelf of its own reads the 50-row artist-only search window instead): if a row's title equals the typed album under ARTIST_PLUS_ALBUM's album fold, or the artist has a row whose title is itself a self-titled placeholder ("s/t"), the typed album names a shelved record, step 2 is skipped, and the request behaves exactly as it did before LML#1392. The guard is needed because ARTIST_PLUS_ALBUM ranks a row whose title contains the song *above* `albums[0]` (which is only the tiebreak), and Backend-Service enrichment types catalog titles verbatim: once step 2 adds Discogs albums, an R.E.M. "Eponymous" / "Driver 8" play would lead with the shelved "Driver 8" 12-inch, and an Astral Social Club "s/t" / "Metal Guru" play with its "Metal guru" 7-inch. Only a placeholder that names nothing on the artist's shelf (e.g. "Epon." for an artist whose self-titled record is catalogued under its own name) takes step 2. It is kept in that album list on every outcome; on a Discogs hit it is followed by Discogs albums titled with the artist's name (the literal self-titled release) and then the rest in Discogs order (`order_self_titled_albums`). A typed album equal to the artist's name has the same guard (LML#1412). Backend-Service enrichment sends a self-titled record's catalog title, which is the artist's name, verbatim. The guard reads the rows the album lane would keep for the typed album (`lookup/album_rows.py::album_rows`, which reads the artist's own rows first, LML#1421), and when they include the artist's self-titled record, a row titled the name and filed under it, step 2 is skipped. Another artist's row does not count, even when the artist filter's prefix match admits it (Arlo Guthrie's *Arlo* for the band Arlo), and neither does a literal "S/T" row, which Backend sends as a placeholder. The album filter always keeps the record, and a sort tiebreak ranks it above siblings that also contain the name ("A arte de Caetano Veloso"), with or without a song. A row titled after the song still ranks first, and step 3b can still narrow the rows to a sibling the song is confirmed on, as for any typed album. The tiebreak is constant for every request whose typed album is not the artist's name. Also as for any typed album, `song_not_found` stays false when step 2 is skipped. A song LML cannot confirm therefore no longer turns the answer into a `fallback` with a "not found" `context_message`, and a song shelved only on a compilation no longer reaches TRACK_ON_COMPILATION. The self-titled record comes back `direct`, which Backend-Service's track-context trust gate (`lmlTrackContextTrust`) accepts. So for a play linked to that record, its enrichment persists the record's own album-level metadata, where on `main` it persisted nothing (`fallback`) or the compilation's cover. Before LML#1412, step 2 replaced the typed album with Discogs' song-to-album answer, so a compilation carrying the song led, and when Discogs did not list the self-titled release it was dropped (in production on 2026-10-02, Caetano Veloso / "Tropicália" / "Caetano Veloso" led with *A arte de Caetano Veloso* and omitted the 1968 record). Until LML#1421 the guard read the lane's 50-row search window instead, which for 16 common-word names (Can, God, Spirit, The Band and twelve more) never reached the record, so step 2 ran for them. The artist correction runs before album resolution (serialized so the LML#866 gate below can read the corrected `parsed.library_artist`). Step-2 tracklist validation runs with bounded concurrency (the LML#536 `_chunked_gather` pattern, minus its accumulator early-exit — the caller post-filters these candidates by artist, so truncating the raw validated list would starve the artist's own album behind leading compilations) and is gated library-first (LML#866): validation is skipped entirely when the corrected-or-typed artist has no library rows, so a non-library artist+track request does one Discogs search and zero tracklist fetches — behavior-preserving because these album names feed only ARTIST_PLUS_ALBUM, which re-filters every album-fed hit to the query artist. **Step 2's Discogs pass is additionally bounded by the spine deadline** (`lookup/spine_deadline.py`, LML#865): `resolve_albums_for_track` runs under `run_within_spine_deadline`, so a step-2 leg that would exceed the caller budget (header-gated) or the universal `LML_SEARCH_HARD_TIMEOUT_MS` ceiling is cancelled — freeing the Discogs semaphore like the step-3 per-strategy `wait_for` — and `perform_lookup` returns the honest empty timed-out response (`song_not_found=true`, `timeout=true`) instead of grinding. Before LML#865 both deadlines wrapped only step 3, so a non-library artist+song request could run 60s+ in step 2 without ever tripping the cap. Step 2's artist-filtered track search is also recorded into a request-scoped `TrackCandidateMemo` (LML#867, `lookup/candidate_memo.py`) — the raw candidate releases plus their validation verdicts, keyed by `(track, artist)` — created once in `_step_prepare_request` and threaded to the search pipeline; see the candidate carry-through note below.
- **Step 3 — Search Pipeline** (`_step_search_pipeline`): Execute strategies in order until results are found (see below). The spine deadline is **spine-level, not step-3-scoped**: step 3's clock is re-based to the spine start via `execute_search_pipeline(pipeline_start_offset_ms=spine_deadline.elapsed_ms())`, so the hard cap and caller budget bound step 2 + step 3 together (a step-2-heavy request that already spent the budget short-circuits step 3 on its first iteration).
- **Comprehensive Multi-Location Union** (`lookup/location_union.py`, LML#1022; folded transparently into `results` per the location-union-transparent-results plan, superseding the original separate-field design): gated on a song present + the server-side `LML_LOCATION_UNION_ENABLED` kill switch (`should_run_location_union`) + the caller not being low-priority (`not is_discogs_low_priority()`, checked at the task-creation site in `lookup/orchestrator.py` — BS enrichment, the CDC firehose, and backfills are excluded there, not via any request field). No per-request opt-in: this is the default posture for every interactive, song-bearing lookup. When gated on, `perform_lookup` launches `resolve_track_shelf_locations` as a concurrent `asyncio` task right after `parsed` is built — racing step 3, not serialized after it — so the probe's cost hides under the whole spine's latency, not just step 3's. It issues a single indexed btree probe against `lml_cache.compilation_track_location` (the LML#1019 recall index) on the normalized `(track_artist, track_title)` key — **no live Discogs call on this path** — ranks the candidates credit-tier (`primary` > `featured` > `extra`) → title-ratio (computed on-the-fly against the typed query title) → `library_id`, and joins each row's bare `library_id` back to a displayable shelf `LibraryItem` via `LibraryDB.get_items_by_ids` (retained on the returned `ResolvedLocation`, not discarded). After `_step_external_cache_fallback` (step 7) builds the response's `result_items`, `build_location_result_items` narrows the ranked list to *every other* location by excluding whichever library ids are already present in the response (`primary_library_ids_from_results`) — so the union fires **even when the artist's own release already matched** (Case A), not only when the pipeline came up empty (Case B) — converts survivors into ordinary `LookupResultItem`s (library item + precomputed-art `DiscogsMatchResult` + a `matched_via` `TrackMatchHint` tagged `source: discogs_release`), and appends them to `results`. Every degraded/shed early return threads the same task through `_build_degraded_response`, which awaits it with a ~250ms bound (`asyncio.wait_for`) rather than the happy path's unbounded await, so a stalled probe never holds up an already-degraded response. Once anything is folded in, `_reconcile_post_fold_signals` recomputes `found_on_compilation`/`song_not_found`/`search_type`/`context_message`/`external_source` from the final list so every signal a consumer or dashboard sees agrees with what's actually in `results` — a no-op when nothing was folded. There is no separate response field and no `LibraryLocation` schema; a folded location is indistinguishable on the wire from a `SONG_AS_TRACK` primary match except by its `matched_via[0].source`. See `docs/env-vars.md` for the kill switch and [WXYC/library-metadata-lookup#1022](https://github.com/WXYC/library-metadata-lookup/issues/1022).
- **Step 3a — Library-Miss Discogs Probe** (`_step_library_miss_probe`, LML#583): Probe Discogs directly (`lookup/strategies/library_miss.py`) on an artist+album request when the pipeline produced no library rows — or, on the **songless** lane, only rows that cannot clear the LML#477 serve floor (`fallback_rows_block_serving`, LML#1319: `_filter_results_by_album_match` admits any token subset via `token_set_ratio`, so a sibling or truncated title fills `library_results`, suppresses this probe, and then collapses to the `release_id=0` sentinel — match enough to block, not match enough to serve). A confident match is synthesized as a row-less `LibraryItem(id=0)` pair. The two lanes differ in what happens next: on a genuine library miss the pair is written straight to `items_with_artwork`, bypassing steps 3b and 4; on the serve-blocked lane `library_results` is **kept** (its rows carry the call numbers, and the gap class includes same-record title truncation), so 3c and 4 run over the rows normally and step 4 prepends the parked pair (`LookupState.serve_blocked_probe_pair`) in front of them — the probe's release id/artwork lead, every shelved row follows. That lane also probes **cache-only** (`allow_api_escalation=False`): the two LML#784 escalations below are skipped, since a probe miss there just keeps the rows and serves the sentinel as before. `lookup.outcome` reports the lanes separately (`library_miss_*` vs `serve_blocked_fallback_*`), so the original slices keep meaning "the library returned nothing". Skipped on `/lookup/bulk` (LML#671). Three LML#784 recall behaviors: a query-side self-titled placeholder ("S/T") swaps to the artist name before searching; when a cache-served candidate set all floor-fails, the search re-issues once with `skip_pg=True` (the fallthrough seam treats any non-empty `pg_read` as terminal, so without the retry a PG candidate set that scores under the floor would mask an API arm that resolves the pair); and when the floor still cleared nothing, compilation-credited candidates get a dual-axis second look against embedded-title-segment and tracklist-credit evidence (`lookup/strategies/va_rescue.py`).
- **Step 3b — Track Validation** (`_step_validate_tracks`): Sequences the gate (both `song`/`artist` typed, plus either real non-rowless results **or** — since LML#1184 — a compilation hit whose only rows are row-less carrying a non-empty `artist_fallback_results` stash; the compilation tier validates the stash, not `library_results`, so it does not need a real row in the latter to run) and delegates the promotion cascade to `apply_track_validation_cascade()` in `lookup/validation.py` (LML#750). If fallback returned all artist albums, validate each against Discogs tracklists (`filter_results_by_track_validation()`, same module) — bounded via `_chunked_gather` (LML#808): probes dispatch `MAX_SEARCH_RESULTS` at a time under the shared `LML_SEARCH_MAX_API_CALLS` cap, and a Discogs breaker shed stops further chunks from dispatching. While the song is still unconfirmed and no compilation was found, this validation widens past `_step_search_pipeline`'s `limit_results` truncation to the full pre-truncation candidate set (`LookupState.unranked_fallback_candidates`, LML#808) — safe now that the fan-out is bounded — so a high-rowid in-library album the artist-only fallback would otherwise truncate away can still be confirmed. When validation can't confirm any candidate AND we're showing artist-fallback results, `find_library_albums_with_cached_track()` (same module) consults the local PG cache directly ("releases by this artist whose tracklist contains this song") and promotes any matching library album over the unrelated fallback. Cache-only — never falls back to the API. This rescue is what closes the recurring "artist+track lookup returns N unrelated same-artist albums" class (LML#267/#560/#801, e.g. Milkman / Aphex Twin → *Richard D. James Album*); its recall hinges on the cache probe (`search_releases_by_track`) not pruning the artist's own release before the artist filter runs — the CTE bug LML#802 fixed. When the track's release is absent from the cache, the widened per-result validation above is what can still rescue it (LML#808) rather than this cache-only rescue. Under an open Discogs saturation breaker the shed keeps the unvalidated fallback rows so the rescue does not run (transient; see the breaker note below). When nothing above confirms anything, `_filter_results_by_song_as_album_title()` (same module) promotes a surviving row whose title matches the typed song — the LML#717 "user typed an album title as the song field" recovery. On the compilation tier, when validation confirms nothing **and** the matched compilation is row-less (WXYC doesn't shelve it), the stashed artist rows are appended behind it, capped at `MAX_SEARCH_RESULTS`, and the cascade returns `found_on_compilation=False` / `song_not_found=True` — the one place this cascade overturns the search pipeline's compilation verdict, because the only row carrying the track is one nobody can pull off the shelf (LML#1184). `search_type` is re-derived to `fallback` alongside it: consumers gate on that field *alone* (Backend-Service's `isTrustedLmlTrackContextMatch` accepts `direct|compilation` and reads neither flag), so leaving it at `compilation` would invite BS to trust rows the cascade just failed to confirm. The probe input on this lane is bounded to `MAX_SEARCH_RESULTS` — the shape reached step 3b not at all before the fix, so an un-truncated fan-out would be new live-Discogs load (15-24 calls) paid on every firing; the pre-existing shelved-comp lane keeps the full stash. Before that fix the stash was dropped outright and the response carried a `Found "<song>" on:` header over rows the caller never received.
- **Step 3c — Streaming Status** (`_step_populate_streaming_status`): Populate each result's `on_streaming` flag from the library DB.
- **Step 4 — Artwork Fetch** (`_step_fetch_artwork`): Fetch album art from Discogs for each result (`fetch_artwork_for_items()` in `lookup/artwork.py`)
- **Step 4b — Metadata Enrichment** (`_step_enrich_metadata`): Populate `release_year`, `artist_bio`, `wikipedia_url`, streaming URLs. Release/artist details are fetched only for `items_with_artwork[0]` — BS/iOS only consume the top-1 result, so paying N Discogs round-trips for non-top-1 items is waste. Streaming-URL fallbacks stay per-result. Gating is *positional*: if the top-1 entry has `artwork=None`, no item carries release-year/bio/wiki, even if items further down have artwork. The lookup pipeline guarantees the strongest match is in position 0, so this is fine in practice. See `enrich_artwork_results()` in `lookup/enrichment/__init__.py`. **Wikipedia-preferred `artist_bio` (LML#513/#1192, `docs/plans/lml-1192-wikipedia-artist-bio.md`):** behind `LML_BIO_PREFER_WIKIPEDIA` (default off, inert without `LML_WIKIPEDIA_SLUG_MATCH` also on — see `docs/env-vars.md`), the coordinator calls `lookup.enrichment.wikipedia_bio.resolve_served_bio` once (top-1 only) right after the Discogs prefetch, which can swap `artist_bio` from the Discogs profile to a cached Wikipedia lead-paragraph extract (`lml_cache.artist_wikipedia_bio`). `wikipedia_url` CAN change from the caller's own live Phase-A pick: since LML#1192 review round 5, the cache read (`entity/artist_wikipedia_bio.py`) is keyed on `discogs_artist_id` alone and serves whichever `wikipedia_url` the stored row carries — which may be a better, fetch-validated URL a background warm wrote, distinct from the caller's unvalidated sync pick. What Phase B does still guarantee is that the served `artist_bio`/`wikipedia_url` pair always describe the SAME page, because both are read off the one cache row together, never compared against or filtered by the caller's own pick. The LML#504 split gate below still nulls both together exactly as before. **Accepted semantic shift**: `profile_tokens` keeps parsing the raw Discogs profile unconditionally (never the Wikipedia extract), so a response can legitimately carry Wikipedia prose in `artist_bio` and Discogs-profile tokens in `profile_tokens` simultaneously — two different source texts, not two renderings of one bio (see `lookup/enrichment/item.py`'s comment above its `profile_tokens` assignment). A cache miss falls back to the Discogs profile and, when `warm_cache` is set, schedules a bounded background fetch (`lookup/enrichment/wikipedia_warm.py`) rather than fetching inline — Wikipedia is never on the request path.
- **Step 5 — Context Message** (`build_context_message`): Generate context string for the caller
- **Step 6 — Identity Resolution** (`_step_resolve_result_identities`): Resolve external identifiers for each result's artist via the entity store.
- **Step 7 — External-Cache Fallback** (`_step_external_cache_fallback`): Opt-in (`include_external_caches`) mojibake recovery — see the dedicated External-Cache Fallback section below. The artist>album>song dispatch precedence and per-branch candidate shaping live in `search_external_fallback()` (`lookup/external_search.py`, LML#750); this step sequences the gate + telemetry and builds response rows via the shared `build_external_catalog_item()` sentinel constructor (same module).
- **Step 8 — Unbound Shelf Fallback** (`apply_shelf_fallback`, `lookup/shelf_fallback.py`, LML#1391/#1393): the true last step of the spine, called after the location-union fold has had its chance to populate `results` — not merely after Step 7. Additive and unbound: **a non-empty response keeps every row it has, in the same order, with `results[0]` never displaced; an empty response may gain the artist's shelf.** The one change to a non-empty response is the LML#1405 self-titled companion (see "Self-titled companion (LML#1405)" in the design notes below). When `result_items` is still empty, the response did not time out or get degraded by a search-leg shed (`state.timed_out` / `state.upstream_shed` — both set their flag and ride the normal return path rather than returning early, so both are checked here explicitly), the caller is not low-priority, the spine deadline is not spent, the typed `album` is non-empty, and the library artist has at least one shelved row of its own (read by artist through `lookup/artist_shelf.py`, LML#1406 — never by the prefix rung in `filter_results_by_artist`, which would list a Canibus row under "other albums by Can"), this returns the artist's shelf as **display-only** rows — `LookupResultItem(library_item=row.to_catalog_item())`, no `artwork` and hence no release id/artwork URL/year/Discogs URL/streaming links. `search_type` is forced to `fallback` (never `direct` — this matters for the album-only shape, where main reports `direct` with zero rows), `external_source` becomes `"library"`, and `context_message` reuses `lookup.matching.album_not_found_message()` (shared with `build_context_message`'s song-bearing branch) so the album-only shape gets the same wording, naming the artist as the listed rows spell it and the typed album verbatim. If the library query raises, the step logs a warning and leaves the empty response as it was. `song_not_found`/`found_on_compilation` are left exactly as the caller computed them. Rows are ordered song-in-title-first (case-insensitive) when a song was typed, then the rest in catalog order, capped at `MAX_SEARCH_RESULTS`; a cache-confirmed-song ordering tier was considered and dropped — the one cache-only primitive that could answer it (`find_library_albums_with_cached_track`, Step 3b's A4 rescue) already runs against these same rows earlier in the pipeline, and a confirmed hit there promotes the row into a non-empty `library_results` before this step can ever run, so re-asking the same cache here would be redundant. Supersedes the larger, closed PR #1396, which repeatedly changed what Backend-Service binds (reordering/replacing/re-binding rows that a `direct`/`compilation` response already carried) and was rejected across five review rounds.

### `LookupRequest` opt-in flags

- `extended: bool` (default `false`) — When true, the top-1 result's `artwork` block carries additional fields LML already loads during enrichment but normally discards: `discogs_artist_id`, `tracklist`, `genres`, `styles`, `label`, `full_release_date`, `artist_image_url`, `profile_tokens`, `writer_credits`. Bio parsing uses `CachedOnlyResolver` (cache-only deep parse) when `DATABASE_URL_DISCOGS` is set; falls back to sync `parse()` otherwise. Designed to let Backend-Service collapse `/proxy/metadata/album` to one LML call, eliminating the follow-up `/discogs/release/{id}` and `/discogs/artist/{id}` round-trips.
  - `writer_credits` (LML#699, for BMI performance-list reporting) is the songwriter/composer subset of the resolved release's already-fetched credits, classified by the writer-role heuristic in `discogs/writer_roles.py` (strip `[qualifier]` → split on `,` → fold hyphen/space → match a fixed base set: `Written-By`, `Composed By`, `Music By`, `Lyrics By`, `Songwriter`, `Words By`; `Arranged By`/`Adapted By` excluded). The `[qualifier]` strip runs before the comma split so a bracket-internal comma (`Written-By [Words, Music]`) doesn't fragment the role. No new Discogs call. `provenance` resolves at two precisions: **track** — when the played `song` matches a tracklist position (`find_track_position` in `discogs/service.py`) and that track carries its own writer credits (the `release_track_artist` `extra=1` rows, read by `cache_service.get_release` into the internal `ReleaseMetadataResponse.track_writers` map, keyed by display position), the credit is scoped to the playcut and tagged `provenance: track` with `track_position`; this path is correct even on a compilation, so it deliberately bypasses the VA guard. **release** — otherwise it falls back to the writer-role subset of `top1_release.extra_artists` (the whole-release approximation), tagged `provenance: release` with `track_position: null`, and is omitted for compilations/Various-Artists (the release-level credit is meaningless per-track). Omitted when no writer resolves — never fabricated. Both precisions additionally require artist-identity verification (the LML#504 split gate's `is_artist_derived_eligible`, intersected with the album gate): a fuzzy album-title match to a *different* artist's release suppresses `writer_credits` entirely rather than leaking the wrong composers into a royalty-reporting payload. Surfacing it on `DiscogsMatchResult` lets it ride the existing `album_metadata` passthrough to Backend-Service, which populates a `flowsheet` composer column with artist-as-proxy fallback.
- `warm_cache: bool` (default `false`) — When true, schedules a fire-and-forget `asyncio.create_task` after the response is composed that runs the *deep* async parse (API-capable resolver) on the top-1 bio. Warms the PG cache for `[a…]`/`[r…]`/`[m…]` references so subsequent reads render richer. Bounded process-wide by `_WARM_CACHE_CONCURRENCY` (currently 4) to cap Discogs API amplification. Read-path callers leave this `false`; write-path callers (Backend-Service's `flowsheet-linkage.service.ts` on flowsheet-entry creation) set it `true`. Single-`/lookup` only: on `POST /api/v1/lookup/bulk` the flag is hard-pinned off per item (LML#742) — a truthy value is discarded with a warning log before the item reaches `perform_lookup`, matching the bulk route's `bandcamp` / `allow_release_resolution_fallback` fan-out pins; the offline warmer (#548) is the supported tier for bulk bio-cache population.

## Search Strategy Pipeline

The strategy seam (`Outcome` value type, `Strategy` Protocol, `_apply` write site, `execute_search_pipeline` runner) lives in `core/search.py`. Each concrete strategy is a `@dataclass(frozen=True)` class in `lookup/strategies/`, one module per strategy; the execute funcs that do the actual library/Discogs work are injected into each strategy at construction time and live in the same module as their strategy class (`SONG_AS_TRACK` and `SWAPPED_INTERPRETATION` over the shared kernel in `lookup/strategies/track_release_matching.py`; LML#722).

| Strategy | Trigger | Class | Execute func |
|---|---|---|---|
| `ARTIST_PLUS_ALBUM` | Has artist, album, or song | `lookup/strategies/artist_plus_album.py` | `search_library_with_fallback()` |
| `SWAPPED_INTERPRETATION` | No results + "X - Y" / "X, Y" / "X. Y" format | `lookup/strategies/swapped_interpretation.py` | `search_with_alternative_interpretation()` |
| `TRACK_ON_COMPILATION` | Song not found + artist + song (live comp discovery only when the location union is inactive — LML#1026, see below) | `lookup/strategies/track_on_compilation.py` | `search_compilations_for_track()` |
| `SONG_AS_ARTIST` | No results + song but no artist | `lookup/strategies/song_as_artist.py` | `search_song_as_artist()` |
| `SONG_AS_TRACK` | SONG_AS_ARTIST ran and returned empty (catalog-track-search §4.2) | `lookup/strategies/song_as_track.py` | `search_song_as_track()` |

Strategies never mutate `SearchState`; they return an `Outcome` and the runner applies it via `_apply`. This makes cancellation safety structural — a cancelled `attempt()` is a no-op against state by construction. Production wiring lives in `lookup.strategies.build_strategies`, called from `perform_lookup`.

**The recall index is authoritative for comp-track resolution on the union-active path (LML#1026).** When the location union is active (song present + `LML_LOCATION_UNION_ENABLED` + not a low-priority caller + a discogs-cache PG source wired), the orchestrator threads its concurrent `location_union_task` into `search_compilations_for_track`, whose `_consult_recall_index` (an `asyncio.shield`ed await, so a per-strategy budget cancellation can't kill the shared task) classifies the probe into a tri-state: an **index hit** (≥1 *renderable* location — a row whose shelf join produced a `LibraryItem`; stale-id rows don't count, or the track would vanish) makes the strategy return nothing at all — the fold supplies the shelf locations (leading the response when nothing else claims the track, trailing the primary when it does), step 3a's library-miss probe is skipped (`_task_resolved_with_renderable_locations`, so its rowless id-0 synthesis can't preempt the shelf row), and no keyword search, live probes, album-title fallback, or rowless carve runs. An **authoritative index miss** (the probe ran; nothing renderable) suppresses the Wave A/B probes and their per-release validates per the #271-locked "removed, not augmented" decision, while the co-located non-comp features (the keyword last-resort, the #319 album-title trio fallback, the #628 rowless non-library carry-through) still run. A **degraded probe** (PG failure, timeout — `CompilationTrackLocationProbeError` — or any rank/join error) restores the full legacy live pass: "union unavailable" is deliberately distinct from "index says no", the same invariant the task-creation gate enforces for the no-PG-source config case, so a discogs-cache outage costs the union, never comp-track recall. With no task at all (kill switch off, class-5 caller, no PG source), the legacy live pass runs byte-identically, which makes `LML_LOCATION_UNION_ENABLED=false` a complete rollback lever for the rework. Each verdict records a `location_union_index_hit`/`_miss`/`_degraded` cache-stats counter (see `docs/observability-rowless-flag.md`).

`SWAPPED_INTERPRETATION` is **Discogs-touching** (LML#622): once it identifies the artist side, it cross-references the *other* part as a track and narrows to the release(s) that actually contain it, rather than returning the artist's whole discography. The release→library matching reuses the same kernel as `SONG_AS_TRACK` (`_match_track_releases_to_library` in `lookup/strategies/track_release_matching.py` — Discogs track search → `search_album_fuzzy` → deferred tracklist validation, bounded by `_chunked_gather` + a `MAX_SEARCH_RESULTS` early-exit). SWAPPED passes both `artist=` (filters the Discogs search) and `require_artist=` (re-filters the matched library rows to the identified artist), so the narrowing stays the artist's own release(s) and the keyword-supplement fallback can't leak another artist's release in; VA compilations are SONG_AS_TRACK's domain (it runs with `artist=None`). When narrowing fires it emits a `matched_via` map (an `Outcome.track_match`, like `SONG_AS_TRACK`); when nothing cross-references — or no `discogs_service` is wired — it returns the artist-filtered result via `Outcome.found` as before. Of the strategies, only `ARTIST_PLUS_ALBUM` is library-only.

### Candidate carry-through (LML#867)

For an artist+song lookup, step 2 (`resolve_albums_for_track` → `lookup_releases_by_track`) and `TRACK_ON_COMPILATION`'s Wave A (`search_releases_by_track(song, artist)`) used to issue the **same** artist-filtered Discogs track search twice with slightly different params (`per_page` 10 vs 20), so neither the L1 nor the PG cache served the second from the first — pure duplication on the request's critical path. The request-scoped `TrackCandidateMemo` (`lookup/candidate_memo.py`) closes that gap: step 2 records its raw candidate releases and per-candidate verdicts (keyed by `(track, artist)`; recorded even for a non-library artist that skipped validation, and even for an empty result), and `search_compilations_for_track` reuses that set as its Wave A seed on a `(song_search, artist_for_probes)` hit — so a canonical-artist swap or a remix-augmented title, which genuinely change the normalized query, miss the memo and re-search. Reuse is gated on the seed's **search breadth**: step 2 now issues its search at the shared `WAVE_A_SEARCH_LIMIT` (`lookup/matching.py`) — the same page a fresh Wave A uses — and the consumer reuses the seed only when its recorded `search_limit` is at least that wide. A seed fetched at a narrower page can be a strict subset even when it came back short of that page — the keyword supplement inside `search_releases_by_track` scales its own page with the limit, so a wider search yields strictly more — so a too-narrow seed is *not* reused; the strategy falls through to the fresh wider gather. Aligning the two page sizes makes the common-case reuse a provable superset, so the memo suppresses the duplicate search without narrowing recall; the gate fails safe — if the two page sizes ever diverge, reuse simply doesn't fire (a re-search), never a silent narrowing. The **wider** Wave B probe (`artist_as_keyword=True` → `q=` keyword + `format=Compilation`) is the recall-critical arm that catches VA compilations the `artist=` filter misses; it is preserved and skipped **only** when the reused seed already holds a true-V/A compilation — exactly the case `merge_wave_b_compilations` discards Wave B (both sides call the shared `has_va_compilation` predicate so the skip can't drift from the merge), so the skip is provably non-narrowing. An empty or non-V/A seed still fires the wider search. The memo is request-scoped only — created fresh per `perform_lookup`, never a cross-request cache tier.

## Discogs Cache (Optional)

The service supports an optional PostgreSQL cache for Discogs data:

1. Query local PostgreSQL cache first
2. On cache miss, query Discogs API
3. Write API results back to cache
4. Gracefully degrade to API-only if cache unavailable

Set `DATABASE_URL_DISCOGS` to enable. The cache schema is defined in [WXYC/discogs-etl](https://github.com/WXYC/discogs-etl).

## Discogs cache fallthrough seam (`discogs/fallthrough.py`)

The 3-tier read-through (in-memory L1 via `@async_cached` → PostgreSQL L2 → Discogs API L3 + optional write-back) is concentrated in `discogs/fallthrough.py:fallthrough()`. Each cache-bearing method in `discogs/service.py` calls the seam with its own `pg_read` / `api_fetch` / `pg_write` closures and, where relevant, the negative-cache hooks. The L1 `@async_cached(<CACHE>)` decorator stays per-method — it owns a separate, already-deep concern (per-type TTL, cache-key normalization, the `should_skip_cache()` bypass).

### Per-method write-back policy

The drift the deepening (#393) removes — every `pg_write=None` call site documents *why* it's read-only:

| Method | `pg_write` | Why |
|---|---|---|
| `get_release` | `cache_service.write_release` | Full read-through. `ReleaseMetadataResponse` maps cleanly to the cache's normalized schema. |
| `get_artist_details` | `cache_service.write_artist_details` | Full read-through. Same shape. |
| `search_releases_by_track` | `None` | Read-only by design — the PG side queries the normalized `release_track` index populated by the ETL pipeline. Writing arbitrary Discogs `/database/search` hits back wouldn't fit that schema. Negative-cache write still fires via `pg_negative_record`. |
| `search` | `None` | Read-only by design — same shape. |
| `validate_track_on_release` | `None` | Read-only by design. Tri-state PG read short-circuits when the cache has an answer; on miss, the API path calls `get_release` which writes back to the `release` cache via its own seam call. The validation verdict itself isn't separately cached. |

When adding a new cache-bearing method, pass an explicit `pg_write=` argument (or `pg_write=None` with a one-line comment explaining why). The seam's signature makes the policy decision visible at the call site.

### Cool-down on cache outage (LML#324)

When a `pg_read` raises one of a narrow set of "DB unreachable" exceptions — `asyncpg.exceptions.PostgresConnectionError`, `CannotConnectNowError`, `InterfaceError`, `UndefinedTableError` (the dedup-swap window), or the local `CacheUnavailableError` — the seam arms a process-wide cool-down for `_COOL_DOWN_SECONDS` (default 30s). While active, `pg_read` is short-circuited and the seam jumps straight to the API leg. `asyncio.CancelledError` propagates; everything else (programming errors, `asyncio.TimeoutError`) falls through to the API without arming.

The arming exception set lives in `_ARMING_EXCEPTIONS` in `discogs/fallthrough.py` and is pinned by tests in `tests/unit/test_fallthrough.py` so a future asyncpg release adding new exception classes can't silently widen the arming criteria.

Cool-down arm projects `data.cache_fallback_fired = {reason, error_class, cool_down_seconds}` onto the active Sentry transaction, matching the pattern used by `_log_album_title_fallback` in `lookup/strategies/track_on_compilation.py`. Queryable in the Sentry trace explorer to track outage incidents.

### Search-arm `statement_timeout` bound (LML#804/#815)

Distinct from both the cache-outage cool-down above and the Discogs breaker below: this bounds the **server-side runtime of every trigram search arm** on the discogs-cache pool. LML#804 bounded the two incident arms (`DiscogsCacheService.search_releases`, `search_releases_by_track`); LML#815 generalized the bound so **all** trigram scans in `discogs/cache_service.py` inherit it — `search_artists_by_name` (the [#359](https://github.com/WXYC/library-metadata-lookup/issues/359) dominant chokepoint), `search_releases_by_title`, `search_tracks_by_title`, `autocomplete_tracks`, and `artist_trigram_candidates` (whose `SET LOCAL` previously pinned only the pg_trgm similarity floor). The acquire / `SET LOCAL` / degrade prologue is **not** hand-copied per arm: it lives in one shared helper, `DiscogsCacheService._bounded_fetch(query, *params, op, extra_set_local=None)`, so bounding a scan is a one-line `rows = await self._bounded_fetch(sql, ..., op="<arm>")` and any future arm inherits the ceiling. The helper runs the query inside a `SET LOCAL` transaction (the same pattern as `artist_trigram_candidates`' `_SET_PG_TRGM_FLOOR_SQL`, which it passes as `extra_set_local`) that pins **both** `statement_timeout` and `work_mem` — `async with self.pool.acquire() as conn, conn.transaction(): await conn.execute(self._search_bounds_sql); return await conn.fetch(...)`. Both values are settings-wired (`DISCOGS_SEARCH_STATEMENT_TIMEOUT_MS` default 10000, `DISCOGS_SEARCH_WORK_MEM` default 128MB — see [`env-vars.md`](env-vars.md)) and built once at construction into `self._search_bounds_sql`.

Why a server-side bound at all: `uvicorn` does not propagate client disconnects into handler coroutines (the LML#370/#372 autopsy), and an asyncpg query runs to completion once dispatched. Since LML#706 clamped the `/lookup` in-flight cap to the discogs-cache pool size, one long trigram query now occupies a scarce pool slot **and** an in-flight cap slot far past the point any caller is listening — the 2026-07-15/16 tail ran p95 5.1s / max 15.4s for 10+ hours after a discogs-cache connectivity blip, with a sampled request waiting 30.8s at the in-flight gate on a `caller_budget_ms: 1`. `statement_timeout` (10s, chosen **above** the largest legitimate caller budget so it only catches true runaways) makes the server cancel the query; asyncpg surfaces the cancel as `asyncpg.QueryCanceledError`.

Degrade boundary: `_bounded_fetch` catches `QueryCanceledError` and re-raises it as `CacheUnavailableError` (logged at WARNING with the arm's `op` name); each arm re-raises that `CacheUnavailableError` unchanged (a leading `except CacheUnavailableError: raise` ahead of its generic `except`, so a timeout is never double-wrapped). `CacheUnavailableError` is already in the fallthrough seam's `_ARMING_EXCEPTIONS`, and each arm's callers already handle it (the `/releases/resolve` + `/lookup` external-search seams catch it; `discogs/router.py`'s autocomplete returns an empty list), so a timed-out search degrades to **cache-only** exactly like an unreachable DB — never a 500 (the same "couldn't ask ≠ confirmed-empty" principle the breaker enforces; LML#755 R2-2). The `acquire`/`transaction` exit rolls back and returns the connection **before** the wrap, so both the pool slot and the in-flight cap slot are freed immediately.

`work_mem` (128MB, deliberately not 1GB — per-connection allocations multiply by pool size on the shared 8GB Railway instance) keeps the trigram bitmap heap scans from going lossy and recheck-storming under degraded latency (the 2026-05-25 pg_trgm finding: ~92s at the default 4MB vs ~12.7s with a large `work_mem`). `SET LOCAL` reverts at transaction end, so neither bound touches the write-serving pool session (the discogs-cache pool also serves api_fetch cache writes, `entity.identity` write-backs, and bulk-drain write-backs). Post-deploy prod EXPLAIN/p95 tuning of both knobs is the follow-up (LML#806).

### Discogs saturation circuit-breaker (LML#755)

Distinct from the cache-outage cool-down above (which shorts the *PG read* leg when the discogs-cache DB is unreachable), this breaker shorts the *live Discogs API* leg when the outbound Discogs path is **rate-saturated**. It lives in `discogs/breaker.py` (`DiscogsCircuitBreaker`) with a per-event-loop accessor in `discogs/ratelimit.py` (`get_discogs_breaker`), the same process-global-on-single-worker scope as the limiter/semaphore.

Root cause it addresses: the outbound limiter (`DISCOGS_RATE_LIMIT` 50/min + a 5-permit semaphore) bounds egress *rate*, but under sustained over-demand (the 2026-07-10 `flowsheet-metadata-backfill` flood) it converts excess load into unbounded per-request *latency* — live probes queue on the 50/min `rate_limiter.acquire()` and 429 backoff stacks to ~62s/call, so a lookup's wall time runs past Backend-Service's 35s client timeout → timeouts → worker saturation → 502s.

The breaker is checked in `discogs/service.py:_request_with_retry` **before** `rate_limiter.acquire()`, and re-checked at the top of each retry attempt (via the READ-ONLY, epoch-aware `should_shed_inflight` — **not** the state-mutating `allow_request`, which would promote the retrying request to the half-open trial under a fresh epoch and latch the breaker HALF_OPEN forever) so a request already past the entry gate sheds promptly if the breaker opens mid-flight, without consuming the trial slot. When shed it **raises `DiscogsBreakerOpenError`** — not a `None` return. This distinction is load-bearing (LML#755 review, FIX 1): a shed is **"couldn't ask, try later"**, which callers must treat as *unknown* — never a confirmed-empty verdict. A `None`/empty from a shed, laundered through the search layer's never-abort swallow, would otherwise poison the durable caches: a 7-day `lookup_negative` row, a `set_cached_release_id(release_id=None)` null-pin, an `@async_cached` memoized `[]`, or a definitive `validate_track_on_release` → `False` that drops a valid candidate. The shed propagates instead:
- `search_releases_by_track._api_fetch` returns `None` (its `except` catches the raise; it also returns `None` on retry-exhaustion / httpx-error via an explicit "any live call absent" flag), so `fallthrough` skips both the write-back and the negative-record.
- `resolve_release_for_track` raises at entry when the breaker is OPEN (all probes would shed anyway), so its L1 `@async_cached` wrapper never memoizes an empty and `_resolve_nonlibrary_release` never writes a null-pin.
- `get_release` re-raises `DiscogsBreakerOpenError` (a genuine 404/None or network/5xx still degrades to `None`), so `validate_track_on_release` propagates "unknown" instead of returning a definitive `False`.

The lookup **fast-fails to cache-only**: library + already-cached-Discogs results, live probe shed. Cache hits never reach this seam (they short-circuit in `fallthrough()` above), so only the live-probe tail is degraded; healthy cache-hit behavior is unchanged.

**Catch boundaries.** Because the shed *raises*, every caller that fans out to Discogs must degrade rather than 500:
- **Search pipeline (primary).** The strategy runner in `core/search.py` catches the shared `BreakerOpenError` base (LML#1118; was `DiscogsBreakerOpenError` until then) in its per-strategy try (alongside the `TimeoutError` catch) and converts it to `Outcome.empty()` — one boundary covers all breaker-fanning strategies (today: TRACK_ON_COMPILATION, SONG_AS_TRACK/SWAPPED, SONG_AS_ARTIST, all Discogs-backed), and a future breaker-guarded strategy is covered without a new catch. It `continue`s (not `break`s), so a later cache-only strategy still runs.
- **`perform_lookup` backstop.** The enrichment tail (library-miss probe, track validation, streaming status, artwork, enrichment) and identity resolution are wrapped in a `BreakerOpenError` catch (LML#1118; was `DiscogsBreakerOpenError`); a shed from any of them returns a cache-only `LookupResponse` (`_build_degraded_response` — library rows, no live enrichment, no context message). Defense in depth so any future raise path degrades to a 200, never a 500. Since LML#930 this same tail carries a **second, orthogonal shed — the caller *deadline*** (`lookup/tail_deadline.py::should_shed_tail`, checked between each tail step against the shared `SpineDeadline`): once the caller's budget (or the universal hard cap) is spent, the remaining live-Discogs/Apple tail is skipped and `_build_degraded_response` returns the same cache-only shape. The two sheds compose — saturation is "couldn't ask", the deadline is "ran out of time to ask" — and both now mark the wire response `degraded: true` with a `degraded_reason` (`upstream_unavailable` for a breaker shed, `deadline_exceeded` for a deadline shed; api.yaml, LML#943), distinct from a genuine no-match (`degraded: false`) and from a hard-cap `timeout: true`. The per-item Apple probe additionally clamps its fixed 4s `wait_for` to the remaining budget (`SpineDeadline.clamp_probe_timeout_s`), the single biggest in-tail overrun source. Telemetry: a deadline shed sets the filterable `lml.deadline.tail_shed_step` / `lml.deadline.tail_shed_limit` tags plus `lml.deadline.tail_remaining_ms` / `lml.deadline.tail_shed_ms` measurements, and every degraded response carries the `lml.degraded_reason` tag (LML#683 two-channel shape).
- **Step-3b track validation** (`lookup/validation.py:validate_one`) catches the shed *specifically* (narrower than its broad `except Exception`) and **keeps the library row unvalidated** rather than dropping it to `None` — a dropped row would launder the shed into `song_not_found` (a wrong 200). Genuine validation errors still drop the row.
- **Diagnostic Discogs routes** (`GET /discogs/release/{id}`, `/discogs/entity/release/{id}`) catch the shed and return **HTTP 503** (transient / retryable), not a raw 500.

State machine (fed **once per request** from `_request_with_retry`, on the terminal outcome — the counting unit is failed *requests*, not per-attempt 429s):
- **CLOSED** → requests flow. `DISCOGS_BREAKER_FAILURE_THRESHOLD` consecutive failed requests (default 4) or a response — 429 *or* success — reporting `X-Discogs-Ratelimit-Remaining` ≤ `DISCOGS_BREAKER_REMAINING_FLOOR` (default 3) trip it OPEN. A single healthy 2xx resets the run.
- **OPEN** → requests shed for `DISCOGS_BREAKER_COOLDOWN_SECONDS` (default 20s), then a single half-open trial is admitted (guarded by a monotonic epoch so a stale response can't decide it).
- **HALF_OPEN** → one trial in flight (concurrent callers still shed); a genuine 2xx with a healthy remaining CLOSES the breaker, a 429 or still-exhausted remaining re-OPENS it, a 5xx is neutral for the *decision* (never closes — a Discogs upstream error is not a rate-limit signal) but IS resolved: like an aborted trial, it re-OPENS for a fresh cool-down so the next admitted trial actually decides (LML#791), rather than leaving the slot occupied with nothing in flight. A trial that dies without any terminal outcome — `httpx.RequestError`, cancellation mid-request or mid-retry-sleep, an unexpected raise — is **inconclusive**: `_request_with_retry`'s admitted body is wrapped in `try/finally`, and any exit without a terminal `record_*` reports `record_aborted`, which re-OPENS for a fresh cool-down → fresh trial (LML#787; the 2026-07-13 incident latched HALF_OPEN for ~8h because these exits recorded nothing and HALF_OPEN sheds every other caller). Belt-and-suspenders: a HALF_OPEN slot occupied past `max(cooldown × 20, 60s)` (400s at the default 20s — sized above the ~360s worst-case legitimate full-backoff trial; the 60s floor keeps the watchdog alive under a zero cool-down config) is presumed stranded by an `allow_request` watchdog and the breaker re-OPENs, catching the residual shape neither a resolved 5xx nor `record_aborted` can see: a trial coroutine lost without its `finally` running.

Every shed increments `discogs_breaker_open_shed` on the per-request `cache_stats` dict — the same #683 `cache.*` counter surface (`cache.discogs_breaker_open_shed` in PostHog, `lml.cache.discogs_breaker_open_shed` on the Sentry transaction, seeded to 0 in `_LML_CACHE_STATS_EXTRA_KEYS`) the row-less flag degradation alerts use, so breaker-open time is alertable. Env-var reference in [`env-vars.md`](env-vars.md).

**Logging & alerting (LML#805).** State *transitions* log once each on the `discogs.breaker` logger, carrying trip context: `CLOSED->OPEN` / `HALF_OPEN->OPEN` at `warning` with the consecutive-failure count, epoch, and cool-down; `OPEN->HALF_OPEN` at `info` (a routine recovery probe); `HALF_OPEN->CLOSED` at `warning` on recovery; plus the LML#787 watchdog and aborted-trial re-opens at `warning`. Per-request sheds log at **`debug`** (`discogs/service.py:_record_breaker_shed`), and the three `/api/v1/lookup`-path callers that catch `DiscogsBreakerOpenError` (`search_releases_by_track`, `get_artist_details`, `search`) treat the shed as expected degrade — none re-logs it at `error`. This matters because a sustained OPEN episode sheds every live probe: before #805 the two `logger.error("Discogs search failed: …")` catch-alls in `discogs/service.py` (and the `get_artist_details` catch) swallowed the propagated shed at ERROR, and the Sentry logging integration (`event_level=ERROR`) turned one OPEN state into tens of thousands of discrete error events (the Jul 11–14 flood: 32,520 events in 4 days). **Full coverage (LML#814).** `get_release` deliberately **re-raises** the shed (the #755 FIX-1 guard, so `validate_track_on_release` can't turn a shed into a definitive `False`), which exposes two cross-module callers on the cache-warmer (`cache/dispatch.py::_refresh_discogs_release`, `POST /api/v1/cache/refresh-for-identities` — the BS-backfill-driven path) and releases-resolve (`release/discogs_resolver.py::resolve_discogs_release`, `POST /api/v1/releases/resolve`) paths; before #814 both caught that propagated shed via a broad `except Exception` and re-logged it at ERROR, so a sustained OPEN episode during a Backend-Service backfill flooded Sentry from those two endpoints too. #814 adds an `except DiscogsBreakerOpenError` ahead of the generic handler at each seam: the shed logs at **`debug`** and degrades to a **retriable** outcome that persists nothing negative — the cache-warmer records the `error` outcome tagged `message="DiscogsBreakerOpenError"` (kept on the existing wire value rather than a new `skipped` to stay in lockstep with the api.yaml `CacheRefreshSourceOutcome` enum; it rolls up to the retriable per-id `error` so the cron retries), and the resolver returns `canonical=None` with a transient rate-limited warning (which skips the orchestrator's `canonical is not None`-gated identity write-back). Every cross-module `DiscogsBreakerOpenError` seam is now demoted; the remaining `logger.warning` sibling callers (`search_releases_by_album_title`, `get_master`, `get_label_image`, `lookup/artwork.py`, `lookup/strategies/va_rescue.py`, `lookup/rowless.py`) are breadcrumb-only (WARNING is not promoted to a Sentry event under `event_level=ERROR`). **Operators: alert on the breaker's transition log lines or the `lml.cache.discogs_breaker_open_shed` counter — never on a per-request "Discogs search failed" error group** (which no longer exists for sheds; a `Discogs search failed` ERROR now means a genuine non-breaker failure).

### Load-adaptive admission shed for low-priority traffic (LML#930 PR2)

A third, orthogonal shed layered onto the same enrichment tail the #755 breaker and the LML#930-PR1 caller-deadline shed already govern — `lookup/admission.py`. Where the breaker sheds on a Discogs-side saturation signal (429s / exhausted rate-limit remaining) and the deadline shed sheds when *this request's* budget runs out, the admission shed sheds proactively when the **process event-loop-lag gauge** (#907, `core/event_loop_lag.py`) is elevated **and** the request is **low priority** (`X-Caller-Class=5` single `/lookup`, or any `/lookup/bulk` item — both already set `discogs.ratelimit.is_discogs_low_priority()`) — the loop-starvation case the breaker structurally cannot see, since the loop can be saturated while Discogs itself is perfectly healthy.

The gate sits in `perform_lookup` right after the search pipeline (step 3) and before the PR1 `tail_steps` loop: `evaluate_admission_shed(low_priority=is_discogs_low_priority(), lag_ms=get_event_loop_lag_ms())`. `lag_ms is None` (sampler off, first ~0.5s of process life, or unsampled) always means "never shed" — fail-safe, since shedding blind is worse than not shedding. The threshold (`LML_ADMISSION_LOOP_LAG_SHED_MS`, default 500ms) sits in the wide empty gap between the live gauge's idle (~1.5ms) and flood (~4000ms) modes on low-priority traffic.

**Shadow vs. enforce.** The feature ships gated behind `LML_ADMISSION_SHED_ENFORCE`, default OFF. In shadow mode `evaluate_admission_shed` always projects `would_shed` telemetry when the predicate holds but returns `None`, so the response falls through to PR1's tail exactly as today — merge is a byte-identical no-op that immediately starts collecting the live would-shed rate for calibration against an induced flood (LML#929 rung-a). In enforce mode a would-shed candidate short-circuits to the same `_build_degraded_response` helper PR1 uses, returning `degraded: true` + `degraded_reason: cache_only` (the search results already found, no live enrichment) — reusing the existing, previously-unemitted `DegradedReason.cache_only` rather than a new wire value.

**Composition.** Enforce mode: the gate fires once, before the tail loop, so a shed preempts PR1's per-step `deadline_exceeded` checks for that request (a proactive whole-class load shed is the proximate cause). Shadow mode: the gate is a pure observer and PR1's deadline shed governs unchanged. The #755 breaker is untouched either way — if a tail step still raises `DiscogsBreakerOpenError` the existing catch degrades to `upstream_unavailable`. Three orthogonal reasons for the same tail-shed shape: `cache_only` ("chose not to refresh — load"), `deadline_exceeded` ("ran out of time to ask"), `upstream_unavailable` ("couldn't ask — Discogs saturated").

Telemetry: `lml.admission.would_shed` / `lml.admission.enforced` tags + `lml.admission.loop_lag_ms` measurement on a would-shed (shadow or enforce), plus the `admission_would_shed` cache-stats counter (seeded 0, alertable baseline). The `lml.low_priority` Sentry tag + PostHog property (`lookup/endpoint_family.py::record_low_priority_tag`, set on every `/lookup` + `/lookup/bulk` request) slices the existing `event_loop_lag_ms` measurement by the traffic this gate would actually shed — otherwise a class-5 single `/lookup` is invisible in that measurement. Full knob reference (calibration rationale, rollout/rollback sequence, accepted enforce spellings) in [`env-vars.md`](env-vars.md).

## External-Cache Fallback for `/api/v1/lookup` (Phase 1.5 mojibake recovery)

`POST /api/v1/lookup` accepts an opt-in `include_external_caches: bool` flag (default `false`). When the WXYC library catalog returns no results AND the request supplies an `artist` field AND the flag is set, the orchestrator runs a fuzzy artist-name search against the discogs-cache PostgreSQL DB; on miss it falls through to musicbrainz-cache. The matched canonical name is wrapped in a synthetic `LookupResultItem` (`library_item.id = 0`, `call_number = "(external)"`, `library_url = ""`) so the caller's existing scoring code applies as-is. The response carries an `external_source` field — `'library' | 'discogs' | 'musicbrainz' | null` — for provenance.

Used by the lossy-mojibake matcher (`tubafrenzy/scripts/db/recovery/lossy_mojibake_recovery.py`) to recover canonical artist names for skeletons not in the WXYC physical catalog. Implementation in `lookup/external_search.py`; the discogs-cache trigram query lives in `discogs/cache_service.py:search_artists_by_name`. Both legs UNION their primary artist table with the alias/variation table (discogs: `artist_name_variation`; musicbrainz: `mb_artist_alias`) so ASCII transliterations and alternate spellings hit, and the canonical primary name is what comes back.

Wiring:
- `DATABASE_URL_DISCOGS` (already required for the standard cache) covers the discogs leg.
- `DATABASE_URL_MUSICBRAINZ` is new — when unset the MB leg is skipped silently.
- Existing callers (no flag) see no behavior change and no extra queries.

## Server-Timing response header (Backend-Service#881, Epic G)

`/api/v1/lookup` and `/api/v1/lookup/bulk` surface the per-stage `RequestTelemetry.track_step` timings — already captured for PostHog — as an out-of-band [`Server-Timing`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Server-Timing) header, so a caller can attribute a slow lookup to a named server stage without any `api.yaml` / `CacheStats` change (the JSON body is byte-identical with or without it). The formatter is `RequestTelemetry.as_server_timing(extra=…)` in `wxyc-fastapi` (`>=1.1.0`); the router wires it via `_emit_server_timing_header` on an injected FastAPI `Response`. Grammar: one `name;dur=<ms>` entry per tracked stage (insertion order), then a derived `discogs` leg (`cache_stats` `pg_time_ms + api_time_ms`, guarded when the context is None → 0), then exactly one live `total`; `/lookup/bulk` emits a batch-level `total` only. Gated on `LML_EMIT_SERVER_TIMING` (default on); a build failure logs at WARNING and ships the response without the header (observability never breaks the request path). Because `metadata_enrichment` is wall-clock over concurrent probes, `Σ steps + discogs ≠ total`, and the header `total` is sampled a few ms before the PostHog `total_duration_ms` — two independent measurements. This is the LML half of a cross-repo trace (request-o-matic forwards + merges the header on `/request` and prints it in the `lookup` CLI). Env-var reference in [`env-vars.md`](env-vars.md).

## Streaming-match telemetry (LML#592)

Every winning streaming match emits a lightweight `matcher.match` Sentry span (via `record_match_telemetry` in `clients/streaming/matching.py`) carrying the per-axis fuzzy scores. It is emitted once per resolved match on both surfaces: the album path (`find_best_source_match`, all adapters) and the Apple track path (`find_track_metadata`, which inlines its own `token_set_ratio` floor). Span data keys:

- `matcher.service` — `"apple_music" | "spotify" | "deezer" | "bandcamp"`
- `matcher.surface` — `"album" | "track" | "track_album_less" | "track_album_fallback"`. On the track path the three values distinguish which pass supplied the winner: `"track"` = the album-**constrained** pass; `"track_album_less"` = the request carried no scoreable album at all; `"track_album_fallback"` = the LML#782 album-dropped re-score. The last two were previously both filed under `"track"`, which is why the album-less population could not be sized when LML#1139 was scoped — **any before/after comparison spanning that change must query `surface IN ('track','track_album_less','track_album_fallback')`**, since `"track"` alone is a strictly smaller population after the split than before it.
- `matcher.artist_score` / `matcher.title_score` — raw fuzzy scores (0-100) of the winner
- `matcher.marginal_artist_clear` — `true` when the artist score is marginal (`[SCORE_MATCH_ACCEPTANCE_FLOOR, MARGINAL_ARTIST_CEILING)`) against a high title (`>= HIGH_TITLE_FLOOR`) — the short-name-collision signature (e.g. "Wand" matching "Wanda" on a shared album title)
- `matcher.query_artist` / `matcher.matched_artist` / `matcher.query_title` / `matcher.matched_title` — the request value vs. the winning candidate's value, attached **only on the marginal subset**. The flag + scores measure the marginal-clear *rate*; these strings let a production sample be hand-labeled for the false-positive *rate* (the scores alone can't tell an organic false match `Wand`→`Wanda` from a legitimate `Wand`→`WAND` casing/punctuation diff — both land at ~88). Marginal-only so names don't ride the whole match stream.

The count of `matcher.match` spans is the denominator and the `marginal_artist_clear` subset is the numerator of the marginal-clear rate. This is **instrumentation only** — it measures the 80/80 floor's behavior so the artist-axis floor can be tightened later on evidence, not assumption. Telemetry failures are swallowed (best-effort), so they never break a lookup.

### Title-axis subset guard (LML#719)

The Apple track path (`find_track_metadata`) scores both axes with `token_set_ratio`, which returns 100 whenever one side's tokens are a subset of the other's — regardless of how much unrelated material the longer side carries. On a Various-Artists request the artist axis can't disambiguate (any VA-credited candidate shares the `various artists` token cluster), so a short generic query title buried inside a long unrelated candidate (`Hound Dog` ⊂ `Black leather (The hound dog mix)`, `token_set_ratio` = 100) clears 80/80 against wholly unrelated catalog spam — surfaced from the 2026-07-01 LML#638 telemetry review. To close this, the title axis additionally requires `score_match_track` (suffix-strip + `token_sort_ratio`) to clear the acceptance floor (`title_subset_is_degenerate` in `clients/streaming/matching.py`). This admits legitimate variant subsets — `la paradoja` vs `la paradoja (Live)`, `Back, Baby` vs `Back, Baby (Remastered)` both score 100 after the suffix strip — while rejecting the degenerate one (42.9). The guard is **title-axis only**: the artist axis keeps bare `token_set_ratio` so leader→ensemble subsets (`Yves`→`Yves Tumor`, `J. Mascis`→`J Mascis + The Fog`) still match, and a flat artist-floor raise is deliberately avoided (the LML#638 decision: the `[80,90)` band is inseparable — this VA case sits at 85.7, interleaved with proven-correct short-name variants). Failure mode is safe by construction: a rejected title drops the Apple URL for that item rather than caching a wrong one.

### Artist-axis V/A guard (LML#1139)

Sibling of the title-axis guard above, on the same Apple track path and with the same fail-safe posture — but closing the *other* axis, and for a case no threshold can reach.

WXYC files Various-Artists compilations under a **shelf-genre convention** rather than an artist name: `Various Artists - Blues`, `Various Artists - Latin`, `Various Artists - Jazz`. Because `Various Artists - ` is a constant ~19-character prefix, **any two such credits score ~85 against each other regardless of content** — the shared prefix does all the scoring work and carries zero identifying information. Over 30d of `matcher.match` spans the two highest-volume marginal clears in the entire band were `Various Artists - Blues` → `Various Artists - Document Records` (85.00, n=14) and `Various Artists - Latin` → `Various Artists - Azzurra Music` (85.00, n=4): 18 of 29 labeled false-positive occurrences (62%).

**This is not a threshold problem, and the floor must not be raised.** In the hand-labeled marginal sample the false positives span artist scores 83.87–85.71 while true positives span 80.0–89.55 — the FP band is not merely overlapping the TP band, it is *entirely contained inside* it. The proof case: `Hank Williams, Sr.` → `Hank Williams` (correct) and `Hank Williams, Jr.` → `Hank Williams` (wrong) both score **83.87096774193549**, identical to 14 significant figures. LML#638 closed no-change on the artist floor for this reason; that decision stands and `SCORE_MATCH_ACCEPTANCE_FLOOR` remains 80.0.

It is also not a title problem. Every measured false positive scored **95–100** on the title axis — `I'm On My Way` = `I'm On My Way`, `Desafinado` = `Desafinado` — because these are generic blues/latin standards recorded on hundreds of compilations. The title *genuinely agrees* and still points at the wrong record, so (since `is_acceptable_match` already requires both axes ≥ 80) no title-axis rule rejects them.

What remains is the album axis, and the dominant false-positive surface is precisely where it was discarded: the LML#782 album-dropped fallback ran because the album-constrained pass **rejected every candidate**, then re-admitted a winner on a vacuous artist plus a generic title. The discriminating signal existed and said no.

So: when no album constrains the scoring, a V/A↔V/A candidate is struck (`va_artist_axis_is_uninformative` in `clients/streaming/matching.py`, applied in `_select_best_track_candidate`). A single `norm_album is None` clause covers both the #782 fallback pass and album-less-from-the-start queries. Both sides are tested with `wxyc_etl.text.is_compilation_artist` — the org's canonical, leading-anchored V/A detector — fed the **normalized** artist on each side, which is also exactly the `lml_cache.track_streaming_url_cache` key form, so the guarded key space and the purged key space (see below) are the same space by construction.

Three properties worth keeping straight:

- **Per-candidate, not a winner veto and not fallback suppression — but a strike never promotes.** Only V/A↔V/A candidates are struck; any other candidate in the same response stays eligible on its own merits. That matters because the artist axis keeps `token_set_ratio` deliberately, for leader→ensemble subsets. A bare per-candidate skip would not be safe on its own, though: striking the *top-ranked* candidate would hand the win to whatever scored next, turning the guard into something that **substitutes** a wrong link rather than withholding one. Against a V/A query the only realistic survivor is the trailing-credit class (`CAGAYANO VARIOUS ARTISTS` at 81.08), which is itself a measured false positive — so a naive skip would trade wrong-URL-A for wrong-URL-B. `_select_best_track_candidate` therefore remembers the best struck score and suppresses the pass when it matched or beat the best surviving candidate. Removals are allowed; promotions are not.
- **V/A matching survives through the album-constrained lane** and through the album path (`find_best_source_match`, all 5 services), which is untouched — the 30d telemetry measured zero V/A false positives there.
- **Accepted recall cost.** An album-less V/A↔V/A query that was genuinely right now returns `None` (the real pair `Various Artists - Asia` / `Jombang Jet` → `Various Artists & Pan Ron` at title 100 is pinned in the tests as a deliberate kill), as does a query whose top candidate is struck and whose runner-up cannot out-evidence it. Dropping the Apple URL beats persisting a wrong deep-link, which Backend-Service then stores on `flowsheet.apple_music_url` and never revisits (BS#2000). Note the downstream shape of that cost: a strike surfaces as `StreamingResolutionStatus.absent`, which BS treats as terminal, so the null does not self-heal on a later album-carrying request. That cost was measured rather than estimated, and the decision to keep it is recorded below.

Documented residuals, deliberately out of scope: V/A pairs whose generic album title fuzzy-agrees ≥ 80 and so clears the constrained lane; one-sided/trailing V/A credits (`Various Artists - Xmas` → `CAGAYANO VARIOUS ARTISTS`, which `is_compilation_artist`'s leading anchor does not fire on — pinned in the tests as the boundary case); generational suffixes; surname-only collisions; lineup supersets.

**Cache purge is part of the same deploy.** `lml_cache.track_streaming_url_cache` (LML#893) is hit-only and TTL-less and is peeked *before* the live probe, so pre-guard wrong V/A deep-links would otherwise serve forever on exactly the repeat-play traffic that recurs most, and the guard would never re-adjudicate them. `scripts/purge_va_apple_track_cache.py` clears them; see `docs/scripts.md`.

#### Downstream status decision (LML#1144): the strike stays `absent`

The guard's recall cost was measured retrospectively rather than by instrumenting the strike and soaking. `lml_cache.track_streaming_url_cache` keys on `to_match_form(artist)` — the same string the guard keys on — and stores the pre-guard Apple deep-link, so resolving each cached row's track id back through `catalog/us/songs?ids=` replays the guard's decision offline over a real query population. Over a 14-day window (71,171 rows), 22 of the 67 arbiter-True credit strings appear across 984 rows, and **929 of those 984 (94.4%) would be struck** — about 66/day. The lane split is the opposite of what the guard's scoping assumed: **97% of strikes are LML#782 fallback-lane** strikes where the request *did* carry an album, and only 3% are album-less-from-the-start.

Precision is high. Of 113 hand-labeled strikes (the album-less and 50–79 album-score strata exhaustively, plus 30 sampled from the <50 stratum), **5 were correct** — all cases where the album axis had already rejected the right album on retained punctuation or a `v/a - ` marker typed into the album field, tracked as LML#1148. The rest are unambiguous (`various / mama` → *Karaoke Music to Your Favourite Spice Girls Songs*; `stax-volt: the complete singles 1959-1968 / respect` → *Reggae Bashment Mix Volume 1*). So the guard is not too aggressive.

**The finding that decided it: the album lane is blocked too, so the `absent` really is permanent — but `unresolved` would not fix that.** `apply_streaming_url_postprocess` fires only on a null URL slot and its verdict *overrides* the track probe's `absent` (see `resolve_streaming_status`), so nulling the slot looked like it would hand the 97% to the album-keyed leg for rescue. Measured over 120 struck `(artist, album)` pairs: **0 recover.** The cause is a comparator asymmetry between LML's two Apple paths — the album path scores the artist with `score_match`, the track path with `token_set_ratio`, and against Apple's `Various Artists` the shelf credits fall *under* the 80 floor on the former while scoring 100 on the latter (`various` 63.64, `various artists - blues` 78.95, `various artists - rock - s` 73.17; only `various artists` and `various artists - asia` clear). The vacuous 100 this guard exists to strike is the only thing that gets a shelf credit past any floor at all, and the path that could adjudicate correctly rejects the same string outright. Substituting the canonical `Various Artists` on the identical sample takes recovery to 23/120; that is LML#1147.

Given that, mapping a strike to `unresolved` buys three deterministic re-refusals against a blocked lane — BS#1915's sweep re-asks with the row's own metadata, and 97.6% of V/A flowsheet rows carry an album, always the *same* album. So the status mapping stays `absent`: it is the honest verdict (the probe ran to completion and found nothing adjudicable), and the recall is recovered upstream by LML#1147 rather than by re-asking. A zero-probe pre-check was also rejected — it cannot cover the LML#782 fallback path, which re-enters `_select_best_track_candidate` with `norm_album=None` on a request that *did* carry an album, and that path is 97% of strikes.

One measurement trap worth keeping: `album_normalized` is `text NOT NULL` and part of that table's primary key, so an album-less request is stored as the **empty string**, never NULL — an `IS NULL` predicate silently reports zero album-less rows.

## What Backend-Service does with what LML returns (BS#1747 / BS#1915)

LML's answers are not re-asked on every play, and several decisions in this repo depend on knowing exactly when they stop being re-asked. The rule has been stated wrongly in a handful of docstrings ("BS never re-asks", "freezes permanently"), so it is written here once and cited from the call sites.

**The gate.** Backend-Service's enrichment worker skips the LML call entirely for an album whose `album_metadata` row already carries a non-null **load-bearing** field — `artwork_url` or `discogs_url` (`hasLoadBearingAlbumMetadata` in `apps/enrichment-worker/precheck.ts`). The check exists to kill the per-play LML-call amplifier: a release played 50 times used to pay 50 cold lookups. It keys on the Discogs match because that is what a successful enrichment produces.

**The consequence.** Every *other* field LML returns for that album — the streaming URLs, `artist_bio`, the release scalars — inherits that verdict. Once an album's artwork resolves, those fields stop being refreshed no matter what LML would now return. An LML-side improvement to a non-load-bearing field therefore reaches new albums and unresolved shells, but not the enriched back catalog.

**The bounded exceptions.** This is durable, not permanent, and the difference is easy to get wrong in both directions:

- **BS#1915** re-opens a row whose `spotify_status`, `apple_music_status` or `bandcamp_status` is `'unresolved'`, bounded by a per-album attempt cap (`streaming_reask_attempts`, not per-service). It fires both on the next play of the album and from an hourly sweep, so an album that is never played again still self-heals.
- **`ENRICHMENT_BANDCAMP_REASK`** (default off) additionally de-freezes the legacy shape: `bandcamp_status IS NULL AND bandcamp_url LIKE '%bandcamp.com/search%'` — rows written before the status columns existed.
- **`absent` is terminal.** The re-ask covers `unresolved` only; a service marked `absent` is never revisited, and neither is a NULL status. That asymmetry is why the probe modules map an unmodeled fault to `unresolved` rather than `absent`.

**Two services have no escape at all.** The re-ask set is exactly those three status columns; `album_metadata` has none for YouTube Music or SoundCloud. Anything LML writes into those two slots is frozen for the life of the row once the album's artwork resolves. That is the practical ceiling on `LML_PERSIST_STREAMING_URL_YOUTUBE_MUSIC` (LML#1103) until a `youtube_music_status` column exists — which in turn needs `StreamingResolution.youtube_music` on the wire, since the status columns mirror LML's per-service verdict.

**Where this bites in practice.** A wrong or low-quality value in a non-load-bearing field is not a per-request defect that the next lookup corrects; it is written once and read for the life of the album. That is the reason the templated search-URL fallbacks (`lookup/enrichment/search_urls.py`) are held to a higher bar than their "last tier of the ladder" position suggests, and the reason the Wikipedia bio drain (`scripts/warm_wikipedia_bios.py`) must complete before `LML_BIO_PREFER_WIKIPEDIA` flips.

## Shelf fallback (step 8): design notes

Moved from the `lookup/shelf_fallback.py` module docstring so the module stays small. The module docstring carries the summary; this section carries the reasoning.

Re-scope of the original LML#1391 fix after PR #1396 was closed: five review
rounds each found a way that attempt changed what Backend-Service binds (a
floor-failing row's own release id/artwork leaking onto a typed-album
request). The corrected scope is narrower and purely additive:

    **Invariant: a response that is non-empty on ``main`` stays byte-for-byte
    unchanged. Only a response whose result list is empty today may change.**

(LML#1405 later added one narrow exception, the self-titled companion row
described below; it inserts a display-only row and changes nothing else.)

:func:`apply_shelf_fallback` is called once, as the true last step of the
spine — after the location-union fold has had its chance to populate
``results``, not merely after Step 7 (``_step_external_cache_fallback``).
That placement matters: a request the fold would otherwise resolve (e.g. a
recall-index hit on the comp-track lane) is excluded from this fallback
exactly as it is excluded on ``main`` today, because its post-fold
``result_items`` is non-empty and the invariant above forbids touching it.
Every early return in ``perform_lookup`` for the tail-shed/admission-shed
degraded flavors (``_build_degraded_response``) and the spine-deadline
timeout returns before this call site, so those are excluded structurally.
Four conditions still have to be checked explicitly, because each either sets
its flag and rides the *normal* return path rather than returning early, or
is simply not visible to any earlier gate: the mid-pipeline hard-cap trip
(``state.timed_out``, set inside ``core/search.py``'s strategy loop), the
search-leg Discogs saturation-breaker shed (``state.upstream_shed``,
LML#1126, caught *inside* step 3 and otherwise reaching the final
``LookupResponse`` with ``degraded=True``), a low-priority caller
(``is_discogs_low_priority()`` — bulk/enrichment/backfill traffic, never a
DJ-facing request), and a spent spine deadline
(``services.spine_deadline.tail_exhausted()``, which skips the step's library
queries when the caller's budget — or the hard cap — ran out after the
last tail-shed check). The caller collapses all four into one ``skip`` flag —
there is nothing left for this function to do differently between them.

The low-priority exclusion matters beyond "don't bother": `/lookup/bulk`
unconditionally marks every item low-priority and its per-item
``BulkLookupResultItem.status`` is ``"match" if lookup.results else
"no_match"`` -- a real response-field contract, not telemetry, documented as
"``no_match`` — ``lookup.results`` is empty". Letting this fallback fire
there would make that contract self-contradictory (``no_match`` alongside a
non-empty ``results``) for every bulk caller, which never asked for a
DJ-facing shelf decoration in the first place. Excluding low-priority
callers — the same signal the location-union gate already uses for the same
reason (``lookup/orchestrator.py``, "D4: BS enrichment, the CDC firehose,
and backfills are excluded") — avoids the contradiction at the source
instead of patching bulk's status derivation to match.

When every one of these holds —

* ``result_items`` is empty;
* ``skip`` is false (the caller's ``state.timed_out or state.upstream_shed
  or is_discogs_low_priority()``, plus the spent-deadline term);
* the typed ``parsed.album`` is non-empty after stripping whitespace;
* the library artist has at least one shelved row of its own, read by
  artist rather than out of a ``db.search`` window (LML#1406, see "Reading
  one artist's rows" below). ``filter_results_by_artist`` is deliberately not
  the gate here: its prefix rung admits "Canibus" for "Can" and five
  unrelated "Low ..." artists for "Low", and this lane names the artist in
  its sentence. When the artist has no rows, the step does not fire;
* the library query does not raise — any exception logs a warning and leaves the
  empty response exactly as ``main`` returns it;

this returns the artist's shelf as **display-only** rows:
``LookupResultItem(library_item=row.to_catalog_item())``, with no
``artwork`` — hence no release id, artwork URL, year, Discogs URL, or
streaming links, since none of those ever ride anywhere but on ``artwork``
— and no ``matched_via``. Nothing here calls Discogs, fetches artwork, or
runs enrichment.

``search_type`` is forced to ``SEARCH_TYPE_FALLBACK``, never ``direct`` —
so Backend-Service's ``requireSearchType: 'direct'`` callers keep rejecting
this shape, including the album-only request where ``main`` reports
``direct`` with zero rows (LML#1393). ``external_source`` goes from null
to ``"library"``. ``context_message`` is the sentence
``build_context_message`` already uses for the song-bearing album-miss case
(``lookup.matching.album_not_found_message``), here naming the artist as
the listed rows spell it (``rows[0].artist``, LML#1406) rather than the
typed spelling,
now reachable for the album-only shape too — ``main``'s
``build_context_message`` never reaches it there, since every branch of
its "song not found" message requires ``parsed.song``. ``song_not_found``
and ``found_on_compilation`` are deliberately left untouched: the caller
already computed them correctly before this step runs.

**Telemetry invisibility.** This function returns the count of rows it
appended (0 when it does not fire) as its fifth element,
``shelf_fallback_rows``. The caller must do two things with it, in this
order, both load-bearing: (1) project the existing Sentry
``lookup.results_count``/``lookup.match_type`` trace attrs
(``_project_post_fold_trace_attrs``) *before* calling this function, over
the pre-fallback ``result_items`` -- those attrs, and the LML#1233
``lookup_completed`` ``results_count``/``miss_kind`` PostHog properties
downstream of them, must report exactly what they would without this step
existing, or a genuine recall miss for a shelved artist inflates
``results_count`` and reports ``hit``, blinding the Layer 2 recall-regression
alert to exactly the misses it exists to catch (``lookup/miss_kind.py``);
(2) thread ``shelf_fallback_rows`` into ``derive_miss_kind``/
``miss_telemetry_properties`` at the router, so the *downstream* telemetry
(not just the pre-fold trace attrs) also classifies a shelf-only response as
a miss. The ONE new, separate signal this lane gets is the Sentry trace
attr ``lookup.shelf_fallback_rows`` (set by ``_mark_shelf_fallback_outcome``)
plus the identically-named PostHog property the router adds. Both are
present only when the lane fires (count > 0) and absent otherwise --
observability for the lane without touching any existing series or event
shape.

### Self-titled companion (LML#1405)

A typed self-titled placeholder ("Epon.", "S/T", "eponymous") runs the step-2 song-to-album lookup (LML#1392). When Discogs resolves the song to some other album only, the self-titled record is never searched for: a request for artist X, album "Epon." returns a live album or a compilation and not the record the listener named.

The fix cannot put that record first. `results[0]` is load-bearing in four ways, each of which a promote-to-front attempt (PR #1414, closed) broke:

- Backend-Service `fetchMetadata` binds `results[0].artwork` with no `search_type` gate.
- With `extended=true`, `artist_bio`, `wikipedia_url`, `discogs_artist_id` and `profile_tokens` come from the release bound at `results[0]`.
- `_step_search_pipeline` cuts to `MAX_SEARCH_RESULTS` before step 3b validates, so a row added before the cut evicts a row the pipeline would have returned.
- A row added before step 4 costs Discogs calls (validation and artwork) on low-priority traffic.

So the companion is added in step 8, after every step that reads or binds rows:

- **Appended, never inserted.** Every row already present is the same object in the same position; companions follow them. The location-union fold requires the rows that carry the track to lead, and appending cannot split them.
- **Never under a claim about the rows.** A response with a `context_message` ("Found X by Y on:", "... here are other albums by Y:") or `search_type: compilation` is left alone: the companion is not known to carry the song, so it must not be listed under a line that says it does.
- **Only when there is room.** Nothing is inserted into a response that already holds `MAX_SEARCH_RESULTS` rows; nothing is evicted.
- **Display-only.** The row has no `artwork`, exactly like a shelf-fallback row, so it makes no Discogs call and Backend-Service's all-rows artwork reader (`artwork/providers/discogs.ts`) skips it.
- **Same `skip` gate.** Low-priority callers (`X-Caller-Class: 5`, `/lookup/bulk`), timed-out and shed responses are byte-identical to before.
- **Equality, not overlap.** The row is one of the artist's own (`rows_for_artist`, see "Reading one artist's rows" below) and its title is that row's artist name whole, compared with punctuation folded. `search_one_album`'s word-overlap rule would also admit numbered siblings ("X II", "X III").
- **The LML#1392 literal-title guard holds.** When one of the artist's shelved titles is itself the typed album or a placeholder (R.E.M. "Eponymous", a catalog "S/T"), nothing is inserted.
- `search_type`, `context_message` and `external_source` are untouched, and the row is **not** counted in `shelf_fallback_rows`: the response is a hit with or without it, so `miss_kind` cannot move. The PostHog `results_count` property does count it (it reports what the caller received), while the Sentry `lookup.results_count` attr is projected before step 8 and does not. The "Telemetry invisibility" paragraph above is about the shelf lane only. The Sentry trace attr `lookup.self_titled_companion_rows` is set only when this lane fires.
- **request-o-matic and the row-less probe.** When `results[0]` is a synthesized row-less item (`library_item.id == 0`, step 3a), request-o-matic strips it and used to post "No results found". With the shelved companion behind it, request-o-matic now posts that row.

Known limit: a response that already has `MAX_SEARCH_RESULTS` rows gets no companion.

### Reading one artist's rows (LML#1406, LML#1418, LML#1421)

Until LML#1406 the shelf lane filtered the first 50 rows of `db.search(query=artist)` down to the artist's own. That query is full-text over every indexed column with no artist constraint, so for a common-word name other artists and other artists' titles filled the window first. Measured over every distinct artist in the 2026-10-02 catalog (23,922 artists): 85 artists holding 248 rows got no shelf (The The, Heart, The Band, Love, James, Mountain). The filter was also strict equality, so "The Stereolab", "Clientele" (for The Clientele) and "Melt Banana" (for Melt-Banana) got nothing either.

`lookup/artist_shelf.py::rows_for_artist` replaces the window with two indexed queries on `LibraryDB`:

1. `artist_names_matching(phrases)` returns the distinct stored `artist` values that contain any phrase, matched against the FTS `artist` column only and with no `LIMIT`. Only the artist strings are read, so a wide phrase costs a few milliseconds.
2. The spellings that are the artist are picked in Python (`artist_spellings`), and `rows_by_artist(spellings)` fetches exactly those rows through `idx_artist`, in id order. A caller that needs only some of those rows restricts its own query to the spellings instead (`search_among`, `titles_by_artist`; LML#1421).

Picking runs rung by rung and the first rung with a hit wins: equal under `normalize_for_comparison`; equal with a leading article stripped from both sides; equal with punctuation folded; both. **A tolerant rung answers only when every spelling it matched is one artist under the first rung.** The catalog files "Girls" beside "The Girls" and "A Frames" beside "The Frames", and those are different bands. "The Girls" and "Girls" each reach their own rows on rung 1; "Frames" matches two artists on rung 2 and gets no shelf, as before.

`alternate_artist_name` and `cross_reference_names` are not consulted: a cross-reference files a band's release under a member's name, which is not "other albums by" that member.

Measured over the same catalog by sending each stored artist's name, and variants of it, through the fuzzy artist correction and then both row sources, counting variants that got no shelf from the window and get the right one now: the stored spelling, 85 artists (none lost); a leading "the" added, 22,336; the leading article dropped, 1,504; punctuation folded to spaces, 742 (another 1,128 already resolved through the artist correction). Residue: about two dozen names whose stored spelling carries a symbol the FTS tokenizer keeps as a token character ("Beak>", "D+", "C+C Music Factory"), which a typed form without the symbol does not reach.

Three guards: a rung whose key comes out empty matches nothing, so a typed "The" is not The The; a typed name longer than 120 characters (twice the longest stored name) is not read, because phrase cost is linear in its terms; and the read is two uncached queries, under 2 ms for an ordinary artist, on paths only step 8 reaches: an eligible empty response, or a non-empty one with a typed self-titled placeholder. The widest real names cost more ("Various Artists", 3,113 rows, about 22 ms; "The The", about 16 ms).

The self-titled companion lane reads the same rows (LML#1418). Until then it looked for the row titled the artist's name in the same 50-row window, and compared the title with the typed artist under `normalize_for_comparison`. Two things changed with the read:

- **The literal-title guard looks at the artist's own rows.** It used to run over `filter_results_by_artist(window)`, which also admits prefix and alternate-name matches, so a "Sun Ra Arkestra" row titled "S/T" in the window would have held back Sun Ra's own. Over every stored artist and its article and punctuation variants in the 2026-10-02 catalog (49,710 spellings, three placeholders each) the old guard never fires where the new one does not, and no spelling loses a companion it had.
- **The title is compared with the row's stored artist, punctuation folded.** `rows_for_artist` reaches "The Clientele" from a typed "Clientele", so the typed name is the wrong yardstick; and the catalog files *Esquivel!* under "Esquivel" and *Peace Loving* under "Peace, Loving" (13 such rows).

Measured the same way, by the spellings that gain a companion: the stored spelling, 29 artists (16 crowded out of the window: Can, God, Heart, James, Spirit, The Band, Voices, Women and eight more; 13 by the punctuation fold); a leading article added or dropped, 2,801; punctuation folded to spaces, 162. The 2,793 spellings that already got one are unchanged.

The artist+album lane reads them too (LML#1421). For each album it used to keep the first 50 hits of `db.search(f"{artist} {album}")` whose artist starts with the typed name, and for a common-word name other artists filled those 50 first: in production on 2026-10-02, God / "God" answered with God Rifle's record as an artist fallback and Heads / "Heads" with Heads Up's. `lookup/album_rows.py::album_rows` now first runs that same full-text match with no `LIMIT`, restricted to rows filed under the artist's stored spellings (`artist_spellings`, then `LibraryDB.search_among`: `... WHERE library_fts MATCH ? AND l.artist IN (...)`, so the shelf is never materialized), and puts those rows through the same title filter. Three rules confine the change to the crowding:

- **Only rows the search matches.** The title filter alone is looser than the search. It accepts "DOGA" for a typed "DOGA (Deluxe Edition)", whose row lacks "deluxe" and "edition", so reading the whole shelf through it would add rows, and every added row costs the caller an artwork lookup. A first draft that read the whole shelf added rows to 4,142 of the 85,311 requests measured below.
- **Own rows first, then alternate-name rows; prefix-only rows drop** (LML#1425 decisions 1 and 5). When own rows pass, the window's rows filed under another artist follow them only when their `alternate_artist_name` credits the typed artist as a whole name at its start (`lookup/alternate_credit.py::credits_artist`: the credit equals the name or continues with `, `, ` & `, ` and ` or ` / `). Rows the window admitted only by an artist-column prefix (Alias & Ehren's *Lillian* for the band Alias, "Sun Ra Arkestra" for "Sun Ra"), by a credit that merely starts with the name ("Agnes Obel & Friends" for "Agnes"), or by a cross-reference drop.
- **The window answers when the artist's own rows do not.** When none of them passes, or the artist has no shelf, the lane reads the window as before, so a typed "Sun Ra" still reaches "Sun Ra Arkestra" and an alternate or cross-referenced name still reaches its rows.

Step 2's guards read the same rows. The LML#1412 album = artist guard reads `album_rows`, so the guard and the lane never disagree about the self-titled record. The LML#1392 placeholder guard reads the titles of every row filed under the artist's spellings (`LibraryDB.titles_by_artist`), and the 50-row artist-only window only for an artist with no shelf: otherwise a common-word artist whose own "s/t" row sits outside the window would take step 2, and the lane would rank a single titled after the song above the record. The artist+song and artist-only fallbacks still read the window (LML#1425).

Measured on the 2026-10-06 catalog (`streaming-data-v1`), lane output over every distinct (artist, title) pair plus album = artist for every artist (85,311 requests), against `main`: 53 change, none goes empty, and every `results[0]` change lands on the artist's own row. 15 empty lanes now find the artist's own self-titled row (Blue, Can, Heart, Spirit, The Band and ten more); 11 now lead with the artist's own row instead of another artist's (God, Heads and James also move from an artist fallback to an album match); 25 keep `results[0]` and drop other artists' rows behind it; 2 (John Coltrane, Miles Davis, album = artist) keep `results[0]` and gain own rows the window had cut off. 32 requests drop 36 rows in all: 33 admitted by an artist-name prefix or its article or punctuation fold (17 of them, over 15 requests, a compilation filed again under a "Various Artists - Rock - X" shelf name), and 3 by a credit `credits_artist` refuses ("The Fiendz" for Fiendz, "The Infinity Dive <split> Ereshkigal", "various artists mixed by Rob Swift"). Over every artist, the placeholder guard changes for no request and the album = artist guard skips step 2 for 16 more (the same common-word self-titled records). Cold timings, p50: the lane's per-album read is 0.3-0.4 ms for an ordinary artist (0.1-0.2 ms on `main`) and 1.3 ms for Various Artists (3,113 rows); the placeholder guard is 0.2 ms for an ordinary artist and 4.4 ms for Various Artists, which now reads every title; an album = artist read for Various Artists matches its whole shelf (15 ms).

### Shelf-lane ordering

1. rows whose title contains the requested song (case-insensitive), when a
   song was typed;
2. *(not implemented — see below)*;
3. the rest, in catalog (id) order.

Capped at ``MAX_SEARCH_RESULTS``.

**Tier 2 (cache-confirmed song) is intentionally not implemented.** The one
cache-only, no-live-API primitive that answers "does a cached Discogs
tracklist already show this song on one of these rows" is
``find_library_albums_with_cached_track`` (``lookup/validation.py``, the
step-3b A4 rescue). It already runs — with this exact ``(artist, song)``
pair — against the artist-fallback rows *before* this function can ever see
them, and when it confirms a row, ``apply_track_validation_cascade``
promotes that row into ``library_results``, making the pipeline's own
result non-empty and keeping this fallback from firing at all. Re-running
that probe here would be a second, redundant cache hit that can only
confirm what the pipeline already would have surfaced and promoted first —
it cannot change this function's output, since this function is only ever
reached in the case where that probe already failed. Wiring in a fresh
Discogs-cache dependency here, only to re-ask the same question with no
chance of a different answer, would add a dependency this step does not
otherwise need, against the re-scope's point of staying small and additive.
