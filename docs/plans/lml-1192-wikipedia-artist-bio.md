# Plan: Wikipedia-preferred artist bios on /lookup

Status: v6 — **APPROVED** implementation plan (plan review 2026-08-14, round 5, "approve with suggestions"; all suggestions incorporated below). This issue is the tracking issue for the program; the canonical copy of this document lands **in PR-A** at `docs/plans/lml-1192-wikipedia-artist-bio.md` (this issue is #1192).

## Problem

`artist_bio` on `/api/v1/lookup` and `/api/v1/lookup/bulk` is sourced exclusively from the Discogs artist `profile` (`lookup/enrichment/top1.py:76`). Discogs profiles are inconsistent in quality, carry Discogs-specific markup (`[a123]`/`[r456]` refs needing the `discogs/markup_parser.py` token subsystem), and are often blank. Wikipedia's lead paragraph is usually a better, prose-clean bio. Jake wants Wikipedia as the **preferred** source — first paragraph / introduction — with Discogs as fallback.

## Decisions already made (do not re-litigate)

- **Scope: `/lookup` + `/lookup/bulk` top-1 `artist_bio` only.** `POST /api/v1/artists/genres/bulk` keeps its Discogs bio (follow-up ticket); `GET /discogs/artist/{id}` stays Discogs by definition.
- **No new contract fields, no CC-attribution machinery.** Jake's call (2026-08-13): this is quotation with a link back to the source, and the link-back already exists — `wikipedia_url` flows through the contract into BS's V2 shapes today (`FlowsheetEntryFields.artist_wikipedia_url` / `FlowsheetV2TrackEntry.artist_wikipedia_url` in `generated/api_models.py` — cite by symbol, the file is a regenerated snapshot and line numbers rot, CLAUDE.md #1117 note) and renders in the playcut details view. Wikimedia's Terms of Use accept a hyperlink to the article as attribution, so no `bio_source`/license-notice fields are added; the swap is **client-transparent** (existing `artist_bio` string just gets better text).
- **Precedence: Wikipedia → Discogs profile → null.**

## Non-goals

- No wxyc-shared / api.yaml change, and no BS/iOS/dj-site work — `artist_bio` and `wikipedia_url` already flow end to end.
- No change to `profile_tokens` / `bioTokens` *machinery*. Tokens remain the tokenized *Discogs* profile — the coordinator keeps parsing the Discogs `top1_bio`, never the Wikipedia extract (see the variable split in Phase B). **Accepted semantic shift**: post-swap, a response can carry Wikipedia prose in `artist_bio` and Discogs-profile tokens in `profile_tokens` — two different source texts, no longer two renderings of one bio. PR-B2 rewrites the now-false coherence comment at `lookup/enrichment/item.py:600-608` ("parsed from `top1_bio`") and records the divergence in the `docs/architecture.md` step-4b note so the next reader doesn't treat it as a bug. (Pre-flip check: confirm the iOS About-the-Artist card renders `artist_bio`, not tokens, so the swap is actually visible.)
- No live MusicBrainz/Wikidata dependency (neither local cache carries artist→Wikipedia sitelinks; verified 2026-08-13).
- No Wikipedia circuit breaker. Every sibling upstream carries one (`discogs/breaker.py`, `clients/bandcamp_breaker.py`) because they sit on the request path; Wikipedia is **never** on the request path here — fetches happen only in the `warm_cache`-gated, depth-bounded background task and the offline drain, and every failure degrades to the Discogs bio. If a live request-path fetch is ever proposed, a breaker becomes mandatory first.

## The two constraints that shape the design

1. **A wrong page pick is now wrong *text*, not just a wrong link.** The current `wikipedia_url` extractor is first-substring-match over the Discogs URL list (`lookup/enrichment/top1.py:77-80`) and can surface band-member/album/label pages — the open bug LML#513. Fixing it becomes a hard prerequisite: bio text is only ever fetched from a high-confidence pick.
2. **BS freezes the first LML answer** (BS#1747 precheck: once Discogs/artwork match, BS never re-asks), so a cold-cache first answer is *permanent* for that album. Combined with the warm gate chosen in Phase B (the lazy warm fires only for `warm_cache` opt-in callers, inheriting the LML#742 bulk pin), the Phase-C offline drain is **the** population mechanism for the existing catalog; the lazy warm only extends coverage to newly-played artists going forward.

## Design

### Phase A — Fix the `wikipedia_url` extractor (LML#513)

- New module `lookup/wikipedia_url.py`: `pick_artist_wikipedia_url(urls, artist_name) -> PickedWikiUrl | None`, where `PickedWikiUrl` carries `url`, `lang`, `slug_score`, `below_floor`. Placement rationale: the helper imports the `score_match` / `SCORE_MATCH_ACCEPTANCE_FLOOR` / `strip_discogs_disambig` trio from `clients/streaming/matching.py`, and no `discogs/` module imports from `clients/` today — the edge runs the other way (`clients/bandcamp.py:38` imports `discogs.admission`), so a `discogs/` home would create the repo's first `discogs → clients` edge and a package cycle. `lookup/artist_resolution.py:22-27` already imports the same trio, making `lookup/` the established home.
  - Parse `https?://{lang}.wikipedia.org/wiki/{slug}`; URL-decode slug, `_`→space.
  - **Hard-reject non-artist qualifiers *before* any stripping.** A slug whose parenthetical (or trailing token) is in `{album, song, single, EP, soundtrack, film, TV series, discography}` is rejected outright — stripping first would destroy the only signal separating artist pages from *eponymous* album pages (`Sessa_(album)` → `Sessa` scores 100 against artist `Sessa`; `normalize_album_title` inside `score_match` compounds it by stripping bare `EP`/`LP` suffixes). These are red-first cases in the table-driven extractor tests.
  - Only then strip the residual disambig suffix with the **existing** `strip_discogs_disambig` (`clients/streaming/matching.py:363-380` — handles `(band)` / `(2)` / `(UK)` shapes; no hand-rolled paren stripping).
  - Score against `details.name` with the existing `score_match` + `SCORE_MATCH_ACCEPTANCE_FLOOR` trio, imported exactly the way `lookup/artist_resolution.py:22-27` already does for artist-name comparison. Known and accepted: `score_match` normalizes through `normalize_album_title` (strips `LP`/`EP`/`12"`) before scoring — fine for artist names, `lookup/strategies/va_rescue.py:108` already relies on the same behavior; stated here so it isn't later read as a bug.
  - Return the highest-scoring candidate with `score >= 80` (the shared floor); `en` wins score ties, but foreign-language wikis are *not* rejected (Noura Mint Seymali-class artists have only non-`en` coverage).
  - Below-floor → fall back to the current first-match pick for the `wikipedia_url` *link* field (avoid regressing populated→None), returned with `below_floor=True` — Phase B **never fetches bio text for a below-floor pick**.
- **`top1.py` changes here — this plan touches it** (the earlier "untouched" claim was self-contradictory; only `lookup/orchestrator.py` stays untouched). `fetch_top1_release_details` swaps the inline `next(...)` at `top1.py:77-80` for the extractor call, and its returned `wiki` element widens from `str | None` to `PickedWikiUrl | None` (same 5-tuple arity); the single unpack site at `lookup/enrichment/__init__.py:243-248` adapts. `top1.py` importing `lookup/wikipedia_url.py` is fine: its docstring contract (`top1.py:1-12`) constrains the *signature* — "one service handle", no per-item handles — not which packages it imports; a pure scoring function adds no handle. **PR-A's coordinator adaptation must be line-neutral** — the coordinator has zero budget headroom in PR-A (the funding relocation lands in PR-B2), so the `.url` unwrap at the `enrich_one(top1_wiki=...)` call site is an in-place edit of the existing line, comment-free. If it cannot stay line-neutral, the `background.maybe_schedule_discogs_bio_warm` relocation moves forward into PR-A as its own pre-step commit.
- Flag: `LML_WIKIPEDIA_SLUG_MATCH`, **default OFF**, `_TRUE_FLAG_VALUES` enable set — the earlier default-ON draft contradicted the "everything lands flag-off" Project-32 mitigation and the house measure-first idiom (`docs/env-vars.md:62`, LML#930 PR2: ship shadow, calibrate on live traffic, then flip). Documented in `docs/env-vars.md`.
- Telemetry: the `set_data` projection `(heuristic_pick, slug_pick, agreement)` + 1% sampled INFO log (mirroring `_log_artist_identity_split_gate`, `lookup/enrichment/item.py:412-427`) **fires regardless of the flag** — shadow mode computes both picks so production divergence is quantified while responses stay byte-identical. The projection/log pair **lives in `lookup/wikipedia_url.py`** (it already computes both picks; `top1.py`'s 17 lines of headroom can't host it), which is why that module is budgeted at 150. Flip staging → prod only after the < 2% regression gate is confirmed on live traffic, not just the offline sample.
- **Empirical gate (from #513):** sample 300 artists from the local Discogs PG (`artist_url` rows containing `wikipedia.org`), compare picks, hand-classify. Regression rate (heuristic right, slug wrong) must be < 2%. Script goes in `scripts/` with results pasted into #513.
- Deliberate divergence from #513's Option B: the helper lands **in LML Python**, not `wxyc_etl.text` (Rust). Rationale: no Rust release/pin-bump gating this program; the promotion to wxyc-etl + the BS-side adoption (`proxy.controller.ts:498`) stay on #513, which remains open for that half.

### Phase B — Wikipedia summary client + cache + read-path swap

**Client** — `clients/wikipedia.py`:

- httpx (already a dependency), `GET https://{lang}.wikipedia.org/api/rest_v1/page/summary/{title}` following redirects. The `extract` field is exactly "first paragraph / introduction" as plain text.
- User-Agent follows the house Wikimedia-family convention (`entity/sources.py:178`): `WXYCBioLookup/0.1 (https://wxyc.org; engineering@wxyc.org)` — org contact, not a personal address. 4s total timeout; single retry on background/warm paths only. On HTTP 429 the client honors `Retry-After` (sleep-and-retry in the drain; treat as a shed in the background warm — never a tight retry loop).
- Reject `type != "standard"` (disambiguation pages return `type: disambiguation`) and empty extracts → negative-cache.
- **Reject on the payload's `description` field** — the closed-form guard the slug denylist can't be. The denylist (Phase A) is an open-vocabulary guess: an unlisted qualifier (`(mixtape)`, `(record label)`, `(film score)`…) gets stripped by `strip_discogs_disambig`, scores 100, and would serve album/label text as the artist bio. The `/page/summary` `description` is authoritative ("1975 studio album by X", "American musician"): reject on `^\d{4} .*(album|EP|single|mixtape)` / `(album|song|single|EP) by ` patterns alongside the `type` check → negative-cache. The slug denylist stays as the cheap pre-filter that avoids the fetch entirely.

**Cache** — new `lml_cache.artist_wikipedia_bio` (LML-owned schema; lifespan-bootstrapped, zero discogs-cache coordination), following the actual `lml_cache.*` mechanism:

- **Runtime source of truth is `entity/artist_wikipedia_bio.py`** — DDL string constants + `set_up_artist_wikipedia_bio_schema(pg)` built on the `entity/ddl.py` primitives (`bootstrap_lml_cache_table`), registered as a new `(label, fn)` entry in the `bootstraps` tuple in `main.py` (currently `main.py:392-472`) so it runs under the existing lifespan advisory lock.
- The `.sql` sidecar is **generated** by `scripts/regenerate_lml_cache_sql.py` (add the module there) and pinned by the per-module parity test, never hand-written.
- Columns: `discogs_artist_id BIGINT PRIMARY KEY`, `wikipedia_url TEXT NOT NULL` (the Phase-A pick the extract came from), `slug_score SMALLINT NOT NULL` (audit: extractor confidence at fetch time), `lang TEXT NOT NULL`, `extract TEXT` (NULL = negative result: 404 / disambig / empty), `fetched_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
- **Freshness is read-side, not writer-enforced**, per the house TTL pattern (`entity/cache_toolkit.py`, `entity/release_resolution_cache.py:36-57`): the read predicate is a `fetched_at > now() - $ttl` cutoff returning the three-valued `CachedValue`; the negative TTL re-exports the existing `DEFAULT_MISS_TTL` (7d) rather than restating it, and the success TTL is a named module constant in `entity/artist_wikipedia_bio.py` (30d) with a written rationale, the way `release_resolution_cache.py:103` documents its 90d — Wikipedia lead paragraphs churn (deaths, new releases, editorial rewrites) far faster than a resolved `release_id`, which is why this cache doesn't inherit the sibling's value. Reads/writes wrapped in `swallowing_fetch` / `swallowing_execute` so a PG hiccup degrades to a cache miss instead of breaking `/lookup`.

**Read path** — new module `lookup/enrichment/wikipedia_bio.py` (see budget accounting above) called once by the coordinator; `top1.py` stays Discogs-only, `orchestrator.py` untouched. The variable split is the crux — `top1_bio` has two other consumers in the coordinator that must keep seeing the **Discogs** text:

1. `top1_bio` (Discogs profile) stays untouched everywhere it exists today: the `profile_tokens` cache-only parse (`lookup/enrichment/__init__.py:299-308`) and the Discogs ref-warm (relocated to `background.maybe_schedule_discogs_bio_warm`) keep operating on Discogs markup, never on Wikipedia prose.
2. `wikipedia_bio.resolve_served_bio(pick, top1_bio, top1_details, discogs_cache_pg)` returns the `served_top1_bio` / `served_top1_wiki` pair. The PG handle is the coordinator's existing `discogs_cache_pg: PgSource | None` (`lookup/enrichment/__init__.py:89`) — the same borrowed pool `main.py` bootstraps every `lml_cache.*` table on and the sibling `lml_cache` read at `item.py:490` uses; when it's `None`, the function degrades straight to the Discogs pair, matching that sibling's posture. It passed into `item.enrich_one(top1_bio=..., top1_wiki=...)`. Flag off, `pick is None`, or `pick.below_floor` → the Discogs pair, byte-identical behavior. Flag on + above-floor pick → one `CachedValue` read of `lml_cache.artist_wikipedia_bio`: fresh hit with non-null `extract` **and `row.wikipedia_url == pick.url`** → `(extract, row.wikipedia_url)` (the served link always points at the page the text came from); a fresh hit whose stored URL diverges from the current pick is **treated as a miss** — self-healing when Discogs URL data or the scorer changes post-drain, and it keeps the served text and the Phase-A telemetry describing the same pick; negative hit **with the same `row.wikipedia_url == pick.url` predicate** → Discogs pair — a negative recorded against a *different* URL is a miss, not a suppression (otherwise a scorer recalibration that moves the pick off a 404/disambig page stays suppressed for the full 7d negative TTL); miss → Discogs pair + schedule the warm task (below). `LML_BIO_PREFER_WIKIPEDIA` is inert unless `LML_WIKIPEDIA_SLUG_MATCH` is ON: with slug-match off there is no above-floor pick, so no text is ever fetched or served from the legacy first-match URL.

   **Amended (LML#1192 review round 6): the `row.wikipedia_url == pick.url` read predicate above did not survive to shipped code.** Round 5 review deleted it outright, not merely under-documented it: `entity/artist_wikipedia_bio.py`'s `get_cached_artist_wikipedia_bio` is keyed on `discogs_artist_id` alone, with no `wikipedia_url` filter — a hit returns whichever `wikipedia_url` the row carries, full stop. Reason: a fetch-validated background warm can legitimately write a row under a DIFFERENT, better URL than the caller's own unvalidated sync pick (e.g. a bare disambiguation-page sync pick vs. a validated qualified `_(band)` warm pick); keying the read on URL equality made that row permanently unreadable by a caller whose sync pick never changes, reintroducing a live Wikipedia dependency on the request path the plan's Non-goals rule out. The freshness property the deleted predicate used to provide is re-homed onto the cache's two TTLs (30d positive / 7d negative) plus `scripts/warm_wikipedia_bios.py --repick` — see that module's docstring for the full account. `docs/env-vars.md`, `docs/architecture.md`, and `docs/adr/0002-wikipedia-preferred-artist-bio.md` were corrected to match in round 6; this paragraph is left as the historical record of the pre-round-5 design rather than rewritten, per this doc's own convention (see the round-5 amendment on the `lookup/enrichment/__init__.py` budget above).
3. `enrich_one` applies the LML#504 artist-identity split gate to the served pair exactly as today (`lookup/enrichment/item.py:396-398` nulls bio/link together) — the pair can never disagree.
4. The relocated Discogs ref-warm gate is re-specified: it currently reads the *served* `enriched[0][1].artist_bio` (`lookup/enrichment/__init__.py:344`), which no longer answers "was the Discogs bio surfaced". New condition: `warm_cache and top1_bio and top1_bio_surfaced and served bio is the Discogs bio` — when Wikipedia text is what iOS renders, deep-parsing the unrendered Discogs profile's refs is exactly the quota burn the LML#504 comment prohibits.

**Miss-warm** — fire-and-forget Wikipedia fetch→cache-write on a cache miss. **The gate is the existing `warm_cache` opt-in, named explicitly** (previous draft's "pinned off on bulk" had no mechanism — `enrich_artwork_results` receives no endpoint-family signal; the LML#742 pin expresses itself solely as `warm_cache=False`, `lookup/router.py:1002-1024`):

- Keying off `warm_cache` (default `False` at `lookup/enrichment/__init__.py:82`) inherits the bulk pin for free and means the warm fires **only for write-path opt-in callers** (BS's flowsheet-linkage commit), not on every single-`/lookup` miss. Accepted consequence, restated from the constraints section: the drain is the population mechanism; the lazy warm is incremental coverage for artists newly entering the flowsheet. (Even for the committing entry itself, BS#1747 freezes the Discogs answer — the warm benefits that artist's *subsequent* albums.)
- Depth-bound admission + shed counter modeled on `lookup/streaming_warm_admission.py` (LML#1108), owned by the dedicated `lookup/enrichment/wikipedia_warm.py` (see budget accounting): bounded queue depth, concurrency 2, a dedicated shed stat key — never an unbounded task set behind a semaphore. Strong-reference task set + done-callback per `lookup/enrichment/background.py`; errors logged and swallowed; no Sentry scope tagging.

**Flag** — `LML_BIO_PREFER_WIKIPEDIA`, default OFF, `_TRUE_FLAG_VALUES` enable set (same polarity as `LML_ADMISSION_SHED_ENFORCE`), read per-request via `os.getenv` so it's a no-redeploy Railway lever and instant kill switch. Documented in `docs/env-vars.md`.

**No new hot-path hop**: request path cost is one PG read on the flag path; live Wikipedia HTTP happens only in admitted background tasks and the Phase-C drain. This respects the Project-32 latency posture and the 4s deadline shed.

### Phase C — Offline pre-warm drain (the primary population mechanism)

- `scripts/warm_wikipedia_bios.py`: seed = distinct Discogs artist ids from the discogs-cache `artist_url` table whose URLs contain `wikipedia.org`, intersected with library artists; run each through the Phase-A extractor; fetch summaries throttled (≤ 3 rps, sequential batches, `Retry-After`-honoring backoff on 429); UPSERT into `lml_cache.artist_wikipedia_bio`.
- House drain conventions: resumable state, `--retry-misses` semantics (retry NULL-extract rows only; never touch successful rows by default — data-safety rule), logging + error handling, runbook note in `docs/scripts.md`.
- Plus an explicit `--repick` mode: re-runs the extractor over already-successful rows and rewrites those whose stored `wikipedia_url` no longer matches the current pick — the operator lever for post-calibration corrections that `--retry-misses` deliberately can't reach. Operator-invoked and targeted (only divergent rows), so it stays inside the data-safety rule rather than fighting it; the read-side URL-match check above self-heals lazily either way.
- Rough scale: bounded by library artists with a Discogs-known Wikipedia URL — expect low-tens-of-thousands; at 3 rps that's a few hours across 1–2 sessions.

2. Slug-match flip first: PR-A's shadow telemetry runs on live traffic; once the < 2% regression gate holds there, flip `LML_WIKIPEDIA_SLUG_MATCH=true` on staging, then prod. (`LML_BIO_PREFER_WIKIPEDIA` is inert without it.)
3. Staging (`main`): run a scoped drain slice, flip `LML_BIO_PREFER_WIKIPEDIA=true` on staging only, verify `/lookup` responses (bio/link coherent, #504 gate still nulls unverified identities, `profile_tokens` still Discogs), watch the new counters. ## Risks

- **Project-32 freeze adjacency.** `lookup/orchestrator.py` is a listed critical surface; this program touches its extraction (`lookup/enrichment/__init__.py`, `item.py`, `top1.py`). Mitigation: `orchestrator.py` itself untouched; everything lands flag-off (byte-identical responses); Jake signs off on timing vs the project's "no new features in touched files" posture before PR-B2 merges.
- **Wrong-page text.** Strictly worse than a wrong link. Mitigation: text only ever served from an above-floor (≥80) slug-scored pick + `type: standard` + the #504 identity gate still in front; the < 2% regression gate in Phase A is the empirical check.
- **BS first-answer freeze (BS#1747).** Mitigated by drain-before-flip ordering; residual: artists absent from the drain seed get Discogs on first ask and frozen — acceptable, it's today's behavior.
- **Client-transparency assumption.** The swap assumes consumers render `artist_bio` as opaque prose. Any client parsing Discogs markup out of `artist_bio` itself (rather than using `profile_tokens`) would mis-render plain Wikipedia text's absence of markup — verify none does during the staging burn-in (expected: none; that's what `profile_tokens` exists for).
- **Licensing posture.** Recorded decision (Jake, 2026-08-13): short excerpt + link back to the source article, which the playcut details view already renders via `wikipedia_url`; Wikimedia ToU accept a hyperlink to the article as attribution. No license-notice rendering. LML guarantees the served link always points at the exact source page of the served text.
- **Wikipedia availability.** Background/drain-only fetches; an outage degrades to Discogs bios, no request-path impact. No breaker by design (see Non-goals).
