# Plan — make the /lookup location-union transparent: fold shelf locations into `results`

**Written:** 2026-07-31 PT
**Revised:** 2026-07-31 PT — folded in the round-2 `/review-plan` findings (`external_source`/`search_type` reconciliation, degraded-path flag recompute, kill-switch-off wording, api.yaml anchor re-check) and the performance review (await-site move, bounded degraded-path await, probe timeout risk, #1026 sequencing upgrade). Round 3 same day: module line-budget recalibration (`test_module_budgets.py`), the converter's missing-shelf-item branch, the `config/settings.py` kill-switch docstring, and the `lookup/strategies/` path fix. Round 4 (approval with suggestions) same day: signal reconciliation stays in the orchestrator (moving it to `location_union.py` would close an import cycle via `build_context_message`); converter builds `lookup.models.LookupResultItem`, not the generated class; `search_type` reconciles to `"compilation"` via the existing `get_search_type_from_state` mapping; LML#1026 chains as the immediately-following PR, not the same PR.
**Supersedes:** the separate-field design shipped in wxyc-shared#270, LML#1022, and request-o-matic#199.
**Driver:** product direction — "the whole idea was that we wouldn't present 'also available on X' to the user. We're just presenting results." The alternate library shelf locations for a track must be surfaced as ordinary results, fully transparent to consumers — no opt-in flag, no separate field, no labeled "Also available on:" section.

---

## 1. Context: what shipped vs. what was intended

Per the #1018 product decision, `/lookup` is WXYC's operational physical-library index: on a track query it should surface the primary match **plus every other library shelf location that carries the same track** (V/A compilations, soundtracks). The recall index `lml_cache.compilation_track_location` (LML#1019) is the cheap precomputed source for those locations.

The **implementation** (LML#1022 / wxyc-shared#270) realized this as:
- a request opt-in flag `LookupRequest.include_locations` (default false), and
- a separate response array `LookupResponse.also_available_on: LibraryLocation[]`, which consumers must know about and render themselves.

ROM#199 (merged to ROM `origin/main`, `b35baa3`, staging only) then rendered that field as a labeled **"Also available on:"** Slack section.

This is the leaky abstraction the product direction rejects. Every consumer has to (a) opt in and (b) special-case a second collection. The intended model is that the locations are simply **more results** — consumers render `results` and the shelf locations appear there like any other match, with zero new handling.

**Nothing is user-visible yet.** The prod recall index is empty (0 rows), so `also_available_on` is always empty and ROM's section never renders. We can course-correct the design before it ever reaches a DJ — no live output to clean up, no incident pressure.

## 2. Empirical finding: the fold is lossless within the existing contract

A `LibraryLocation` can be represented as an ordinary `LookupResultItem` with **no information loss and no new schema**:

| `LibraryLocation` field | Home in `LookupResultItem` |
|---|---|
| `library_id` | `library_item.id` (positive → real shelved release) |
| `album_title` | `library_item.title` |
| `artist` (shelf artist, e.g. "Soundtracks - L") | `library_item.artist` |
| (rest of shelf metadata: call_number, genre, format, library_url…) | already fetched by the probe's shelf join `db.get_items_by_ids`, so a full `LibraryCatalogItem` is constructible |
| `track_title` | `matched_via[0].title` |
| `track_artist` (per-track credit) | `matched_via[0].artist_credit` |
| `track_position` | `matched_via[0].position` |
| (source provenance) | `matched_via[0].source = discogs_release` (recall index carries `discogs_release_id`; honest, **no new enum value**) |
| `discogs_release_id` | `artwork.release_id` |
| `artwork_url` | `artwork.artwork_url` (+ derived `release_url`); streaming URLs stay null → honest "physical-only" row |
| `credit_role` (primary/featured/extra) | **ranking-only signal — consumed server-side before assembly, never displayed.** No wire home needed. |

`matched_via` is the field the catalog-track-search work already added for exactly this purpose ("a track-title match drove this release into the results"), and **dj-site's `MatchedTrackChips` already renders it.** So folding shelf locations into `results` tagged with `matched_via` lights up existing consumer rendering for free.

## 3. Target end state

1. **`/lookup` returns shelf locations inside `results`.** On a track query, after the primary result(s), LML appends one `LookupResultItem` per other shelf location carrying the track (deduped against the primary's library ids), each tagged with a `matched_via` `TrackMatchHint`. Ranking (credit-tier → title-ratio → library_id) determines order among the appended items; the primary always precedes them.
2. **The wire contract loses `include_locations` and `also_available_on`** (and the `LibraryLocation` schema). Consumers render `results` — nothing else.
3. **Gating is entirely server-side and identity-based.** LML runs the recall-index probe for interactive track lookups and skips it for the low-priority lane (`X-Caller-Class=5`: enrichment worker, CDC firehose, backfills). No consumer opt-in. The `LML_LOCATION_UNION_ENABLED` kill switch survives.
4. **Consumers change little or nothing.** ROM#199 reverts (locations appear in its normal results loop). dj-site's `MatchedTrackChips` renders the new items automatically wherever it consumes `/lookup`-backed results.

## 4. Design decisions (forks + recommendations)

**D1 — Presentation shape.** Fold into `results` (RECOMMEND) vs. keep a separate field consumers merge. Rejecting the latter: it keeps the leak (consumers must know a second collection exists). Only folding into `results` is truly transparent.

**D2 — Depth.** Lean probe appended as `results` items (RECOMMEND) vs. running comp locations through the full main search pipeline (live Discogs enrichment per location). Rejecting the latter: it reintroduces the per-location Discogs cost the LML#1019 precomputed index was built to avoid, and collides with the project-32 enrichment-latency freeze. The lean items are honest (physical-only, streaming URLs null, precomputed art).

**D3 — Contract migration.** Fully remove `include_locations` + `also_available_on` + `LibraryLocation` now (RECOMMEND) vs. deprecate them as no-op shims for one minor. Rejecting the shim: there are **zero live consumers** (ROM#199 is staging-only and we revert it; the prod index is empty). oasdiff will flag removing a response field and a request param as breaking — expected and acceptable at zero consumers; take the version bump wxyc-shared's policy assigns.

**D4 — Server-side gate.** Run on `song present` + kill-switch + **`not is_discogs_low_priority()`** (RECOMMEND), i.e. default-run for interactive callers, opt-out for class 5. **Reuse the existing context var, do not thread a new parameter:** `perform_lookup`'s signature is explicitly frozen (LML#722, `router.py:910`); `is_discogs_low_priority()` is already imported and used in the orchestrator (`orchestrator.py:43,1128`), is set from `is_low_priority_caller_class(caller_class)` in the router (`router.py:521,532`), is inherited into the union task's context (`~:1105-1109`), and bulk sets it unconditionally `True` (`:868`) so the firehose skips correctly. Gate on it inside the orchestrator — no signature change. Rejecting the request flag (leaky) and default-off-unless-known-interactive (would silently under-serve any interactive caller BS hasn't registered). **Precondition to verify:** BS forwards `X-Caller-Class=5` on the enrichment/CDC/backfill callers (per BS#1826/#1843 it does when the caller is registered). If a firehose caller is unregistered it would pay one cheap indexed btree probe and get extra trailing items it ignores — functionally safe, but the probe cost is what the freeze cares about, so registration must be confirmed before promoting to prod.

**D5 — `matched_via` source tag.** Reuse `discogs_release` (RECOMMEND) — the recall index rows are Discogs-release-derived and carry `discogs_release_id`. Avoids a `TrackMatchSource` enum addition.

## 7. Risks and mitigations

- **A consumer that renders *all* of `results` will now show location rows.** Desired for ROM/dj-site. Audit other `/lookup` consumers: BS enrichment takes `results[0]` (extras ignored → safe); iOS/Android consume via BS, not LML directly. Confirm no consumer treats `results` as "matches for exactly the queried release."
- **Lean items are visibly sparser** (no streaming links). Honest — they represent a physical shelf location — but confirm ROM/dj-site render a streamless result acceptably.
- **Ranking must keep the primary first.** The append-after-primaries construction guarantees it; test Case A explicitly.
- **State/flag/telemetry desync from the fold** (the review's High finding; round 2 added `external_source`/`search_type` and the degraded-path flag recompute as Mediums) — addressed in §5.2's "reconcile all state-derived signals from the final post-fold `result_items`" step (now covering both response fields), the degraded-path recompute, and the telemetry-agreement test; called out here so it stays visible.
- **External-cache (mojibake) fallback suppression** — addressed by ordering the fold *after* `_step_external_cache_fallback` in §5.2; regression-tested by the "external-fallback-still-runs on a primary miss" case.
- **Losing the physical backups on a degraded shed** — the current design deliberately preserves the locations across every shed (`orchestrator.py:1278-1280`); the fold must too (§5.2 degraded-path bullet), or a Discogs-down shed strips exactly the physical-shelf fallback a DJ needs. Regression-tested by the "degraded/shed path still carries the locations" case.
- **Firehose probe cost** depends on the D4 registration precondition. Quantified: an unregistered class-5 caller pays one extra connection acquire per song-bearing request against the shared discogs-cache pool — default `max_size=5` (`entity/sources.py:34-35`), and staging shares prod's PG — so at CDC-flood rates (the LML#337 incident class) this is pool contention, not just probe CPU. `/lookup/bulk` sets low-priority unconditionally (`router.py:868`); confirm the firehose actually rides bulk, which shrinks the residual exposure to the singular-lookup enrichment worker. Verify before prod promotion; kill switch is the incident lever.
- **The probe has no timeout, and default-on makes that matter.** `get_compilation_track_locations` swallows exceptions but not slowness; a slow pool acquire or PG hiccup becomes spine latency on every interactive track lookup (nobody paid under opt-in-default-false). Mitigations: the §5.2 await-site move (the happy path gives the probe the whole tail to finish), the bounded degraded-path await, and a `command_timeout`/acquire bound on the probe itself as belt-and-suspenders. This is squarely the failure class the project-32 freeze exists for. One qualifier on "races step 3 for free": the shelf join runs on the same shared aiosqlite connection as step 3's searches, and aiosqlite serializes onto one background thread — the join interleaves with step 3 rather than truly overlapping (single-digit-ms `IN` query; no action needed, just don't count on full parallelism).
- **Removing a just-published contract field** is an oasdiff-breaking change. Acceptable at zero live consumers; coordinate the version bump and the downstream regen order (wxyc-shared publish → LML/ROM regen), per the standard cross-repo api-model merge order.
